# PEMatching V1 实施方案：企业标准 JSON 先行，政策条件暂不标准化

## 1. 背景与目标

当前 `backend/PEMatching` 已具备以下真实链路能力：

- 企业侧：可读取 `backend/PEMatching/Enterprisedata/企业数据(1).json`
- 政策侧：可通过 `structure` 接口拉取主政策详情，并提取 `structured_conditions`
- 匹配侧：已支持离线 CLI 和轻量 API

但现有匹配结果仍主要依赖 LLM 直接输出“匹配率/星级推荐”，尚未形成符合 `20260721政策申报条件细化聚类.xlsx` 要求的可解释评分体系。

本期实施目标：

1. 先把企业原始数据统一转换为企业标准 JSON
2. 基于企业标准 JSON 完成硬性/软性、定量/定性的本地评分
3. 政策条件暂不做完整标准化，继续复用当前 `structured_conditions`
4. 将 LLM 从主评分器调整为解释器和兜底补充器

## 2. 本期边界

| 项目 | 本期决策 |
|---|---|
| 交付范围 | 仅覆盖 `backend/PEMatching` 的离线 CLI 和同链路 API |
| 政策条件标准化 | 暂不做一级/二级类别标准模型，只做轻量规则识别 |
| 企业标准 JSON 存储 | 运行时生成，不新增数据库表 |
| 输出兼容性 | 保留 `政策标题`、`匹配率`、`星级推荐`、`是否推荐`、`条件匹配详情`、`总体建议` 等字段 |
| 主排序依据 | 改为 `final_score` |

## 3. 企业标准 JSON 设计

企业标准 JSON 按以下七组组织：

1. `基础信息`
2. `经营与行业`
3. `研发与人员`
4. `知识产权与成果`
5. `经营规模与成长性`
6. `合规与资质`
7. `元数据`

每个核心字段统一保留以下信息：

| 字段 | 说明 |
|---|---|
| `字段名` | 标准字段名称 |
| `标准值` | 用于评分的归一化值 |
| `单位` | 统一单位 |
| `原始来源字段` | 对应原始 JSON 字段名，可为多个 |
| `原始证据文本` | 用于回溯的文本证据 |
| `数据状态` | `原始` / `缺失补齐` / `推断` |
| `数据类型` | `定量` / `定性` / `布尔` |

### 3.1 关键字段示例

| 分组 | 核心字段 |
|---|---|
| 基础信息 | 企业名称、统一社会信用代码、注册日期、注册地、主体类型、是否在厦注册 |
| 经营与行业 | 一级行业、二级行业、三级行业、科技服务领域、业务标签、核心技术领域、主要产品或服务 |
| 研发与人员 | 职工总数、科技人员总数、科技人员占比、博士人数、硕士人数、本科人数、研发费用总额、研发费用占销售收入比例、研发机构认定 |
| 知识产权与成果 | I类知识产权数量、II类知识产权数量、知识产权总数、高新技术企业认定、科技型中小企业认定、新型研发机构认定 |
| 经营规模与成长性 | 注册资金、资产总额、净资产、销售收入、主营业务收入、利润总额、纳税总额 |
| 合规与资质 | 合规经营状态、企业信用状态、荣誉资质、单位类型 |

## 4. 缺失值策略

Excel 明确要求“无数据默认均值，而不是空或 0”，本期采用如下规则：

1. 对研发、人员、营收、知识产权等关键评分字段引入默认均值配置
2. 默认值配置文件位置：`backend/PEMatching/config/enterprise_feature_defaults.json`
3. 对明确来自原始记录的真实数值保留原值
4. 对平台快照中的占位 `0`，若字段被配置为 `treat_zero_as_missing=true`，则视为缺失并回填均值
5. 在标准 JSON 中显式标记 `数据状态=缺失补齐`

## 5. 评分体系

### 5.1 总体公式

```text
final_score = hard_gate * (score_A * 0.7 + score_B * 0.3) * coeff_C
```

### 5.2 评分步骤

1. `硬性预筛`
   - 先检查注册地、主体类型、强制资质、合规限制、明确硬门槛
   - 任一不通过则 `final_score = 0`
2. `A 类直接命中评分`
   - 直接依赖标准字段判断的布尔/数值条件
   - 例如：注册地、高新资质、研发占比、知识产权数量、销售收入门槛
3. `B 类间接命中评分`
   - 基于行业、业务标签、荣誉、简介文本等弱映射字段进行匹配
4. `C 类定性系数修正`
   - 对行业领域、核心技术、主营产品、研发管理等文本条件做相似度修正
   - 系数区间固定为 `0.8 ~ 1.2`

### 5.3 细则

| 类别 | 规则 |
|---|---|
| 硬性指标 | 不通过直接 0 分 |
| 软性定量 | 按 `min(1.5 * 企业值 / 达标值, 1.0)` 计分 |
| 软性布尔 | “有”计 0.7，“无”计 0 |
| 软性定性 | 使用文本余弦相似度近似值转换为 `0.8 ~ 1.2` 系数 |

## 6. 政策侧处理策略

本期明确不做“政策标准 JSON”。

政策侧继续复用 `policy_loader.py` 产出的 `structured_conditions`，只做轻量规则识别：

1. 高频关键词识别
   - 例如：高新技术企业、科技型中小企业、新型研发机构、注册地、独立法人
2. 数值阈值识别
   - 例如：科技人员占比、研发费用占比、知识产权数量、销售收入、资产总额
3. 布尔/否定条件识别
   - 例如：重大安全事故、严重环境违法、经营异常、失信记录
4. 行业和技术领域相似度修正

## 7. 输出字段

在现有匹配结果基础上，新增以下机器可读字段：

| 字段 | 说明 |
|---|---|
| `hard_pass` | 是否通过硬性预筛 |
| `hard_fail_items` | 硬性未通过原因列表 |
| `score_A` | A 类得分 |
| `score_B` | B 类得分 |
| `coeff_C` | C 类定性修正系数 |
| `raw_score` | 未乘以 C 系数前的分数 |
| `final_score` | 最终总分 |
| `enterprise_standard_snapshot` | 企业标准 JSON 快照 |

## 8. 实施顺序

1. 新增默认值配置与方案文档
2. 改造 `enterprise_loader.py`
   - 加载企业默认值配置
   - 标准化企业字段
   - 聚合同企业重复记录
   - 生成标准 JSON 快照
3. 新增 `scoring_service.py`
   - 解析 `structured_conditions`
   - 执行硬性/软性/A/B/C 评分
4. 改造 `matching_service.py`
   - 先走本地 scorer
   - 再按需调用 LLM 生成解释
5. 通过小样本和 `--validate-only` 方式验证链路

## 9. 测试要点

| 场景 | 验收要求 |
|---|---|
| 企业字段缺失 | 不再默认写死 0，而是走缺失补齐并有状态标记 |
| 硬性指标淘汰 | 返回 `hard_pass=false`、`final_score=0` 和失败原因 |
| 定量指标门槛 | 分数符合 `1.5` 补强系数和封顶规则 |
| 定性匹配 | 相似度高低对 `coeff_C` 有明确影响 |
| 兼容老结果 | 原有字段不丢失，新增字段可直接供后续前端/API 消费 |
