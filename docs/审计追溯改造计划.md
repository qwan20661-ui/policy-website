# 前端写库链路审计追溯改造计划

> 文档日期：2026-07-15
> 适用架构：Node 网关 `server.js` + Java JDBC 中间层 `JDBCService.java` + 达梦数据库 `SYSDBA`

---

## 一、背景与目标

当前项目已经进入前端可直接维护、审核、删除、保存结构化结果的阶段，但多数业务表只保留了业务字段，缺少统一的操作人追溯能力。

现阶段存在三个典型问题：

| 问题 | 现状 | 风险 |
|---|---|---|
| 最后修改人不可见 | 多数表没有 `CREATED_BY` / `UPDATED_BY` | 页面难以展示“谁改的” |
| 一次操作的联动写库不可追溯 | `fusion-detail/save`、审核、关联关系调整会同时改多张表 | 排查问题时只能猜测链路 |
| 删除行为缺少证据 | 部分接口仍为物理删除 | 删除后原表记录消失，无法回放 |

本次改造目标不是单纯“补几个字段”，而是建立一套适合当前项目的轻量审计体系，满足以下目标：

| 目标 | 说明 |
|---|---|
| 看当前状态 | 能快速知道一条记录是谁创建、谁最后修改、最后修改时间是什么时候 |
| 查完整历史 | 能追溯某个用户在某个时间点做了什么操作 |
| 串联一次前端操作 | 能把一次页面点击触发的多表写入串成同一个操作事件 |
| 保持改造可控 | 不大幅改现有接口契约，不做过重的历史分表体系 |

## 二、推荐方案

本项目推荐采用“**业务表最小审计字段 + 统一审计日志表**”的混合方案。

### 2.1 方案对比

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 仅新增一张统一审计日志表 | 历史集中、便于回放 | 页面要显示最后修改人时需要额外查日志；当前状态查询成本高 | 不建议单独使用 |
| 每张表仅补 `创建/修改人+时间` | 当前状态展示方便 | 只能看到最后一次修改，无法看完整历史；物理删除后证据丢失 | 不建议单独使用 |
| 每张表都做完整 history 表 | 审计能力最强 | 表多、链路复杂、维护成本高，不适合当前项目节奏 | 暂不采用 |
| **业务表最小审计字段 + 统一审计日志表** | 同时兼顾当前状态展示和完整追溯，成本可控 | 需要同时改数据库、网关、JDBC 写入链路 | **推荐采用** |

### 2.2 推荐设计原则

| 原则 | 说明 |
|---|---|
| 时间字段复用现有字段 | 已有 `CREATED_AT` / `UPDATED_AT`、`CREATE_TIME` / `UPDATE_TIME`、`CREATE_AT` / `UPDATE_AT` 的表，不重复新增时间字段 |
| 操作人字段统一 | 默认补 `CREATED_BY`、`UPDATED_BY`，长度建议统一 `VARCHAR2(100)` |
| 专用审核字段保留语义 | 如 `MARK_REVIEWED_BY`、`MARK_REVIEWED_AT`、`CONFIRMED_BY`、`CONFIRMED_AT` 继续保留，不拿它们替代通用审计字段 |
| 一次前端操作生成一个链路 ID | 例如 `TRACE_ID`，用于把一次保存涉及的多表更新串联起来 |
| 删除优先留痕 | 即使暂不全部改为软删，也要保证删前写入统一审计日志表 |

## 三、改造范围判定标准

本次范围不是只看“页面直接编辑哪张表”，而是按“**前端用户动作是否会触发写库**”来判定。

### 3.1 纳入首批改造的范围

| 判定标准 | 是否纳入 |
|---|---|
| 前端页面直接新增、编辑、审核、删除的表 | 是 |
| 前端一次保存动作联动写入的结果表、关系表、缓存表 | 是 |
| 前端高频使用且需要展示最后修改人的表 | 是 |

### 3.2 暂不纳入首批的范围

| 判定标准 | 是否纳入 |
|---|---|
| 系统表、数据库内部统计表 | 否 |
| 当前前端仅读不写的基础来源表 | 暂不纳入首批 |
| 仅离线导入脚本写入、当前页面无写操作的表 | 暂不纳入首批 |

## 五、业务表字段改造策略

### 5.1 统一规则

| 场景 | 处理策略 |
|---|---|
| 表已有创建时间字段 | 不新增创建时间字段 |
| 表已有修改时间字段 | 不新增修改时间字段 |
| 表无创建时间字段 | 新增 `CREATED_AT TIMESTAMP DEFAULT CURRENT_TIMESTAMP` |

## 六、统一审计日志表设计

建议新增一张统一审计日志表，例如：`SYSDBA.OPERATION_AUDIT_LOG`。

### 6.1 设计目标

| 目标 | 说明 |
|---|---|
| 记录操作事件 | 谁在什么时间做了什么 |
| 记录影响对象 | 哪张表、哪条记录被修改 |
| 串联多表操作 | 同一次页面保存使用同一个 `TRACE_ID` |
| 为删除留痕 | 删除前先写审计日志 |

### 6.2 建议字段

| 字段 | 类型建议 | 说明 |
|---|---|---|
| `ID` | `VARCHAR2(36)` | 主键 UUID |
| `TRACE_ID` | `VARCHAR2(64)` | 一次用户操作的链路 ID |
| `MODULE` | `VARCHAR2(100)` | 模块名，如 `base-data`、`fusion-detail` |
| `ACTION` | `VARCHAR2(50)` | 操作类型，如 `create/update/delete/approve/revoke/link/move` |
| `TARGET_TABLE` | `VARCHAR2(100)` | 目标表名 |
| `TARGET_ID` | `VARCHAR2(100)` | 目标主键 |
| `BIZ_KEY` | `VARCHAR2(200)` | 业务主键，如 `sourcePolicyId`、`fusionPolicyId` |
| `OPERATOR_ID` | `VARCHAR2(100)` | 操作人 ID |
| `OPERATOR_NAME` | `VARCHAR2(100)` | 操作人姓名/用户名 |
| `BEFORE_JSON` | `CLOB` | 修改前快照 |
| `AFTER_JSON` | `CLOB` | 修改后快照 |
| `REMARK` | `VARCHAR2(1000)` | 备注 |
| `CREATED_AT` | `TIMESTAMP` | 日志写入时间 |

### 6.3 建议索引

| 索引字段 | 用途 |
|---|---|
| `TRACE_ID` | 查询一次操作涉及的全部表 |
| `TARGET_TABLE, TARGET_ID` | 查询某条业务记录的历史 |
| `OPERATOR_NAME, CREATED_AT` | 查询某个操作人的历史 |
| `MODULE, ACTION, CREATED_AT` | 查询某模块某类动作的历史 |

## 七、操作人来源设计

当前项目已经具备登录态和用户名获取能力，建议直接复用，不再让每个页面各自拼接。

### 7.1 当前基础

| 位置 | 现状 |
|---|---|
| `server.js` | 通过 `policy_session` 保存 Node 会话，`/api/auth/session` 可拿到当前用户 |
| `JDBCService.java` | 登录接口返回 `id / username / realName / role` |
| `policy-classification.html` | 已有 `resolveReviewerName()`，部分接口手工传 `operator` / `reviewedBy` |

### 7.2 推荐改造

| 层级 | 改造建议 |
|---|---|
| 前端 | 不再让各页面分别维护操作人传参逻辑，除特殊审核字段外尽量不显式传 `operator` |
| Node 网关 | 从会话中统一获取当前用户，在转发给 JDBC 时注入 `operatorId`、`operatorName`、`traceId` |
| JDBC 层 | 写库时统一使用 `operatorName` 赋值到 `CREATED_BY` / `UPDATED_BY`，并同步写审计日志 |

### 7.3 保留兼容项

对于已经存在显式审核传参的接口，如 `reviewedBy`、`operator`，建议先兼容保留，再逐步过渡到统一注入。

## 八、接口与写库链路改造顺序

### 8.1 第一批：直接维护型接口

| 接口前缀 | 主要目标 |
|---|---|
| `/api/baseDataDict/*` | 补通用审计字段和日志 |
| `/api/baseDataRecords/*` | 补通用审计字段和日志 |
| `/api/categoryFieldInfo/*` | 补通用审计字段和日志 |

### 8.2 第二批：审核与融合维护型接口

| 接口前缀 | 主要目标 |
|---|---|
| `/api/policies/update` | 补 `POLICY_METADATA` / `POLICY` 的更新人和日志 |
| `/api/policies/approve` / `/api/policies/revoke` | 补审核行为日志 |
| `/api/attachment-types/update` / `approve` / `revoke` | 补 `POLICY_ATTACHMENT` 审计 |
| `/api/fusion-classification/policies/*` | 补 `X1_FUSION_POLICY` 审计 |
| `/api/fusion-classification/documents/*` | 补 `X1_POLICY_DOCUMENT` / `X1_POLICY_BASE_INFO` 审计 |
| `/api/fusion-classification/policies/parent/update` | 补 `X1_FUSION_POLICY_RELATION` 审计 |
| `/api/fusion-trace/save` | 补 `FUSION_TRACE_CACHE` 审计 |

### 8.3 第三批：结构化详情联动保存接口

| 接口 | 主要目标 |
|---|---|
| `/api/fusion-classification/fusion-detail/save` | 给所有联动更新表补 `UPDATED_BY`、缺失时间字段、统一写审计日志 |

这条链路是本次改造的重点难点，因为一次保存会影响多张结果表，必须引入统一 `TRACE_ID`。

### 8.4 第四批：删除链路

| 接口 | 当前问题 | 改造建议 |
|---|---|---|
| `/api/classification/policies/delete` | 物理删除多张表 | 删除前写统一审计日志，后续可评估改软删 |
| `base-data` 删除接口 | 物理删除 | 删前写日志，必要时补快照 |
| 融合文档删除 | 部分已软删 | 继续补操作人和统一日志 |

## 九、实施阶段计划

### 9.1 阶段划分

| 阶段 | 目标 | 产出 |
|---|---|---|
| 第 1 阶段 | 冻结范围和字段规范 | 本文档 + 最终纳入表清单 |
| 第 2 阶段 | 新建统一审计日志表 | 审计表 SQL |
| 第 3 阶段 | 打通 Node 会话用户统一注入 | 网关透传方案 |
| 第 4 阶段 | 改直接维护型表和接口 | 第一批 SQL + 后端代码 |
| 第 5 阶段 | 改融合审核和关系维护链 | 第二批 SQL + 后端代码 |
| 第 6 阶段 | 改 `fusion-detail/save` 联动保存链 | 第三批 SQL + 后端代码 |
| 第 7 阶段 | 改删除链路和文档 | 删除留痕 + 文档更新 |

### 9.2 推荐优先级

| 优先级 | 先做内容 | 原因 |
|---|---|---|
| P0 | 统一 `operatorId/operatorName/traceId` 注入 | 后续所有接口都依赖这套能力 |
| P1 | `base-data` 相关表 | 改造简单、容易先形成标准 |
| P2 | `POLICY_METADATA` / `POLICY_ATTACHMENT` / `X1_FUSION_POLICY` / `X1_POLICY_DOCUMENT` | 当前高频操作区，审计价值最高 |
| P3 | `fusion-detail/save` 联动表 | 链路复杂，放在统一框架稳定后实施 |
| P4 | 删除审计 | 需要结合现有删除策略评估 |

## 十、风险与注意事项

| 风险点 | 说明 | 应对建议 |
|---|---|---|
| 字段命名不统一 | 部分表是 `CREATE_TIME`，部分是 `CREATED_AT` | 不强行统一旧字段名，只补人字段和缺失时间字段 |
| 一次保存更新多张表 | 如果没有统一 `TRACE_ID`，日志会碎片化 | 强制在网关层生成并透传 `TRACE_ID` |
| 物理删除导致原表证据丢失 | 仅改原表字段不够 | 删除前先写统一审计日志 |
| 前后端分别传操作人 | 容易漏传或不一致 | 尽量改为 Node 网关统一注入 |
| 旧运行进程未重启 | 改完代码和 SQL 后，live 行为可能仍是旧版本 | 每阶段实施后都要区分“源码已改”与“运行态已更新” |

## 十一、验收标准

### 11.1 功能验收

| 验收项 | 标准 |
|---|---|
| 页面新增记录 | 原表能看到创建人、创建时间 |
| 页面更新记录 | 原表能看到最后修改人、最后修改时间 |
| 页面审核动作 | 原表审计字段更新，统一日志表有记录 |
| `fusion-detail/save` | 同一次保存涉及的多表日志可通过 `TRACE_ID` 串联 |
| 页面删除动作 | 即使物理删除，也能在统一日志表中找到删除前快照或关键信息 |

### 11.2 文档验收

| 文档 | 要求 |
|---|---|
| `docs/database_schema.md` | 同步新增审计字段和审计日志表说明 |
| 接口文档 | 标明操作人和审计行为影响 |
| 本文档 | 作为后续实施基线保留 |

## 十二、结论

本项目不适合走“只做一张审计表”或“每张表都做完整历史表”这两种极端方案。

最适合当前架构和节奏的做法是：

1. 给前端写库链路涉及的业务表补齐最小审计字段。
2. 新增一张统一审计日志表记录完整操作事件。
3. 由 Node 会话统一注入当前登录用户和操作链路 ID。
4. 按“基础数据 -> 审核/融合 -> 结构化联动保存 -> 删除链路”的顺序分批实施。

这样既能满足页面展示“最后修改人/最后修改时间”，又能满足问题排查、责任追踪和多表联动回放的需要，实施成本也能控制在当前项目可接受范围内。
