# 企业政策匹配新规则

> 版本：V1.0  
> 日期：2026-08-06  
> 状态：需求确认稿，作为后续重构与验收基准  
> 适用目录：`backend/PEMatching_v2`

---

## 1. 目标与边界

### 1.1 目标

输入企业完整画像，从审核通过的主政策中找出：

1. 企业当前已经具备较多申报条件的政策；
2. 企业当前尚未完全达标，但通过成长可以达到的政策；
3. 按申报条件符合程度和政策时效性排序的全部可推荐政策。

本系统不是法律意义上的资格认定工具。最终申报资格仍以政策原文、主管部门审核和企业实际申报材料为准。

### 1.2 不再采用的设计

1. 不再使用 A/B/C/D/E/F 六维政策标签作为核心召回和评分依据；
2. 不再使用旧 150 分制；
3. 不再通过多轮 Agent 自主决定检索、评分和排序；
4. 不再把所有硬性条件失败统一解释为整条政策不推荐；
5. 不再逐条件单独调用模型；
6. 不再仅依赖标准字段映射判断全部申报条件。

### 1.3 核心原则

1. `ruleTableJson` 是审核后的正式核验条件目录，存在有效规则时优先且仅以该目录参与评分；
2. 政策原始 `applicationRequirement` 用于解释规则语义、记录冲突，并在规则表为空时作为条件发现的回退来源；
3. 模型负责理解条件、核对企业证据并给出逐条件分数；
4. 服务端负责证据校验、数值复算、AND/OR 聚合、业务排除和时效加权；
5. 缺失、明确为 0、明确不满足必须严格区分；
6. 模型没有企业证据时不得推测或编造。

## 2. 政策数据源

### 2.1 主政策范围

服务每次启动时同步一次当前已经完成两级审核的主政策：

```text
GET http://127.0.0.1:3000/api/fusion-classification/policies
    ?page=1
    &size=100
    &reviewStatus=1
    &requireSourcePolicyId=1
    &structureReviewStatus=1
```

当前核验结果为 78 条，实际运行时以接口 `pagination.total` 为准，不在代码中写死政策数量。

不使用 `structureReviewStatus=all` 的结果参与推荐。

### 2.2 政策详情

每条主政策通过以下接口读取详情：

```text
GET http://127.0.0.1:3000/api/fusion-classification/fusion-detail
    ?fusionPolicyId={政策ID}
```

### 2.3 核心字段

| 数据 | 字段 | 用途 |
|---|---|---|
| 审核状态 | `reviewStatus`、`structureReviewStatus` | 确定是否进入政策库 |
| 标识 | `id`、`sourcePolicyId`、标题 | 唯一定位和展示 |
| 政策信息 | `policyInfo.summary` | 模型理解政策背景 |
| 行业 | `policyInfo.industryField`、`industryFieldPath` | 行业适用性判断 |
| 属地 | `policyInfo.applicableScope`、`applicableScopePath` | 属地适用性判断 |
| 场景 | `policyInfo.sceneUsage`、`sceneUsagePath` | 政策用途和资质目标判断 |
| 申报条件 | `conditions[].applicationRequirement` | 规则语义、冲突审计及规则表为空时的回退依据 |
| 申报对象 | `conditions[].applicableTarget`、`applicableTargetPath` | 主体适用性判断 |
| 申报时间 | `applicationStartTime`、`applicationEndTime`、`applicationInstruction`、`announcementDate` | 时效判断 |
| 结构化规则 | `ruleTableJson` | 硬性、软性、条件组、目标值和单位 |
| 支持方式 | `supportMethods` | 研发补助等业务分类及支持力度 |
| 关键词 | `keywords` | 资质、研发、专利和场景辅助判断 |
| 文档 | `documents.publishDate`、`policyAttribute`、`reviewStatus` | 政策年份和动作类型判断 |
| 关联关系 | 父政策、子政策、祖先政策 | 政策链路辅助判断 |

申报材料、附件、联系方式不参与核心匹配。

政策有效期与申报期是不同概念，不得用 `effectiveStartDate/effectiveEndDate` 直接替代申报时间。

### 2.4 数据冲突口径

当 `applicationRequirement` 与 `ruleTableJson` 存在遗漏、冲突或错误分组时：

1. `ruleTableJson` 存在有效条件时，以其硬性、软性、目标值、单位和 AND/OR 结构作为正式核验目录；
2. 模型使用 `applicationRequirement` 理解规则语义并检查遗漏或冲突；
3. 发现冲突时输出冲突信息和对应原文，不得静默覆盖规则表；
4. 原文明示但规则表遗漏的条件只进入冲突审计，不参与本次评分；
5. 仅当 `ruleTableJson` 没有有效条件时，才从 `applicationRequirement` 回退发现并核验条件。

## 3. 企业画像数据

### 3.1 允许使用的数据

模型允许读取完整企业画像，包括：

1. 注册时间、注册类型、注册地址、行政区和园区；
2. 行业分类、高新技术领域、企业简介、产品和服务介绍；
3. 营收、主营收入、资产、研发费用、研发占比、技术合同额；
4. 员工、研发人员、学历人才、科技人员数据；
5. Ⅰ类、Ⅱ类知识产权、发明专利和知识产权总数；
6. 科小、创新型中小企业、高企、专精特新、小巨人等资质；
7. 研发机构、研发会计科目、产学研合作等研发条件；
8. 主要技术、主要产品、荣誉资质等结构化子表；
9. 上游补充的 `eligibilityFacts`。

### 3.2 证据约束

1. 模型必须返回企业证据字段路径、字段原值和简短证据文本；
2. 允许根据企业简介、产品、技术等文本做语义判断；
3. 不允许仅根据企业名称、行业惯例或常识补全事实；
4. 企业字段不存在时必须返回数据缺失；
5. 相邻概念不得无条件等价，例如营业收入不得直接替代主营业务收入；
6. 允许使用已经确认的业务代理字段，但必须标明代理来源。

## 4. 总体匹配流程

```text
服务启动
  → 同步 78 条已审核政策及详情
  → 代码组装政策条件包
  → 构建企业画像
  → 执行全局和明确业务排除
  → 对每条剩余候选政策调用一次模型
  → 模型判断该政策全部条件并逐条件给分
  → 服务端校验证据和数值
  → 服务端按 AND/OR 聚合条件分
  → 加入小权重时效分
  → 排除无任何有效匹配的政策
  → 返回全部可推荐政策并排序
```

### 4.1 候选政策与推荐政策

模型调用前的政策统一称为候选政策。只有模型完成条件判断、服务端完成校验和排除后，才能称为推荐政策。

### 4.2 模型调用粒度

1. 一条候选政策调用一次模型；
2. 一次调用包含该政策全部硬性、软性和特殊通道条件；
3. 不同政策可以受控并发；
4. 不允许一条条件调用一次模型；
5. 不允许把全部政策和全部条件一次性放入同一个超长请求。

一个政策内统一判断可以保留条件上下文和 AND/OR 关系，也能避免重复发送企业画像。

## 5. 条件类型与术语

### 5.1 硬性与软性

硬性、软性和分组仅从有效 `ruleTableJson` 读取。模型必须对照原文检查分类是否合理，但不得据此新增计分条件；规则表为空时才回退原文。

硬性条件不再天然等于一票否决，必须进一步判断失败效果：

| 失败效果 | 含义 | 处理 |
|---|---|---|
| 范围不适用 | 主体、属地、行业明确不在范围 | 直接排除 |
| 不可逆 | 成立年限已超过、规模上限已超过 | 直接排除 |
| 可成长 | 营收、研发、人员、资质等未来可达到 | 保留并按完成度计分 |
| 普通软性差距 | 当前未达到但不影响政策相关性 | 保留并扣分 |
| 数据缺失 | 企业没有可验证数据 | 记缺失分，不算条件命中 |

### 5.2 `unresolved`

`unresolved` 表示政策条件已经抽取，但尚未绑定到经过确认的企业标准字段。它不代表条件无效，也不代表不支持。

企业匹配阶段由模型结合 `enterpriseFields`、条件原文和完整企业画像寻找证据。

### 5.3 `llm_judge`

`llm_judge` 表示不能只用单个数值操作符完成判断，需要模型进行语义核对或组合事实判断。

若条件实际可以通过多个结构化字段确定性计算，例如比较两个年度研发费用，应优先由服务端复算，不应永久依赖模型结论。

### 5.4 AND/OR

1. AND 组：组内条件分数取平均；
2. OR 组：组内分支分数取最高值；
3. OR 任一分支为 100 分，整个组为 100 分；
4. 原文有“或、任一、满足其一”等表达时必须保留 OR；
5. 模型发现规则表把原文 OR 错写成 AND 时，以原文修正本次判断并记录冲突。

特殊通道作为政策定义的替代满足路径处理，不设置未经确认的固定加分或保底分。

## 6. 直接排除规则

### 6.1 企业级信用拦截

企业明确存在失信或经营异常时：

1. 不推荐任何政策；
2. 返回企业异常说明；
3. 不继续调用逐政策模型。

信用字段缺失不得解释为信用正常，也不得触发信用拦截。

### 6.2 申报主体

政策明确只面向个人、高校、事业单位或其他非企业主体，当前企业主体不在允许范围时直接排除。

模型应综合 `applicableTarget`、`applicableTargetPath` 和 `applicationRequirement` 判断，不能只依赖标题关键词。

### 6.3 属地

政策明确限定行政区、园区或特定范围，企业注册地明确不在范围内时直接排除。

范围无法精确判断时不得直接排除，应交给模型返回缺失或低置信判断。

### 6.4 行业

政策明确限定特定行业，企业行业明确不属于该范围时直接排除。

政策为通用行业或企业行业无法确定时，不因行业直接排除。

### 6.5 政策年份

以当前年份为基准：

1. 只推荐今年和去年的政策；
2. 前年及更早政策直接排除；
3. 今年或去年的政策无论是否已经截止都可以推荐；
4. 截止状态只影响时效分，不直接决定推荐与否。

政策年份优先使用申报时间，缺失时参考已审核文档的发布时间和申报说明。

### 6.6 已有资质

企业已经具备某项资质时，不再推荐申请同一资质或更低层级资质的政策，只推荐资质链下一步。

已有资质判断以企业画像明确为 `true` 为准。

### 6.7 知识产权与研发补助

企业确认没有知识产权时，不推荐研发补助类政策。

按照本项目约定，Ⅰ类、Ⅱ类字段都为空时也按无专利处理，不进入研发补助推荐。

### 6.8 不可逆上限

以下条件明确不满足时直接排除：

1. 成立年限不超过某值，但企业已超过该年限；
2. 营收、员工、资产等规定最高上限，但企业已明确超过；
3. 其他无法通过正常成长重新满足的条件。

### 6.9 没有任何有效匹配

1. 政策有条件，但企业全部条件都缺数据：不推荐；
2. 政策所有可判断条件均为 0 分：不推荐；
3. 缺失条件的 10 分不算“条件已达到”；
4. 至少存在一个有企业事实支撑且分数大于 0 的条件，才进入正常推荐排序。

如果政策本身同时缺少有效 `applicationRequirement` 和有效 `ruleTableJson`，可以按行业、属地、资质链暂时保留在结果末尾，但不得伪造条件分，等待政策数据后续补齐。

## 7. 成长型推荐规则

### 7.1 基本原则

企业当前未达到政策条件，但条件能够通过正常经营成长达到时，政策仍可以推荐。

因此，“硬性未满足”不再自动转换为“不推荐”，模型必须识别该条件是否可成长。

### 7.2 最低门槛

最低营收、研发投入、员工数量、研发人员、资质、知识产权等条件当前未达到时：

1. 保留政策；
2. 按当前完成度给分；
3. 明确企业当前值、政策目标值和差距；
4. 不得因为硬性标签直接把整条政策记为 0。

### 7.3 资质成长链

资质链不是强制单线序列，允许存在业务分支，但只推荐企业当前状态的直接下一步，不跨级推荐远期资质。

当前确认链路：

| 当前状态 | 下一步政策 |
|---|---|
| 无科技资质 | 创新型中小企业、科技型中小企业 |
| 创新型中小企业 | 专精特新中小企业 |
| 科技型中小企业 | 国家级高新技术企业 |
| 国家级高新技术企业 | 新型研发机构、未来产业骨干企业等直接后继政策 |
| 专精特新中小企业 | 创新联合体、科技小巨人、规模以上工业企业等符合行业条件的后继政策 |
| 专精特新小巨人 | 制造业单项冠军、独角兽、瞪羚等符合行业条件的后继政策 |
| 上市后备培育企业 | 上市企业相关下一步政策 |

企业资质字段全部为空时，按“无资质”处理，只推荐资质链起点。

技术交易奖励类政策需要结合技术合同认定和技术交易事实判断。

## 8. 知识产权口径

### 8.1 字段

| 字段 | 含义 |
|---|---|
| `ipClass1Count` | Ⅰ类知识产权数量 |
| `ipClass2Count` | Ⅱ类知识产权数量 |
| `inventionPatentCount` | 发明专利授权总量 |
| `ipCount` | 知识产权总数 |

### 8.2 判断规则

1. 政策只要求“有知识产权”时，优先使用 `ipClass1Count + ipClass2Count`；
2. 政策明确要求Ⅰ类知识产权时，只使用 `ipClass1Count`；
3. 政策明确要求Ⅱ类知识产权时，只使用 `ipClass2Count`；
4. 政策要求发明专利时优先使用 `inventionPatentCount`；
5. 即使 `inventionPatentCount` 为 0 或为空，也允许使用Ⅰ类、Ⅱ类知识产权总量作为业务代理依据；
6. 使用代理时必须标注“使用知识产权总量作为替代依据”，不得表述为企业已确认拥有发明专利；
7. Ⅰ类、Ⅱ类同时为空时按无专利处理；
8. Ⅰ类、Ⅱ类明确为 `0 + 0` 时按无专利处理。

## 9. 条件评分

### 9.1 模型逐条件输出

模型必须为每个条件输出：

1. 条件标识和原文片段；
2. 硬性或软性；
3. 所属 AND/OR 组；
4. `satisfied`、`partially_satisfied`、`not_satisfied` 或 `missing`；
5. 失败效果：范围不适用、不可逆、可成长或普通差距；
6. 0～100 条件建议分；
7. 企业证据路径、原值和证据文本；
8. 判断理由和置信度。

### 9.2 数值最低门槛

对于“企业值 ≥ 政策目标值”类条件：

```text
达到或超过目标：100 分
未达到目标：企业实际值 ÷ 政策目标值 × 100
```

例如政策要求营收 2000 万元，企业为 1400 万元，条件分为 70 分。

分数限制在 0～100 范围，不再采用“30分起步 + 完成比例”的旧公式。

### 9.3 数值最高上限

企业值在上限内记 100 分。企业明确超过不可逆上限时直接排除，不再按反向比例保留。

### 9.4 明确条件与缺失条件

| 情况 | 条件分 | 是否算条件命中 |
|---|---:|---|
| 明确满足 | 100 | 是 |
| 明确部分达到 | 按完成比例 | 是 |
| 明确不满足 | 0 | 否 |
| 数据缺失 | 10 | 否 |

语义条件由模型根据企业证据给出 0～100 分，服务端校验证据是否真实存在。

### 9.5 聚合

1. AND 条件组取组内条件平均分；
2. OR 条件组取各分支最高分；
3. 各正常条件组暂按等权平均得到 `conditionScore`；
4. 硬性、软性暂不设置额外权重，后续有人工标注数据后再校准；
5. 直接排除规则优先于总分。

### 9.6 时效分

第一版采用可配置的小权重时效分：

| 状态 | 初始时效分 |
|---|---:|
| 今年正在申报 | 100 |
| 今年尚未启动 | 85 |
| 今年已经截止 | 70 |
| 去年政策 | 50 |
| 前年及更早 | 直接排除 |

初始总分：

```text
finalScore = conditionScore × 90% + timelinessScore × 10%
```

时效权重和分值属于可调配置，不写死在模型提示词中。

### 9.7 服务端校验

模型只返回逐条件语义状态、建议分和证据路径。服务端负责：

1. 根据路径回读企业事实，不接受模型回填事实值；
2. 复算可计算的数值条件分；
3. 计算 AND/OR 组分和 `verifiedConditionScore`；
4. 计算时效分和 `finalScore`；
5. 根据已核验证据生成直接排除结论。

正式排序只使用服务端复算的 `finalScore`，不要求模型重复计算条件总分和最终总分。

## 10. 模型输入输出契约

### 10.1 单政策输入

每次模型调用只包含一个政策：

```json
{
  "schemaVersion": "policy-condition-match-input-v2",
  "policy": {
    "fusionPolicyId": "6451",
    "title": "政策标题",
    "policyInfo": {},
    "conditions": [],
    "ruleTableJson": {},
    "keywords": []
  },
  "enterprise": {
    "facts": [
      {"path": "$.metrics.revenueWan", "value": 1400, "label": "企业营业收入"}
    ]
  },
  "evaluationRules": {
    "missingScore": 10,
    "minimumThresholdFormula": "actual/target*100",
    "conditionKeys": []
  }
}
```

### 10.2 模型输出

```json
{
  "schemaVersion": "policy-condition-match-output-v2",
  "sourceConflicts": [],
  "conditionResults": [
    {
      "conditionKey": "C3-B1/S3-1",
      "status": "partially_satisfied",
      "failureEffect": "growable",
      "score": 70,
      "evidencePaths": ["$.metrics.revenueWan"],
      "reason": "政策门槛为2000万元，当前完成度为70%",
      "confidence": "high"
    }
  ],
  "discoveredConditions": []
}
```

### 10.3 安全约束

1. 模型只能引用输入中的企业字段；
2. 模型不回填政策 ID、企业事实值、条件原文或规则分组；
3. 规则表非空时 `discoveredConditions` 必须为空，原文遗漏只写入 `sourceConflicts`；
4. 规则表为空并回退发现条件时，模型必须说明条件来自哪段 `applicationRequirement`；
5. 模型输出不符合 JSON 契约时最多重试一次；
6. 单条政策失败不得中断其他政策判断。

## 11. 并发、缓存与批量

### 11.1 并发

1. 不同政策允许并发调用模型；
2. 并发数通过环境变量配置；
3. 必须设置全局并发上限，实时请求和批量请求共享限流；
4. 不允许对全部政策无限并发；
5. 遇到限流时采用退避和有限重试。

### 11.2 缓存

条件判断缓存键至少包含：

```text
企业画像内容哈希 + 政策条件内容哈希 + 模型版本 + 提示词版本
```

任一输入变化时缓存自动失效。

### 11.3 批量

1. 批量企业之间可以并发，但必须服从全局模型并发限制；
2. 单企业中的政策失败不影响其他政策；
3. 单企业失败不影响同批其他企业；
4. 批量输出保留企业输入顺序；
5. 记录每家企业的候选数、模型调用数、缓存命中数、失败数和耗时。

## 12. 返回结果

外部主要返回：

```text

```

业务页面不要求展示复杂门禁档位，核心是分数、排序和可解释理由。

内部审计必须保留：

```text

sourceConflicts
scoreSource

```

返回全部未被直接排除、至少存在一个有效匹配条件的政策，不先截断 TopN。调用方如需分页或 TopN，在最终排序后处理。
