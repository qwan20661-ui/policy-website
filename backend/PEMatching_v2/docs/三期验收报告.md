## 3. 双模式一致性（核心验收项）

20 家企业，每家分别跑 `agent` 与 `deterministic`：

| 指标 | 结果 | 判定 |
|---|---|---|
| **有效重合度**（同分互换视为等价） | **平均 100%　最低 100%**（阈值 90%） | ✓ |
| 原始重合度 | 平均 95.0%　最低 70.0%（差异全为同分互换） | — |
| 分数一致性 | **20/20 完全一致** | ✓ |
| 档位一致性 | **20/20 完全一致** | ✓ |
| 企业标签一致性 | **20/20 完全一致** | ✓ |
| 排序错序（不同分数间） | **0 处** | ✓ |
| 无更高分政策被漏 | **20/20** | ✓ |
| agent 降级率 | **0%**（要求 ≤10%） | ✓ |
| agent 耗时 P50 | 58.5 秒 | — |

脚本判定结果：**验收通过**。5 家企业的原始重合度在 70-80%，经 `tieSwapOnly` 判定全部属于同分互换（两侧独有政策的分数集合完全相同），非缺陷。

分数、档位、标签三项 100% 一致，证明**防越权设计有效**——分数确实只从确定性函数来，模型无法影响。

### 3.1 关于「重合度」指标的修正

原验收标准是「推荐集合重合度 ≥90%」。实测发现该指标在**同分政策多时天然达不到 100%**，需区分两种情况：

**情况一：真问题（已修复）**

第一轮比对最低 70%，查差异政策的分数后发现方向与预期相反——agent 独有的政策分数**更高**（98.33 vs 91.33），是 deterministic 漏了它们。

根因两层：表层是 deterministic 只用一组标签检索一次，agent 会换多组标签多次检索；深层是 `limit` 截断——检索对无行业值企业返回近百条同权重政策（C 标签为空导致命中维度数相同），排序退化为按 `fusionPolicyId` 稳定排序，30 条截断恰好切掉 ID 偏后的高分政策。

修复：`_search_candidates` 改为四组互补口径检索后合并去重（全标签组 / 领域组 / 阶段属地组 / 规则信号组），两模式共用同一函数；候选上限从 `max(top_n*3, 30)` 放宽到 `max(top_n*6, 120)` 覆盖全库。验证：6501（98.33 分）正确进入 deterministic 推荐 #2 位，候选池从 31 涨到 89 条。

**这个 bug 的价值**：双模式重合度不只在检验 Agent 是否越权，也在检验**基准侧本身是否正确**。只跑 agent 模式看结果好坏，这个检索覆盖不足的问题不会暴露——agent 恰好靠多次检索绕过了它。

**情况二：同分截断（非缺陷）**

修复后仍有 5 家原始重合度在 70-80%。查差异政策发现**分数完全相同**：神手科技的 9 条差异政策全是 93.33 分。原因是该企业 C 标签为空，领域匹配度被剔除分母，剩余项表现一致导致大批政策同分，`top_n` 截断时两模式取到不同的同分政策。

因此修正指标定义（**收紧而非放宽**）：

| 指标 | 定义 |
|---|---|
| `effectiveOverlap` | 两侧独有政策的分数集合相同时（纯同分互换）视为等价 |
| `scoreFloorRespected` | **新增硬指标**：任一模式是否漏掉对方推荐中更高分的政策 |

验收条件从「重合度 ≥90%」改为「有效重合度 ≥90% **且** 分数一致 **且** 标签一致 **且** 无更高分政策被漏 **且** 零错序」，比原标准多了后两条。

比对表格里加了 `纯同分互换`、`分数下限守住` 两列，复核时可自行判断差异性质。

## 5. 降级路径实测

把 `V2_API_URL` 指向不可达地址（`127.0.0.1:59999`）：

```
LLM 不可达时: 8.5s
  degraded=True reason=llm_unavailable turns=1
  推荐 5 条 (候选30 评分30)
  #1 6451  93.33 direct_push [template] 厦门市创新联合体备案申请
      领域大类精确匹配 C1；知识产权 56 件（来源 ipClass1+2），落 ≥10 件档；
      常年受理；信用记录因字段缺失未参与计分。
  事件: mode → llm_unavailable → fill_profile → fill_rules → fill_search
        → fill_scored → explain_failed
```

接口返回 200 与完整分数，推荐结果与 deterministic 模式完全一致（同为 6451/6470/6499，93.33 分）。事件序列清楚显示兜底过程。

## 6. 开发中修复的五个问题

这些只有跑真实 LLM 才会暴露，单测无法覆盖。

### 6.1 耗时 787 秒 → 57 秒

上下文单调膨胀：prompt 从 2064 涨到 19812 token，模型在长上下文上生成变慢直至触发 240 秒超时 × 3 次重试 = 726 秒。

修复：加上下文压缩，保留最近 2 轮完整往返，更早的工具结果压成一行摘要（保留政策 ID 与分数便于模型引用）。安全前提是**状态不在消息历史里**——profile、检索结果、评分结果都在 `SessionState`，模型不需要翻历史。token 轨迹改为回落（10586 → 8799）。

### 6.2 降级率 16.7% → 0%

两家企业跑满 12 轮没收尾。日志显示模型在评分后**逐条调 `get_policy_detail` 读全文写理由**，一家调了 6 次，每次占一轮。

修复：prompt 里说明轮次预算，同时在 handler 层加 `DETAIL_LIMIT=2` 硬限。**实测是硬限起的作用——光靠 prompt 约束不住模型的调用行为。**

### 6.3 模型只评部分候选

21 条候选只评了 7 条，93.33 分的政策没进推荐。修复：`_fill_missing` 给所有未评分候选补分，并按 deterministic 口径补齐候选池。

### 6.4 模型排序让高分政策掉出推荐位

原逻辑只要模型给的顺序是评分集合子集就采用，结果 88.33 分排在 93.33 之前。修复：只在模型覆盖了 `top_n` 全部高分政策时才采用其顺序，否则按分数排并记 `model_order_ignored` 事件。

### 6.5 `llm_client.py` 异常漏网

`TimeoutError` 是 `OSError` 子类而非 `urllib.error.URLError`，原来漏在异常处理外会直接崩出去。修复后归入 `LLMError` 并可重试。

## 7. 超出原计划补的两项

**模板理由兜底**。模型常只给部分政策写理由，其余位置原为空白。现用确定性模板填（串接得分最高两项的 `basis` + 时效性 + 字段缺失说明），`reasonSource` 标明 `model` 或 `template`。deterministic 模式因此也有了可读理由。

**四组互补检索**。见 3.1，原计划是单组检索。

## 8. 防越权设计验证

| 设计 | 验证方式 | 结果 |
|---|---|---|
| 状态不经模型手（profile 存 `SessionState`，工具 schema 不接受 profile 参数） | 单测断言 schema 无 profile 字段 | ✓ |
| 只能对 `search_policies` 返回过的政策评分 | 实测传造假 ID 被拒 | ✓ |
| 分数只从 `SessionState` 取，不信模型转述 | 单测：模型输出 `totalScore=999`，响应仍为真实分数 | ✓ |
| 模型只出 `reason`/`note`/`summary` 三个文案字段 | 双模式分数 20/20 一致 | ✓ |
| 重复调用检测（同工具同参数超 3 次） | 实测第 4 次被拦 | ✓ |
| `get_policy_detail` 次数上限 | 实测第 3 次被拦 | ✓ |
| 结果裁剪（详情去掉 `relatedPolicies`/`documents`） | 单测断言字段不存在 | ✓ |

## 9. 遗留问题

### 9.1 阈值 80 分失效（四期，优先级最高）

100 家 deterministic 批跑：`direct_push` 809 条 / `needs_supplement` 184 条 / `not_recommended` 7 条，Top1 分数 P50 达 98.89。**80 分线基本不起分流作用**。

校准前置条件：需业务方给推送量口径（每企业平均推 N 条，或直推档人工抽检准确率 ≥X%）。

### 9.2 同分政策过多（已排入四期 T5）

C 标签为空的企业（约七成）领域匹配度被剔除分母，导致大批政策同分——实测神手科技有 9 条政策同为 93.33、三友软件在 96.89 分档有 6 条以上。这使排序退化、`top_n` 截断带有随意性，双模式原始重合度因此掉到 70-80%。

**这比调阈值更影响推荐质量**——阈值只改档位标签，次级排序直接决定企业实际看到哪些政策。

已排入[四期 T5](四期_校准与调优开发流程.md#6-t5同分政策次级排序三期遗留)，方案是加次级排序键（申报期紧迫度 → 支持力度 E → 申报门槛 D → 标签置信度），只在总分相同时生效、不改总分。若仍不够，备选是对 `effectiveWeight` 低的企业按比例折减总分。

### 9.3 agent 模式耗时

P50 58.5 秒，最大 285 秒（并发下 LLM 网关排队）。若需对外提供实时查询，建议默认 `deterministic`（74ms），仅在需要模型撰写理由时用 `agent`。
