# 企业政策匹配 T3 实施记录

> 实施日期：2026-08-07  
> 规则基准：[企业政策匹配新规则.md](企业政策匹配新规则.md)  
> 开发计划：[企业政策匹配重构开发计划.md](企业政策匹配重构开发计划.md)

## 1. 实施结论

T3“取消旧政策打标依赖”已完成。新匹配链路的政策读取、直接字段来源和资质成长链均不依赖 A/B/C/D/E/F 标签。

1. 新增 `service/match_policy_source.py`，新链路只从 T2 条件包读取候选政策；
2. 新增 `config/qualification_growth_chain.json` 和 `service/qualification_growth.py`，资质成长链迁移为人工业务配置；
3. 服务默认启动不再执行旧后台政策打标；
4. 旧标签查询、旧 Agent、旧确定性推荐和手工打标命令均保留，用于灰度和回滚；
5. 旧标签索引缺失或为空不再改变新政策源的健康状态；
6. 本阶段未提前实现 T4 预过滤，也未切换最终推荐 API。

## 2. 新政策源边界

新链路唯一政策集合来自：

```text
config/policy_condition_snapshot.json
  -> service.policy_condition_package
  -> service.match_policy_source
```

`match_policy_source` 不导入 `service.tagging`、`service.policy_index`，也不读取 `config/policy_tags.json`。

直接字段映射如下：

| 匹配事实 | 条件包来源 | T3 是否判断 |
|---|---|---|
| 行业 | `policyInfo.industryField/industryFieldPath` | 否 |
| 属地 | `policyInfo.applicableScope/applicableScopePath` | 否 |
| 申报对象 | `conditions[].applicableTarget/applicableTargetPath` | 否 |
| 支持方式与金额 | `supportMethods[].supportType/amount/maxAmount` | 否 |
| 申报时效 | `conditions[].applicationStartTime/applicationEndTime/applicationInstruction` | 否 |
| 政策有效期 | `policyInfo.effectiveStartDate/effectiveEndDate` | 否，与申报期分开保留 |

这些字段在 T3 只归组和透传，不根据标题或关键词擅自推断适用性。行业、属地、主体和时效的确定性排除在 T4 实现，模糊语义交给后续单政策模型。

## 3. 资质成长图

成长链采用图结构而非旧的单线数组，只配置业务确认的直接后继：

| 当前状态 | 直接后继 |
|---|---|
| 无科技资质 | 创新型中小企业、科技型中小企业 |
| 创新型中小企业 | 专精特新中小企业 |
| 科技型中小企业 | 国家级高新技术企业 |
| 国家级高新技术企业 | 新型研发机构、未来产业骨干企业 |
| 专精特新中小企业 | 创新联合体、科技小巨人、规模以上工业企业 |
| 专精特新小巨人 | 制造业单项冠军、独角兽、瞪羚 |
| 上市后备培育企业 | 上市企业 |

配置校验保证：

1. 状态、政策目标和资质字段标识唯一；
2. 所有后继引用必须存在；
3. 必须且只能有一个“无资质”兜底状态；
4. 读取直接后继时不递归展开，避免跨级推荐；
5. 政策目标关键词只作为 T4 的候选识别配置，T3 不据此排除政策。

## 4. 启动与回滚

默认配置：

```text
PEMATCHING_V2_LEGACY_TAGGING_ON_STARTUP=false
```

默认启动流程为：

```text
同步审核政策
-> 生成条件包
-> 校验新匹配政策源和资质成长图
-> 启动服务
```

不会创建旧后台打标线程，也不会调用政策打标模型。仅在旧链路灰度或回滚确有需要时，显式设置 `PEMATCHING_V2_LEGACY_TAGGING_ON_STARTUP=true`，才会启动旧增量打标任务。

原变量 `PEMATCHING_V2_TAGGING_ON_STARTUP` 已从 `.env` 和 `.env.example` 删除，代码也不再读取该变量，避免历史 `true` 值意外触发新链路打标。

## 5. 健康状态

`GET /health` 新增 `matchPolicySource`，它是新链路政策可用性的判断依据。`policyIndex` 只标记为 `legacy_on_demand`，不读取或校验旧标签；旧标签统计仅在旧 `/api/v2/policy-tags` 接口收到请求时按需加载。

以下情况仍会影响新链路健康状态：

1. 审核政策同步不可用；
2. 条件包不存在、损坏或哈希不一致；
3. 新政策源存在重复政策；
4. 资质成长图格式错误或存在悬空后继引用。

## 6. 验证结果

专项与相关回归：

```text
test_t3_tag_independence.py + test_policy_condition_package.py：18 passed
test_api_server.py（排除一个既有旧标签断言）：41 passed, 1 deselected
```

专项覆盖：

1. 旧标签文件删除和写入空对象时，新政策源结果一致；
2. 新政策源模块没有旧打标与旧索引依赖；
3. 行业、属地、申报对象、支持金额和申报时效直接来自条件包；
4. 资质图只返回直接后继并保留业务分支；
5. 悬空后继引用被拒绝；
6. 默认主启动不调用旧打标任务；
7. 显式旧链路开关仍可进入原后台打标入口。

基于 T2 当前 76 条真实条件包快照：

| 指标 | 数量 |
|---|---:|
| 新政策源政策 | 76 |
| 含行业字段 | 74 |
| 含属地字段 | 75 |
| 含申报对象 | 74 |
| 含支持方式 | 76 |
| 含申报时效 | 74 |
| 资质状态 | 7 |
| 资质政策目标 | 13 |
| 含多个直接后继的分支状态 | 4 |

合并运行出现的一个旧断言为：当前 `PEMATCHING_V2_FORCE_APPLICABLE=true`，旧标签索引中不可申报政策数为 0，因此“包含不可申报后数量必须增加”的历史断言不成立。该问题属于已有旧链路测试数据与当前配置不一致，不由 T3 修改业务行为规避。

## 7. 后续边界

T4 将基于本次新政策源和资质图实现明确业务预过滤，包括主体、属地、行业、年份、资质直接后继和研发补助等规则。T4 必须输出排除原因和证据，并继续区分缺失值与明确不满足。

当前 `/api/v2/tagmatch/*` 仍是旧标签推荐接口。最终新旧引擎切换、单企业接口和批量接口迁移按 T7/T8 实施，不能把旧接口仍需标签误判为 T3 未解耦。
