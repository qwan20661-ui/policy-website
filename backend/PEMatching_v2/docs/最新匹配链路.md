# 最新匹配链路（PEMatching_v2 推荐管线）

> 本文件描述当前代码实现的完整匹配逻辑与已知问题，作为后续修改匹配规则的基准。
> 与此配套的通俗说明见 [企业政策匹配规则通俗说明.md](企业政策匹配规则通俗说明.md)。

---

## 0. 一句话

输入企业工商信息 → 给企业画像 → 先挑候选政策 → **对每条候选政策按申报条件评估（硬性先行，硬性不过一票否决）** → 硬性+软性条件一起算分得到 **0–100 申报要求符合度** → 按符合度排序、定档 → 业务规则再过滤 → 输出推荐清单。

推荐排序**不再用旧的 150 分制**；评分/排序/档位全部由资格门禁（`service/eligibility/`）确定性产出，大模型只负责抽取企业事实和写解释文案，改不了分数。

---

## 1. 整体流程（六步）

| 步骤 | 做什么 | 关键代码 |
|---|---|---|
| ① 给企业画像 | 工商数据 → 标准化标签/指标/资质/信用 | `service/profile.py build_profile` |
| ② 选候选 | 规则四通道(G0–G4) + 多组标签检索 → 候选清单 | `service/rules.py evaluate_rules`、`service/agent.py _search_candidates` |
| ③ 申报要求判定 | 对每条候选政策逐条核对申报条件：**先硬性** | `service/eligibility/gate_service.py`、`condition_evaluator.py` |
| ④ 算分 | 硬性(通过) + 软性条件平均 → **0–100 符合度** | `eligibility/score_aggregator.py` |
| ⑤ 排序定档 | 按符合度降序；直推/需补充/不推荐/不可评估 | `service/agent.py _assemble` |
| ⑥ 业务规则过滤 | 过期/已有资质/无专利/面向个人 → 排除 | `service/agent.py _assemble`（调 `scoring.py` 的 `is_ancient_policy`、`filter_policy_by_qualification`） |

入口：`run_tagmatch_batch.py`（CLI）与 `api_server.py`（`/api/v2/tagmatch/enterprise`、`/batch`）→ `service/agent.py run_match` → deterministic / agent 两模式收敛到同一个 `_assemble`。

## 2. 候选选择

- **规则四通道**：G0（信用前置拦截，命中即整家不推）→ G2（普惠）/ G3（升级链）/ G4（精推，需 enableStage2）。每条规则三态：命中 / 未命中 / **跳过**（依赖字段缺数据，不算命中也不算未命中）。
- **多组标签检索**：全标签 / 领域 / 阶段属地 / 规则信号四组互补口径，去重合并得到候选。
- 候选全量进入评估（静态模式下 77 条全评估，约 0.02s）。

---

## 3. 申报要求判定（核心：硬性先行）

每条政策有一份**申报条件档案**（`config/eligibility/policy_profiles.jsonl`），把政策原文申报条件拆成硬性组（`hardRuleGroups`）、软性组（`softRuleGroups`）、特殊通道组（`specialPassRuleGroups`）。

**判定顺序**：对每条候选政策——

1. 先逐条核对**硬性条件**：任一明确不满足 → 直接 `not_recommended`，**不再判软性**；
2. 硬性全部通过 → 进入算分。

**每条条件的三种结果**：满足 / 不满足 / 无法判断（缺数据判不了 → 记"缺失"，待补齐后重新判定）。

**企业事实从哪来**（每条件取一个事实值）：

- **静态映射**（确定性）：`field_mapping.json` 把条件对应字段直接映射到企业画像字段取值。
- **模型抽取**（LLM）：`use_llm_evidence` 开启时，让模型从企业原始数据里**选出一条证据路径**（exact/supporting/missing），服务端回读该路径的值。**模型不产分数**，只选证据 + 语义类条件给 pass/fail。

---

## 4. 算分（0–100 申报要求符合度）

只有**硬性全部通过**才进入算分；算分时**硬性与软性条件都参与**：

| 条件结果 | 单条得分 | 说明 |
|---|---|---|
| 硬性·通过 | 100 | 每条通过记 100，一并计入平均 |
| 软性·满足 | 100 | |
| 软性·不满足 | 30 起步 | "≥"类按企业实际值靠近门槛的程度加分 |
| 缺失（unknown） | 10 | 判不了按最低分，**不是 0**（0=确认达不到，10=不知道） |
| 硬性·不满足 | 0 且整条不推荐 | 一票否决，不参与排序 |

**符合度 = 各条可计分条件（硬性+软性）得分平均 ×100** = `conditionMatchScore`（0–100）。

特殊通道（破格条款）：某特殊组条件全部精确核实满足时，按 `max(平均分, 90)` 记、可直推。

---

## 5. 排序、定档与推荐列表

- **排序键**：`conditionMatchScore` 降序；同分用次级键（更接近截止日 / 支持力度大 / 门槛低 / 置信度高），再按政策 ID 稳定排序。
- **档位**：

| 档位 | 判定 | 是否进推荐 |
|---|---|---|
| `direct_push` | 符合度 ≥60 且条件全核实 | 进 |
| `needs_supplement` | 有条件"无法判断"（缺数据） | 进 |
| `not_recommended` | 硬性不满足 或 全核实但 <60 | **不进**，单列 `eligibilityExclusions` |
| `not_evaluable` | 无申报条件档案 / 评估出错 | **静默丢弃**（不出现在任何列表） |

- 推荐列表只含 `direct_push` + `needs_supplement`，取前 `top_n`。
- 之后做**业务规则过滤**：前年以前过期不推、已具备资质不推同级认定、无专利不推研发补助、面向个人不推企业——被过滤的进 `eligibilityExclusions`。
- 顶层还输出 `eligibilityResult.eligibilityEvaluations`（全部可评估政策，含 `not_recommended`，不含 `not_evaluable`）、`candidateCount`、`scoredCount`、`recommendableCount`。

---

## 6. 推荐项字段（推荐接口响应）

推荐项不再含旧 150 分字段（`totalScore/baseScore/bonusScore/scoreExplanation/bonusDetail/timeliness`），改为：

```
fusionPolicyId, rank, policyTitle, tags, applicationWindow,
conditionMatchScore, gateStatus, directPushAllowed, gateReasons,
conditionDetails, matchedRules, policyEvidence, reason, reasonSource
```

## 7. LLM 抽取与性能（重要）

- **开关**：`use_llm_evidence`。`None` = 跟随环境变量 `PEMATCHING_V2_ELIGIBILITY_LLM_ENABLED`（`.env` 当前为 `true` → **默认开启模型抽取**）。`--no-eligibility-llm` / `useLlmEvidence=false` 可强制关。
- **效果**：开启后 65 个 `llm_judge` 语义条件由模型抽取企业事实判定；不开则全部按"缺失"记 10 分。
- **代价（已实测）**：单条政策 LLM 抽取 **5–20s**（平均约 12s），41 条可评估政策串行 ≈ **单家 8 分钟**，批跑/API 不可用。
- **选定方案（候选窗口 + 并发，已实施）**：LLM 开启时，按候选的检索相关性（`matchScore`）取前 N 条（`top_n+10` 下限 24）做 LLM 精评，其余候选不进入精评窗口；窗口内逐政策 LLM 调用**并发**（`V2_ELIGIBILITY_LLM_WORKERS`，默认 6）。实测单家 deterministic 从约 8 分钟降到 **约 70 秒**（top_n=10 时窗口 24 条）。
- **static 模式（LLM 关）**：不走窗口、不走并发，一次性串行评估全部候选（约 0.02s）。

---

## 8. 两种工作模式

- **deterministic**：固定顺序，不调模型写文案；分数仍走资格评估（LLM 开则也调模型抽取）。
- **agent**：模型多轮 tool 编排（检索/读详情/评分工具），最终排序由 `_assemble` 按资格评估确定性重排，模型只写 reason/note/summary。
- 两模式收敛到同一评分 → 双模式重合度验收 ≥90%（实测 100%）。

## 9. 数据现状

- 政策库 **77 条**；77 条都有资格档案，但**仅 41 条可评估**（36 条档案为空 → `not_evaluable` 静默丢弃）。
- 41 条可评估中 40 条 `partial`（有未解析条件）；214 个条件项里 **206 个未映射标准字段**、**65 个依赖 `llm_judge`**。
- **只有 1 条政策（6451）有硬性条件**——硬性门禁目前基本空转。
- 不开 LLM 时推荐普遍 10 分、全落 `needs_supplement`；开 LLM 后分数提升取决于企业数据完整度。

## 10. 已知问题

| # | 问题 | 影响 | 状态/方向 |
|---|---|---|---|
| 1 | **LLM 逐政策抽取慢**（~12s/条），全量串行单家约 8 分钟 | 批跑/API 不可用 | **已实施**：候选窗口 + 并发，单家约 70 秒（见 §7）；仍偏慢，目标环境换更快端点可再降 |
| 2 | **36/77 政策档案为空** → 大量政策 `not_evaluable` 被静默丢弃 | 推荐覆盖少 | 需补齐政策申报条件档案（跑 sync 后人工核对） |
| 3 | **206/214 条件未映射标准字段** → 静态判定记"缺失"10 分 | 不开 LLM 时分数普遍很低 | 补 `field_mapping.json` 或开 LLM |
| 4 | **仅 1 条政策有硬性条件** | "硬性一票否决"几乎不生效 | 需给更多政策补充硬性申报条件 |
| 5 | **`.env` 默认 `PEMATCHING_V2_ELIGIBILITY_LLM_ENABLED=true` 且端点较慢** | 单测/批跑易误触发 LLM | 测试已用 conftest 强制关闭；批跑可 `--no-eligibility-llm` |
| 6 | **既有 5 个测试失败（与本次改造无关，数据漂移）**：政策 6548 已不在库、77 条全 applicable、行业映射未覆盖样本 | 测试套件非全绿 | 待清理数据/断言，不在本次范围 |
| 7 | **候选窗口用检索 `matchScore` 排序**，窗口外政策即使资格分高也不会被推荐 | 可能漏掉"标签不贴但条件够"的政策 | 权衡接受；如需覆盖可增大窗口 |

## 11. 主要配置与开关

| 配置 | 默认 | 说明 |
|---|---|---|
| `PEMATCHING_V2_ELIGIBILITY_LLM_ENABLED` | false（.env 当前 true） | LLM 抽取总开关；`use_llm_evidence=None` 时跟随 |
| `V2_ELIGIBILITY_LLM_WORKERS` | 6 | 窗口内并发逐政策 LLM 抽取的线程数 |
| `V2_AGENT_MAX_TURNS` | 12 | agent 模式最大轮次 |
| `--top-n` / `topN` | 20 | 推荐条数 |
| `--stage2` / `enableStage2` | off | 是否启用 G4 精推通道 |
