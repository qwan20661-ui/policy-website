# 五期开发流程：V1 资格门禁评分迁移

> 文档状态：需求已确认，待开发。
>
> 目标读者：后续分阶段接力开发、审查和验收的不同 AI 或开发人员。
>
> 核心决策：V2 继续负责政策召回、推荐评分和排序；V1 的逐申报条件评分迁移为一条新的、独立的资格门禁链路。资格门禁不参与 V2 推荐分计算，不改变 V2 候选集合、排序、推荐档位和推荐理由。

---

## 0. 已确认决策

以下决策已经由需求方确认，后续 AI 不得自行改写；如确需变化，必须先新增决策记录并重新确认。

| 编号 | 决策 | 约束 |
|---|---|---|
| D1 | 政策推荐继续使用 V2 链路 | V2 的标签、规则信号、候选召回、推荐分和排序保持原职责 |
| D2 | V1 评分作为推荐后的资格门禁 | 输入是企业数据和 V2 已推荐的政策 ID；输出是逐条件评分和资格状态 |
| D3 | 新计分规则必须走独立链路 | 不把 V1 算法写进 `service/scoring.py`，不让 V1 分数参与 V2 总分 |
| D4 | 完整保留 V1 软性、硬性和直通车能力 | 不能只迁移最终平均公式；必须迁移规则模型、求值、证据、单位、分支和聚合语义 |
| D5 | 没有可执行 V1 规则时保留 V2 推荐 | 资格状态为 `not_evaluable`，不得按 0 分或“不满足”解释，也不得允许直推 |
| D6 | V2 运行时与 V1 零代码、零数据目录耦合 | 不 import V1 模块，不运行时读取 V1 `config/`、`output/` 或日志；V1 仅作为迁移输入与对照基线 |
| D7 | V1 评分语义等价迁移 | 硬性失败归零、软性条件计分、缺失口径、直通车、证据层级、条件明细均需保留 |
| D8 | 缺失数据不是资格证明 | 缺失条件可以按 V1 口径计 10 分，但只要存在关键缺失、被拒绝证据或未知分支，就不得进入资格直推 |
| D9 | V2 当前仍在修改 | 本期开发先建立独立模块和独立接口，避免与正在变化的推荐链路交叉修改 |

### 0.1 一句话架构

```text
V2 推荐链路：企业 → 标签/规则信号 → 候选政策 → V2 推荐分 → 固定排序

V1 资格门禁链路：企业 + 已推荐政策ID → 资格规则 → 条件求值 → 条件分 → 资格状态
```

两条链路可以由调用方先后调用，但在代码、配置、分数和响应语义上必须保持独立。

## 1. 业务边界

### 1.1 两条链路分别回答什么问题

| 链路 | 回答的问题 | 可以做什么 | 不可以做什么 |
|---|---|---|---|
| V2 推荐链路 | 哪些政策与企业更相关、更值得关注 | 召回候选、计算推荐相关度、形成排序、给出推荐理由 | 不得把相关度分解释为满足申报资格 |
| V1 资格门禁链路 | 企业对该政策已结构化申报条件的匹配情况如何 | 逐条件比较、识别硬失败、计算软性分、列出缺失证据、给出资格状态 | 不得改写 V2 分数、排序、候选数量或推荐理由 |

### 1.2 本期目标

1. 将 V1 的规则画像结构转换为 V2 自有的资格规则快照。
2. 将 V1 的硬性、软性、直通车、单位换算、操作符、证据分层和聚合逻辑迁移为 V2 独立实现。
3. 建立新的资格门禁接口，不修改 V2 推荐接口的既有评分与排序语义。
4. 建立 V1/V2 资格评分对照测试，证明迁移前后条件结果和分数等价。
5. 对无规则、空规则、不完整规则、来源冲突和企业数据缺失给出可审计状态。
6. 为后续不同 AI 接力开发提供不可歧义的任务拆分、输入、输出和验收门槛。

### 1.3 非目标

| 非目标 | 说明 |
|---|---|
| 重构 V2 推荐算法 | V2 推荐仍在修改，本期不得借迁移资格评分改变推荐分 |
| 用资格分重新排序 V2 推荐 | 本期禁止；资格结果仅作为并列的门禁结果展示 |
| 把两个分数加权成综合分 | 本期禁止；没有经过真实样本校准前不得设计综合权重 |
| 自动认定企业具有法律意义上的申报资格 | 规则仅覆盖已结构化且可由当前企业数据核验的条件，不能替代政策原文和人工审核 |
| 在迁移时顺带修复 V1 全部历史问题 | 先完成可验证的语义等价迁移；已知缺陷单独登记、单独决策、单独回归 |
| 运行时调用 V1 服务或读取 V1 文件 | 迁移完成后 V2 必须能在没有 V1 目录和 V1 服务的环境中独立运行 |

## 2. 当前基线与迁移风险

### 2.1 V2 当前基线

V2 当前推荐评分位于 `service/scoring.py`，主要包含：

- 领域匹配度；
- 发展阶段匹配；
- 创新活跃度；
- 规模适配；
- 信用记录；
- 关键词、时效性和培育链路附加分；
- V2 推荐档位与确定性排序键。

这些字段属于推荐相关度，不属于逐申报条件资格评分。本期不得将 V1 条件分写入上述基础分、附加分、`totalScore`、`secondarySortKey` 或 `band`。

### 2.2 当前工作区原型的处理原则

当前工作区已经存在少量资格规则和保护逻辑原型，例如：

- `config/policy_eligibility_rules.json`；
- `service/policy_eligibility.py`；
- `service/policy_evidence.py`；
- `agent.py` 中资格过滤、推荐档位降级或排除逻辑；
- 对应的资格测试。

这些内容属于**待盘点原型**，不是本方案的既定实现。第一位开发 AI 必须先完成以下判断：

| 检查项 | 处理要求 |
|---|---|
| 是否修改 V2 原始 `band` | 如有，迁移为独立资格状态，不得继续覆盖 V2 档位 |
| 是否从 `recommendations` 删除政策 | 如有，取消资格链路对 V2 推荐集合和 TopN 的修改 |
| 是否让资格状态参与 V2 排序 | 如有，移除该耦合 |
| 是否只有 `hardConditions` 简化结构 | 不得直接扩写为最终结构；需要升级为完整 V1 规则画像 schema |
| 是否缺少软性组和直通车组 | 必须补齐迁移设计和测试 |
| 是否把粗标签或规则关键词当资格证据 | 禁止；资格证据必须对应具体政策条件和企业事实 |

不得直接删除或覆盖用户当前未提交修改。必须先记录 `git status`、`git diff` 和未跟踪文件，再以最小补丁进行兼容改造。

### 2.3 V1 当前更新快照的实际覆盖情况

当前 `backend/PEMatching/config/主政策申报条件.json` 已于 `2026-08-05T11:04:53+08:00` 从本地 structure API 更新。文件顶层 `summary.total=84`，按每条政策唯一的 `ruleTableJson` 统计如下：

| 指标 | 当前本地结果 |
|---|---:|
| 政策/规则画像总数 | 84 |
| 含软性组 | 40 |
| 空规则画像 | 44 |
| 含硬性组 | 0 |
| 含直通车组 | 0 |
| 条件组/条件项 | 212 / 212 |
| 当前操作符 | `gt`、`gte`、`lte`、`llm_judge` |
| 当前 `ruleKind` | `direct`、`reference` |

注意：同一规则画像还会出现在 `rule_table_json` 和 `raw_detail.ruleTableJson` 中，统计时必须按顶层政策 ID 和规范字段 `ruleTableJson` 去重，不能递归计成三份。

该快照可以作为当前迁移输入，但它只实际覆盖软性规则，不能单独证明硬性和直通车迁移完成。即使当前 84 条政策没有这两类实例，资格引擎仍必须完整实现并使用 V1 fixture/特征测试验收硬性和直通车能力，以支持后续规则更新。

V1 当前真实规则源优先级应按以下顺序核验：

1. 权威 structure policy detail API 返回的 `ruleTableJson`；
2. 经审核并保存的规则表目录结果；
3. 与同一来源更新时间对应且已验证 `summary.total` 的当前导出快照；
4. 未记录来源时间或总数的历史缓存只作为离线兜底和差异对照。

如果权威 API 在开发环境不可用，开发 AI 必须明确标记“离线快照验证”，不得声称完成全量迁移验收。

### 3.3 两种调用方式

本期以独立接口为主，避免 V2 推荐接口在开发期间发生契约漂移。

#### 方式 A：调用方串行调用，作为正式方案

```text
1. POST /api/v2/tagmatch/enterprise
2. 从响应中取得按 V2 排好序的 fusionPolicyId 列表
3. POST /api/v2/eligibility/evaluate
4. 调用方按 fusionPolicyId 合并展示，V2 排名不变
```

#### 方式 B：未来可选的组合编排接口

组合接口只能顺序编排两条独立服务，必须原样保留：

- `recommendationResult`：V2 原始结果；
- `eligibilityResult`：资格门禁结果；
- 两套分数、状态和原因不得合并为一个字段。

方式 B 不属于本期必做项，除非接口调用方明确要求。

## 4. V2 资格规则快照 schema

### 4.1 顶层 manifest

建议使用 `manifest.json` 记录一次完整同步，而不是让规则文件成为无来源的大 JSON。

```json
{
  "schemaVersion": "pematching-v2-eligibility-manifest-v1",
  "generatedAt": "2026-08-05T00:00:00+08:00",
  "sourceType": "structure_api_rule_table_json",
  "sourceBaseUrlHash": "仅保存非敏感摘要",
  "sourcePaginationTotal": 0,
  "fetchedPolicyCount": 0,
  "profileCount": 0,
  "executableProfileCount": 0,
  "emptyProfileCount": 0,
  "invalidProfileCount": 0,
  "sourceReviewStatus": "all",
  "sourceStructureReviewStatus": "all",
  "contentSha256": "",
  "generatorVersion": "v1"
}
```

### 4.2 单政策规则画像

建议将单政策画像保存为 JSONL，便于流式写入、局部重跑、断点续传和逐政策差异审计。

```json
{
  "schemaVersion": "pematching-v2-eligibility-profile-v1",
  "fusionPolicyId": "6548",
  "policyTitle": "厦门市科技型中小企业评价",
  "sourcePolicyUpdatedAt": "",
  "sourceRuleTableVersion": "1.2",
  "sourceRuleTableHash": "",
  "migrationStatus": "migrated",
  "coverage": "complete",
  "hardRuleGroups": [],
  "softRuleGroups": [],
  "specialPassRuleGroups": [],
  "definitionNotes": [],
  "applicationChecklistGroups": [],
  "migrationWarnings": []
}
```

### 4.3 必须原样保留的组级字段

| 字段 | 用途 | 是否参与评分 |
|---|---|---|
| `conditionNo` | 政策原条件编号 | 审计字段 |
| `rawText` | 条件组原文 | 审计和解释 |
| `conditionContext` | 条件上下文 | 分支判断和语义约束 |
| `conditionBranchId` | 稳定分支标识 | 防止不同 OR/ANY 分支串线 |
| `conditionBranchText` | 分支原文 | 解释和人工复核 |
| `conditionOperator` | `AND`、`OR`、`ANY` 等组操作符 | 是 |
| `conditionFieldItems` | 可执行条件项 | 是 |
| `unresolvedFragments` | 未能结构化的政策片段 | 阻断完整资格结论 |
| `evaluationRole` | `eligibility_signal`、`quantitative_signal` 等 | 决定组语义，不直接作为固定权重 |
| `specialPassEffect` | 直通车命中后的效果 | 仅直通车组使用 |

### 4.4 必须原样保留的条件项字段

| 字段 | 用途 |
|---|---|
| `itemId` | 展示标识；不能假设政策内一定唯一 |
| `semanticItemKey` | 运行时唯一键，建议由政策 ID、组类型、组序号和项序号组成 |
| `sourceFragmentId` | 原文片段来源 |
| `itemName` | 条件名称 |
| `policyFragment` | 对应政策原文 |
| `itemStatus` | `rule`、`supporting`、`reference`、`unresolved` 等 |
| `enterpriseFields` | 候选企业字段列表 |
| `sourceStandardField` | 原标准字段元数据 |
| `matchRule.ruleId` | 规则标识 |
| `matchRule.ruleKind` | 规则生成侧元数据，仅用于审计和证据分类，不作为固定 70/30 权重 |
| `matchRule.fieldType` | number、boolean、text、date、list 等 |
| `matchRule.operator` | `gte`、`lte`、`gt`、`lt`、`eq`、`has_value`、`llm_judge` 等 |
| `matchRule.targetValue` | 政策门槛值 |
| `matchRule.unit` | 政策门槛单位 |
| `matchRule.description` | 规则说明 |

### 4.5 非评分容器

以下内容必须迁移和展示，但不得计入资格分：

| 容器 | 用途 |
|---|---|
| `definitionNotes` | 指标定义、统计口径、人员工作时间等说明 |
| `applicationChecklistGroups` | 材料、报告、承诺、申报系统、审计文件和流程要求 |

不得把材料齐备度、申报时间或流程说明误写成企业资格得分。

## 5. V1 评分语义兼容契约

### 5.1 常量

| 常量 | 值 | 含义 |
|---|---:|---|
| `DEFAULT_MISSING_SCORE` | `0.1` | 缺失或被拒绝事实的召回型条件分，即百分制 10 分 |
| `PRESENT_DATA_BASE_SCORE` | `0.3` | 有企业事实但软性条件未达到目标时的基础分，即百分制 30 分 |
| `RECOMMENDATION_SCORE_THRESHOLD` | `0.6` | 条件匹配分推荐阈值，即百分制 60 分 |
| `SPECIAL_PASS_MIN_SCORE` | `0.9` | 有真实证据命中直通车时的最低分，即百分制 90 分 |

常量必须集中定义，禁止散落在多个模块中。迁移阶段不得修改数值。

### 5.2 证据层级

| 层级 | 计分桶 | 含义 | 资格处理 |
|---|---|---|---|
| `A1_exact` | `verified` | 企业原始字段可与政策条件直接比较 | 可以支撑资格结论 |
| `A2_derived` | `verified` | 由完整字段和本地确定性公式推导 | 可以支撑资格结论，但必须返回推导公式 |
| `B_supporting` | `supporting` | 代理、引用或辅助证据 | 可以参与 V1 条件分，不足以单独证明严格资格 |
| `U_missing` | `unverified` | 没有可核验企业事实 | 条件可按 10 分计分，但门禁不得直推 |
| `R_rejected` | `unverified` | 证据路径或语义类别校验失败 | 清空无效证据，按缺失或不可计算处理，门禁不得直推 |
| `N_not_evaluable` | `excluded` | 规则目标、单位或结构无法可靠计算 | 不进分母，门禁不得直推 |
| `S_skipped` | `excluded` | 当前企业不适用该条件分支 | 不进分母，不等同失败 |

### 5.3 条件求值

#### 数值条件

1. 先确定企业值、企业单位、目标值和目标单位。
2. 在比较前完成单位标准化，禁止只对显示值换算。
3. 执行本地确定性比较。
4. 保存原值、标准化值、换算公式、操作符和比较结果。

| 条件类型 | 满足 | 有事实但不满足 | 缺失 |
|---|---:|---:|---:|
| 硬性数值 | 100 | 0，并形成硬失败 | 10，但进入待补充，不得视为通过 |
| 软性下限 | 100 或按 V1 成长性公式计算 | `min(1, 0.3 + current/target)` | 10 |
| 软性上限/等值 | 100 | 30 | 10 |

需要以 V1 特征测试锁定每种操作符的精确边界、零值、负值、空值和除零行为。

#### 布尔和枚举条件

| 类型 | 满足 | 明确不满足 | 缺失 |
|---|---:|---:|---:|
| 硬性 | 100 | 0，并形成硬失败 | 10，待补充 |
| 软性 | 100 | 30 | 10，待补充 |

#### 定性条件

- 模型只能输出事实状态、证据路径、证据文本、条件分支和标准化候选值。
- 模型不得给条件打分，不得做单位换算，不得决定硬失败，不得计算总分。
- 服务端必须回读证据路径的真实企业值。
- 语义不兼容时将证据降级为 `R_rejected`，不得把相邻概念当作等价证据。

示例：

- “研发人员占比”不能证明“学历员工占比”；
- “科技型中小企业资质”不能证明“获奖、实验室、产学研联合体或项目参与”；
- 企业注册地址不能直接证明项目实施地址；
- 自然人经历不能证明企业资质。

### 5.4 组求值

组求值必须独立于条件项求值，禁止先扁平化后平均。

| 组类型 | 基本语义 |
|---|---|
| `hardRuleGroups` | 明确硬失败可使最终资格分归零；待确认不能视为通过 |
| `softRuleGroups` | 在硬性门禁允许继续时计算成长性或适配性条件分 |
| `specialPassRuleGroups` | 真实证据命中后触发直通车语义，最低分可提升至 90，但缺失或代理证据不得触发 |

`conditionOperator` 的精确行为必须先通过 V1 特征测试确认。若 V1 当前对 `AND`、`OR`、`ANY` 或分支组合存在历史歧义，不得由迁移 AI 静默重写；应将实际行为冻结为兼容测试，并在独立问题清单中提出改进方案。

### 5.5 聚合公式

适用且可评分条件等权平均：

```text
condition_match_score = sum(condition_score × condition_weight)
                        / sum(condition_weight)
```

当前兼容契约中普通条件权重为 1。证据桶用于审计展示，不再使用静态 `ruleKind` 70%/30% 聚合。

```text
hard_failed = 存在明确硬性失败

final_score = 0                              if hard_failed
final_score = max(condition_match_score, 90) if special_pass_hit_with_verified_evidence
final_score = condition_match_score          otherwise
```

百分制值只在输出层转换；内部建议继续使用 `0.0..1.0`，避免重复除以 100。

### 5.6 资格门禁状态

资格门禁状态和 V2 推荐档位是两套不同枚举。

| `gateStatus` | 触发条件 | `directPushAllowed` | 对 V2 推荐的影响 |
|---|---|---:|---|
| `direct_push` | 有可执行规则、无硬失败、无关键待确认、证据满足要求且分数达到 60；或有真实证据命中直通车 | true | 不改变 V2 排名和档位，仅提供资格结论 |
| `needs_supplement` | 存在缺失事实、被拒绝证据、未知分支、不可计算关键条件或不完整覆盖，但没有明确硬失败 | false | 保留 V2 推荐原样，提示补充数据 |
| `not_recommended` | 存在明确硬性失败，或全部条件已有证据但最终分低于 60 | false | 保留 V2 推荐原样，资格侧显示不建议申报 |
| `not_evaluable` | 无规则画像、空规则画像、规则 schema 非法、来源冲突、无任何可评分条件 | false | 保留 V2 推荐原样，说明无法评估 |

状态优先级：

```text
规则不可用/来源冲突
    > 明确硬性失败
    > 关键待确认或证据不足
    > 分数阈值
    > 直通车
```

说明：直通车不能覆盖来源冲突、规则不可用或明确硬失败。

## 6. 企业字段适配

### 6.1 适配层职责

V1 规则中的企业字段命名与 V2 `profile.py` 输出不完全一致。必须建立显式字段映射，禁止在求值器中散落字段别名。

`enterprise_adapter.py` 负责：

1. 接收 V2 标准企业画像或原始企业请求；
2. 生成资格评分专用的只读事实快照；
3. 将 V1 中文标准字段映射到 V2 JSONPath；
4. 保留原始值、标准化值、单位、年份、来源路径和可用状态；
5. 区分 `null`、空串、空列表、真实数值 0 和布尔 false；
6. 不填充均值，不猜测，不将标签结果反推成企业事实。

### 6.2 字段映射格式

```json
{
  "schemaVersion": "pematching-v2-eligibility-field-map-v1",
  "mappings": [
    {
      "v1Field": "营收规模-年营业收入",
      "v2Paths": ["$.metrics.revenueWan"],
      "semanticCategory": "financial.revenue",
      "canonicalUnit": "万元",
      "yearPolicy": "latest_available",
      "mappingStatus": "verified"
    }
  ]
}
```

### 6.3 映射安全门槛

| 情况 | 处理 |
|---|---|
| 精确字段可用 | `A1_exact` |
| 由完整字段确定性推导 | `A2_derived`，返回公式和参与字段 |
| 只有相邻字段或代理证据 | `B_supporting`，不得冒充精确事实 |
| 字段不存在 | `U_missing` |
| 路径存在但语义类别不兼容 | `R_rejected` |
| 年份或单位无法确定 | `N_not_evaluable` 或待补充，不能直接比较 |

## 7. 接口契约

### 7.1 新接口

```http
POST /api/v2/eligibility/evaluate
Content-Type: application/json
```

建议请求：

```json
{
  "enterprise": {},
  "fusionPolicyIds": ["6548", "6590"],
  "includeConditionDetails": true,

}
```

规则：

- `fusionPolicyIds` 的顺序必须原样保留；该顺序通常来自 V2 推荐结果。
- 接口不得自行重新召回政策或重新计算 V2 推荐分。
- 单条政策失败不得污染其他政策结果；每条均返回状态。

### 7.3 对外响应与完整归档

建议沿用“对外精简、服务端完整留痕”的原则：

| 位置 | 保存内容 |
|---|---|
| API 响应 | 门禁状态、条件分、核心计数、原因、可选条件明细、`runId` |
| 服务端归档 | 企业事实快照、规则快照哈希、每项求值、证据路径、单位换算、模型事实、拒绝原因、完整组结果 |

完整归档应原子写入，文件名使用安全的 `runId`。不得在日志或响应中泄露密钥、内部服务地址和无关企业敏感字段。

### 7.4 不得修改的 V2 字段

资格链路不得覆盖以下推荐字段：

- `totalScore`；
- `baseScore`；
- `bonusScore`；
- `band`；
- `rank`；
- `reason`；
- `reasonSource`；
- `matchedRules`；
- `candidateCount`；
- `scoredCount`；
- V2 的 `recommendations` 数量和顺序。

## 8. 分阶段开发流程

不同 AI 必须按顺序接力。除非任务明确允许，不得跨阶段提前实现后续模块。

### 阶段 T0：工作区与现有原型盘点

**目标**：保护当前未提交修改，确认哪些资格代码属于现有原型。

**输入**：当前工作区、本文档、`docs/问题.md`、V2 原有开发文档。

**执行**：

1. 记录 staged、unstaged、untracked 文件。
2. 阅读资格原型及对应测试，绘制实际调用路径。
3. 标记哪些代码正在改变 V2 分数、档位、排序或推荐集合。
4. 输出原型处理表：保留、迁移、替换、隔离、待确认。
5. 不修改 V1 文件，不清理用户文件，不提交 Git。

**交付**：`docs/五期_T0_现状盘点.md`。

**完成门槛**：能够回答“当前资格原型是否影响 V2 推荐行为”，并提供文件与测试证据。

### 阶段 T1：权威规则源同步与覆盖审计

**目标**：获得可追溯的 V1 规则迁移输入，证明硬性、软性和直通车实际覆盖情况。

**执行**：

1. 通过权威 API 拉取最新政策目录和详情。
2. 明确使用全部审核状态：`--review-status all --structure-review-status all`。
3. 检查分页字段和 `pagination.total`，禁止只取第一页或默认 reviewed-only 范围。
4. 每条政策立即落盘，记录来源更新时间和 SHA-256，支持安全断点续传。
5. 审计 `hardRuleGroups`、`softRuleGroups`、`specialPassRuleGroups`、空画像、非法画像和未解析片段。
6. 将 API 结果与本地 `主政策申报条件.json` 做差异报告。

**建议命令**：

```powershell
cd E:\workspace\kejiju-frontend
python backend\PEMatching_v2\script\sync_v1_eligibility_profiles.py --review-status all --structure-review-status all --resume
python backend\PEMatching_v2\script\audit_eligibility_profiles.py
```

**输出**：

- `config/eligibility/manifest.json`；
- `config/eligibility/source_profiles.jsonl`；
- `output/eligibility_audit/<runId>/summary.json`；
- `output/eligibility_audit/<runId>/invalid_profiles.jsonl`；
- `output/eligibility_audit/<runId>/coverage.csv`。

**阻断条件**：

- API 总数无法验证；
- policy ID 重复或缺失；
- 拉取失败未被单独记录；
- 硬/软/直通车统计与输入内容不一致；
- 只使用本地旧快照却声称权威全量完成。

### 阶段 T2：V2 资格规则 schema 与迁移器

**目标**：将 V1 规则画像转换为 V2 自有、版本化、可校验的规则快照。

**执行**：

1. 定义 schema 和 Python 数据模型。
2. 保留所有评分容器、非评分容器、原文、分支、操作符、单位和来源元数据。
3. 为每项生成稳定 `semanticItemKey`，不得只依赖可能重复的 `itemId`。
4. 对未知操作符、未知单位、非法 `ruleKind`、空目标值和重复规则 ID 给出明确错误。
5. 迁移结果写入临时文件，完整成功后再原子替换正式快照。
6. 迁移脚本幂等；相同输入产生相同内容哈希。

**交付文件**：

- `service/eligibility/models.py`；
- `service/eligibility/profile_loader.py`；
- `script/sync_v1_eligibility_profiles.py`；
- `config/eligibility/policy_profiles.jsonl`；
- schema 和迁移测试。

**完成门槛**：

- 输入、输出政策数逐项对账；
- 每个被跳过画像都有原因；
- 相同输入连续迁移两次，内容哈希一致；
- V2 在删除或重命名 V1 目录的测试环境中仍能加载资格规则。

### 阶段 T3：企业字段适配与证据安全

**目标**：把 V2 企业数据转换为 V1 条件求值所需的可审计事实，但不制造等价关系。

**执行**：

1. 建立中文 V1 字段到 V2 JSONPath 的映射文件。
2. 为每个映射标记语义类别、单位、年份规则和映射状态。
3. 实现路径回读和真实 0/false/null 区分。
4. 实现确定性派生字段并返回公式。
5. 实现语义类别兼容校验和拒绝原因。
6. 对列表字段保留元素路径，禁止数组索引错配。

**交付文件**：

- `config/eligibility/field_mapping.json`；
- `service/eligibility/enterprise_adapter.py`；
- `service/eligibility/evidence.py`；
- `tests/test_eligibility_enterprise_adapter.py`。

**完成门槛**：所有映射都有正例、缺失例、真实 0/false、语义错配和年份/单位异常测试。

### 阶段 T4：条件求值器与单位换算

**目标**：实现与 V1 等价的单条件确定性求值。

**执行**：

1. 迁移并重构数值、布尔、枚举、存在性和定性规则求值。
2. 实现单位标准化和比较前换算。
3. 保留 V1 的 10/30/100 和硬失败 0 分语义。
4. 为每个操作符建立边界测试。
5. 记录 `evalStatus`、`passSource`、证据层级、得分桶和审计说明。
6. LLM 仅在 `llm_judge` 且本地事实不足时作为事实抽取器；无模型时返回可重试或待确认，不得伪造 0 分。

**建议先跑的 V1 基线测试**：

```powershell
cd E:\workspace\kejiju-frontend
python -m pytest backend\PEMatching\test_rule_engine_growth_scoring.py backend\PEMatching\test_semantic_rule_scoring.py backend\PEMatching\test_semantic_match_service.py -q
```

**完成门槛**：固定输入下，V2 条件求值结果与 V1 的状态、标准化值和分数一致；允许的字段命名差异必须在映射表中登记。

### 阶段 T5：组求值、聚合与资格门禁

**目标**：完整实现硬性组、软性组、直通车组及最终门禁状态。

**执行**：

1. 在独立模块中实现组级操作符和分支行为。
2. 硬性明确失败使最终资格分归零。
3. 软性条件在允许执行时参与等权平均。
4. 直通车只允许真实证据触发，最低分提升到 90。
5. 计算证据覆盖率、默认缺失数、待确认数、失败数和可评分条件数。
6. 按第 5.6 节状态优先级输出门禁结果。
7. 无规则、空规则和零可评分条件统一返回 `not_evaluable`，但原因码必须不同。

**建议原因码**：

| 原因码 | 含义 |
|---|---|
| `RULE_PROFILE_NOT_FOUND` | 没有该政策规则画像 |
| `RULE_PROFILE_EMPTY` | 有画像但三个评分容器为空 |
| `RULE_PROFILE_INVALID` | schema 或规则非法 |
| `RULE_SOURCE_CONFLICT` | 政策来源存在冲突 |
| `NO_SCORABLE_CONDITION` | 没有可评分条件 |
| `HARD_CONDITION_FAILED` | 明确硬性失败 |
| `MISSING_ENTERPRISE_FACT` | 企业事实缺失 |
| `EVIDENCE_REJECTED` | 证据语义或路径被拒绝 |
| `CONDITION_NOT_EVALUABLE` | 条件无法可靠计算 |
| `UNKNOWN_BRANCH` | 条件分支无法确认 |
| `SCORE_BELOW_THRESHOLD` | 条件均已确认但分数低于 60 |
| `SPECIAL_PASS_VERIFIED` | 真实证据命中直通车 |

**完成门槛**：状态优先级、分数、计数和原因码均有独立测试；任何缺失或被拒绝证据都不能得到 `direct_push`。

### 阶段 T6：独立 API 与归档

**目标**：提供不影响 V2 推荐接口的资格评分 API。

**执行**：

1. 新增 `/api/v2/eligibility/evaluate`。
2. 保持请求中的政策 ID 顺序。
3. 每条政策独立返回结果；单条失败不影响其他政策。
4. 完整明细原子归档，API 返回安全 `runId`。
5. 增加请求数量、请求体大小、超时和模型并发保护。
6. 接口文档单独描述资格分，不把它写成 V2 推荐总分。

**回归要求**：调用新接口前后，相同企业调用 V2 推荐接口所得政策集合、排名、`totalScore` 和 `band` 必须逐字段一致。

### 阶段 T7：V1/V2 等价对照与真实样本验证

**目标**：证明“迁移”而不是“重新设计”。

**测试层级**：

| 层级 | 数据 | 目标 |
|---|---|---|
| L1 单条件特征测试 | 人工最小 fixture | 锁定每种字段类型、操作符、单位和缺失行为 |
| L2 规则组测试 | 硬/软/直通车 fixture | 锁定组操作符、硬失败、待确认和直通车 |
| L3 单政策对照 | 固定企业 + 固定规则画像 | V1/V2 每个条件状态、分数和最终分一致 |
| L4 多政策批量对照 | 固定企业样本 | 统计差异率、差异类型和不可比较原因 |
| L5 V2 推荐不变回归 | 同一 V2 输入 | 推荐集合、排序、推荐分和档位 100% 不变 |
| L6 API/归档测试 | HTTP 请求 | 响应、runId、归档和失败处理一致 |

**允许差异**：

- 字段名称翻译；
- 增加 schema 版本、原因码和审计字段；
- 将 V1 中“缺失 10 分但看起来可推荐”的结果收紧为资格侧 `needs_supplement`，但条件分仍保持 V1 数值。

**不允许差异**：

- 同一已核验证据被换成不同企业字段；
- 单位未换算或换算顺序改变；
- 硬失败不再归零；
- 缺失数据变成 0、100 或严格符合；
- 软性规则被当硬性淘汰；
- `ruleKind` 被重新用作固定 70/30 权重；
- 资格结果改变 V2 推荐排序。

### 阶段 T8：灰度、监控与切换

**目标**：先旁路验证，再允许调用方展示资格结果。

**建议开关**：

| 环境变量 | 默认值 | 作用 |
|---|---|---|
| `PEMATCHING_V2_ELIGIBILITY_ENABLED` | `false` | 是否启用资格接口 |
| `PEMATCHING_V2_ELIGIBILITY_LLM_ENABLED` | `false` | 是否允许定性事实抽取 |
| `PEMATCHING_V2_ELIGIBILITY_ARCHIVE_ENABLED` | `true` | 是否保存完整运行归档 |
| `PEMATCHING_V2_ELIGIBILITY_MAX_POLICIES` | `20` | 单次最大政策数 |
| `PEMATCHING_V2_ELIGIBILITY_RULE_MANIFEST` | 默认正式 manifest | 指定规则快照版本 |

**灰度顺序**：

1. 本地 fixture；
2. 单企业、单政策；
3. 单企业、V2 Top3；
4. 固定企业样本、V2 Top10；

6. 人工抽检通过后由调用方展示；
7. 不允许资格链路失败导致 V2 推荐接口失败。

| AI-2 字段证据 | T3 | 字段映射、适配器、证据校验及测试 | 不改 V2 profile 语义，除非有独立兼容适配 | 字段覆盖率、拒绝样例、测试 |
| AI-3 条件引擎 | T4 | 条件求值和单位换算 | 不改组聚合、API、V2 scoring | 操作符矩阵、V1 对照结果 |
| AI-4 门禁聚合 | T5 | 组求值、聚合、门禁服务及测试 | 不改 V2 推荐排序 | 状态矩阵、原因码、测试 |
| AI-5 API 集成 | T6 | 独立 endpoint、归档、接口测试和接口文档 | 不改 V2 推荐响应契约 | curl、响应样例、失败样例 |
| AI-6 验收审计 | T7 | 对照脚本、验收报告；只修复已确认缺陷 | 不重写算法口径 | 差异报告、回归结果、DoD 判断 |
| AI-7 灰度交付 | T8 | 配置开关、监控和部署文档 | 不默认开启生产 | 灰度报告、回滚说明 |

### 9.2 每位 AI 开始前必须做

1. 阅读本文档全部内容。
2. 阅读上一阶段交接报告和测试输出。
3. 执行 `git status --short`，区分用户修改和前序阶段修改。
4. 只认已提交或交接报告明确列出的上游契约，不猜测未完成内容。
5. 先跑与本阶段相关的最小测试，记录基线。
6. 如发现上游契约不成立，停止扩展实现，先输出阻断证据。

### 9.3 每位 AI 结束时必须交接

建议新增 `docs/五期交接/T<n>_交接.md`，内容必须包含：

| 项目 | 必填内容 |
|---|---|
| 完成范围 | 实际完成的任务，不写计划中的未完成项 |
| 修改文件 | 每个文件及职责 |
| 契约变化 | schema、接口、状态、原因码是否变化 |
| 测试命令 | 可复制的 PowerShell 命令 |
| 测试结果 | 通过数、失败数、未执行原因 |
| 产物位置 | manifest、快照、报告和归档路径 |
| 未决问题 | 明确阻断与非阻断项 |
| 下一 AI 输入 | 下一阶段需要读取的文件和固定版本哈希 |
| 回滚方式 | 删除或关闭本阶段能力的方法 |

### 9.4 防止多 AI 互相覆盖

- 同一阶段只指定一个主 AI 修改同一模块。
- 数据迁移、条件引擎、门禁聚合和 API 分属不同目录或文件。
- 不允许多个 AI 同时编辑 `service/agent.py`、`service/scoring.py` 或 `api_server.py`。
- 任何跨阶段公共契约先修改 schema/接口文档和契约测试，再修改实现。
- 不提交生成的大型输出文件，正式规则快照是否入库由仓库策略和 `.gitignore` 决定。
- 不执行 `git reset --hard`、覆盖式 checkout 或删除用户未跟踪文件。

## 10. 测试矩阵

### 10.1 条件级必测场景

| 场景 | 预期 |
|---|---|
| 企业值等于下限 | `gte` 通过，`gt` 不通过 |
| 企业值等于上限 | `lte` 通过，`lt` 不通过 |
| 金额单位为元/万元/亿元 | 比较前统一换算，结果一致 |
| 比例为 0、百分数和小数 | 不混用 0.3 与 30% |
| 企业值真实为 0 | 视为有效证据，不当作缺失 |
| 布尔 false | 视为有效反证，不当作缺失 |
| 字段 null/空串/空列表 | 按字段类型进入缺失或空集合语义 |
| 目标值非法 | `not_evaluable`，不进入分母 |
| 单位未知 | `not_evaluable` 或待补充，不直接比较 |
| 语义相邻但不等价 | `R_rejected`，清除伪证据 |
| 重复 itemId | 使用 `semanticItemKey`，不得覆盖事实 |
| 不同年份数据 | 按年份策略选择并返回依据 |

### 10.2 组级必测场景

| 场景 | 预期 |
|---|---|
| 硬性组全部满足 | `hardPass=true` |
| 硬性组明确失败 | 最终资格分 0，`not_recommended` |
| 硬性组事实缺失 | 保留条件 10 分口径，门禁 `needs_supplement` |
| 软性条件未达到下限 | 按 V1 成长性公式计分，不形成硬失败 |
| 软性条件全部缺失 | 10 分进入兼容分，但不得直推 |
| 直通车有精确证据 | `specialPassHit=true`，最低 90 分 |
| 直通车仅代理或缺失证据 | 不得触发 |
| 无规则画像 | `not_evaluable`，分数为 null |
| 空规则画像 | `not_evaluable`，原因 `RULE_PROFILE_EMPTY` |
| 无可评分条件但有材料清单 | `not_evaluable`，材料不参与评分 |

### 10.3 V2 不受影响回归

对固定企业请求，在启用资格链路前后分别保存 V2 推荐响应，至少比较：

```text
fusionPolicyId
rank
totalScore
baseScore
bonusScore
band
reason
matchedRules
candidateCount
scoredCount
```

除时间戳、请求 ID 等运行元数据外必须完全一致。

## 12. 风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| 本地 V1 快照不完整 | 迁移后只有软性或大量空规则 | 权威 API 拉取、分页总数校验、覆盖审计设为 T1 阻断门槛 |
| 资格逻辑混入 V2 推荐 | 推荐排序和线上行为漂移 | 独立目录、独立接口、V2 响应逐字段不变测试 |
| 缺失 10 分被解释为符合 | 用户误以为具备资格 | 条件分兼容但门禁强制 `needs_supplement` |
| 粗标签被当成政策条件证据 | 产生假背书 | 资格证据只能绑定具体条件项和企业事实 |
| 字段语义错配 | 高分但证据错误 | 语义类别白名单、路径回读、拒绝原因和专项测试 |
| 单位或年份错配 | 数值判断方向错误 | 比较前标准化、保留换算公式、年份策略测试 |
| V1 当前行为本身有歧义 | 迁移 AI 各自理解不同 | 特征测试冻结当前行为，改进另开决策，不静默修改 |
| 多 AI 修改同一入口 | 补丁互相覆盖 | 串行接力、文件所有权、交接报告、公共契约优先 |
| 模型不可用 | 定性条件无法判断 | 返回待确认/可重试，确定性条件继续执行，不返回虚假 0 分 |
| 规则快照更新后历史结果不可复现 | 无法审计 | 每次运行保存 manifest 哈希和单政策 profile 哈希 |

## 13. 完成定义（DoD）

只有以下全部满足，才能宣布“V1 资格门禁评分已迁移到 V2”：

### 13.1 数据与规则

- [ ] 权威规则源已拉取，分页总数和实际落盘数完成对账。
- [ ] 硬性、软性、直通车、空规则、非法规则和未解析片段均有统计。
- [ ] V2 规则快照有 schema、版本、来源时间和 SHA-256。
- [ ] V2 运行时不读取 V1 目录或调用 V1 服务。

### 13.2 算法

- [ ] 硬性、软性和直通车全部实现。
- [ ] 10/30/100、硬失败 0 分和 60 分阈值保持兼容。
- [ ] 单位换算发生在比较之前。
- [ ] `ruleKind` 仅作审计元数据，不重新引入固定 70/30 聚合。
- [ ] 缺失、拒绝、不可计算和跳过状态能够区分。
- [ ] 缺失或代理证据不能触发资格直推。

### 13.3 接口与隔离

- [ ] 独立资格接口可按输入政策顺序返回结果。
- [ ] V2 推荐接口的集合、排序、分数、档位和理由没有变化。
- [ ] 无规则政策保留 V2 推荐，资格侧返回 `not_evaluable`。
- [ ] 单政策资格失败不影响其他政策，也不导致 V2 推荐失败。
- [ ] 完整证据归档可通过 `runId` 追踪。

### 13.4 测试与验收

- [ ] 单条件、规则组、单政策、多政策、API 和归档测试全部通过。
- [ ] V1/V2 固定样本对照差异已解释，未解释差异为 0。
- [ ] V2 推荐不变回归差异数为 0。
- [ ] 至少完成人工核对：硬失败、软性成长分、缺失待补充、无规则不可评估、直通车各 3 个样例。
- [ ] 每个开发阶段都有交接报告、测试命令和回滚说明。

### 13.5 明确不能作为完成证据的情况

- 只创建了 `policy_eligibility_rules.json`；
- 只实现了几个 `hardConditions`；
- 只把 V1 最终分数字段复制到 V2；
- 只跑通一条政策；
- 只使用本地旧快照，没有验证权威 API 总数；
- 资格链路通过修改 V2 `band` 或删除推荐项实现门禁；
- 测试通过但没有 V1/V2 对照；
- 代码可运行但缺失数据仍能进入资格直推。

## 14. 推荐执行顺序与里程碑

| 里程碑 | 包含阶段 | 可验收成果 | 是否可交给下一 AI |
|---|---|---|---|
| M0 基线冻结 | T0 | 当前原型与 V2 耦合点清单 | 是 |
| M1 规则可迁移 | T1-T2 | 权威规则快照、schema、覆盖审计 | 是 |
| M2 条件可求值 | T3-T4 | 字段证据、单位换算、条件结果与 V1 对照 | 是 |

| M5 迁移可验收 | T7 | 全面对照报告、人工抽检、DoD | 是 |

后续 AI 应以里程碑为交接单位，不应以“写完若干文件”作为完成标准。
