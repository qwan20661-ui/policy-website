# PEMatching_v2 接口文档

企业工商数据 → 政策标签匹配 → 评分排序。独立服务，默认端口 `8020`（老链路占 `8010`，互不影响）。

**本服务无鉴权，仅供内网调用。** 若需暴露到公网，必须在网关层加认证。

## 启动

```powershell
# 启动时会同步审核政策并生成新条件包，不执行旧 A-F 后台打标
python backend/PEMatching_v2/api_server.py

# 当前 /api/v2/tagmatch/* 仍为旧链路；其标签缺失时按需手工生成
python backend/PEMatching_v2/run_policy_tagging.py
```

统一响应格式：

```json
{"success": true, "data": {...}, "meta": {...}, "message": ""}
```

失败时 `success=false`、`data=null`、`message` 为错误原因。

---

## 1. 两种模式的区别（先读这节）

| | `deterministic` | `agent` |
|---|---|---|
| 耗时 | **P50 约 75ms** | **约 50 秒** |
| 是否调 LLM | 否 | 是（多轮 tool-calling） |
| 结果可复现 | **是**，同输入必同输出 | 排序可能有微小差异 |
| 推荐理由 | 确定性模板（引用计分依据） | 模型撰写，更具体 |
| 检索策略 | 一次，用规则聚合的标签 | 可换标签组合多次检索 |

**分数在两种模式下完全一致**——分数由确定性函数算出，模型不参与计算。实测双模式推荐集合重合度 100%，差异仅在同分政策间的顺序。

选用建议：批量推送、回归测试、对延迟敏感的场景用 `deterministic`；需要可读推荐理由的单企业查询用 `agent`。大批量 `agent` 请用 CLI 而非接口。

## 2. `GET /health`

健康检查与配置回显。

```powershell
curl http://127.0.0.1:8020/health
```

响应 `data` 关键字段：

| 字段 | 说明 |
|---|---|
| `status` | `ok` / `degraded` / `unavailable`，由政策同步和新条件包政策源决定 |
| `model` | 当前 LLM 模型名 |
| `config` | 并发、超时、轮次上限等运行参数 |
| `policySnapshot` / `policyConditionSnapshot` / `policyTags` | 文件是否存在、大小、更新时间 |
| `policySync` | 审核政策同步状态、数量、版本和降级原因 |
| `matchPolicySource` | 新链路条件包政策数、版本和直接字段覆盖统计 |
| `policyIndex` | 旧标签索引标记；健康检查不加载旧标签，固定为按需加载状态 |

旧标签缺失不会让新链路健康状态降级。若 `status=degraded`，优先检查 `policySync.degradedReason` 和 `matchPolicySource.error`。旧 `/api/v2/tagmatch/*` 或 `/api/v2/policy-tags` 不可用时，再检查 `policyTags` 并按需执行旧打标命令。

## 3. `POST /api/v2/tagmatch/enterprise`

单企业匹配。

### 请求

**请求体**：企业接口的响应对象（`BaseBusinessInfo` + 子表结构），或包在 `enterprise` 字段里：

```json
{"enterpriseName": "...", "registerDate": "...", "operationInfoList": [...], ...}
```

必填字段只有 `enterpriseName`，其余全部可缺失——缺失字段的处理见第 5 节。对于工商接口没有覆盖、但政策原文要求核验的事实，可附带 `eligibilityFacts`；值必须来自可追溯的业务数据源，未提供时系统会返回 `unknown`，不会假定通过：

```json
{
  "enterpriseName": "...",
  "eligibilityFacts": {
    "isProvincialNewResearchInstitution": true,
    "positiveEvaluationConclusion": true,
    "xiamenFirstCompletionUnit": true,
    "fujianLegalPerson": true,
    "researchCapability": true
  }
}
```

**查询参数**：

| 参数 | 必填 | 默认 | 说明 |
|---|---|---|---|
| `mode` | 否 | `agent` | `agent` / `deterministic` |
| `keyword` | 否 | 无 | 查询关键词，驱动关键词附加分。**中文需 URL 编码** |
| `enableStage2` | 否 | `false` | 是否执行 G4 第二轮精推规则 |
| `topN` | 否 | `20` | 返回政策条数上限，最大 100 |
| `today` | 否 | 当天 | 基准日期 `YYYY-MM-DD`，影响成立年限与时效性判定。用于复现历史结果 |

### 示例

```powershell
$body = Get-Content "backend/PEMatching/企业测试目录/2452_测试企业名称201.json" -Raw
$kw = [uri]::EscapeDataString("研发补助")
Invoke-RestMethod -Method Post -ContentType "application/json" `
  -Uri "http://127.0.0.1:8020/api/v2/tagmatch/enterprise?mode=deterministic&keyword=$kw&topN=5" `
  -Body $body
```

### 关键字段解读

| 字段 | 怎么用 |
|---|---|
| `meta.dataCompleteness` | **先看这个**。结果建立在多少信息量上，缺失字段多则符合度参考价值下降 |
| `meta.degraded` / `degradedReason` | `agent` 模式下模型异常时为 `true`，此时结果由确定性路径产出，分数仍可信 |
| `meta.requestId` | 查审计日志用：`backend/PEMatching_v2/logs/<requestId>.log` |
| `reasonSource` | `model` 表示模型撰写，`template` 表示确定性模板兜底 |
| `gateResult.creditChecked` | `false` 表示信用字段无值未校验——**不等于信用良好** |
| `recommendations[].conditionMatchScore` | **申报要求符合度（0–100）**，推荐按它降序排序 |
| `recommendations[].gateStatus` | 档位：`direct_push` / `needs_supplement` / `not_recommended` / `not_evaluable`；**推荐列表只含前两者** |
| `recommendations[].directPushAllowed` | 是否允许直推（`gateStatus=direct_push` 时为 `true`） |
| `recommendations[].gateReasons` | 档位判定原因码（如 `HARD_CONDITION_FAILED`、`MISSING_ENTERPRISE_FACT`、`SCORE_BELOW_THRESHOLD`） |
| `recommendations[].conditionDetails` | 逐条件的满足/不满足/缺数据结果，供核验 |
| `policyEvidence` | 规则关键词与具体政策关键词的直接交集；为空表示没有政策级规则背书 |
| `eligibilityExclusions` | `not_recommended`（硬性不通过/符合度不足）与业务规则排除的政策，不进入 `recommendations`，在此保留 ID、原因与建议动作 |
| `eligibilityResult` | 全部可评估政策（含 `direct_push`/`needs_supplement`/`not_recommended`）的资格评估清单；**不含 `not_evaluable`（无申报条件档案或不可评估，静默丢弃）** |
| `recommendableCount` | 通过资格与业务规则过滤后、最终可推荐的政策数，允许小于请求的 `topN` |

## 4. `POST /api/v2/tagmatch/batch`

批量匹配。请求体为企业对象数组，或含 `enterprises` 数组的对象。查询参数同上。

上限 50 条（`V2_BATCH_MAX_SIZE`）。**`mode=agent` 的批量耗时 = 单企业约 50 秒 × 条数 ÷ 并发数**，大批量请用 CLI：

```powershell
python backend/PEMatching_v2/run_tagmatch_batch.py --mode agent --limit 100 --workers 4
```

响应 `data.results` 是数组，顺序与输入一致，每项含 `index` / `enterpriseName` / `success`。单条失败不影响其余，失败项带 `error` 与 `meta.requestId`：

```json
{
  "success": true,
  "data": {"results": [
    {"index": 0, "enterpriseName": "甲公司", "success": true, "data": {...}, "meta": {...}},
    {"index": 1, "enterpriseName": "乙公司", "success": false,
     "error": "ValueError: ...", "meta": {"requestId": "abc123"}}
  ]},
  "meta": {"total": 2, "succeeded": 1, "failed": 1, "mode": "deterministic"}
}
```

**校验时机**：所有企业记录先全部校验格式，任一条缺 `enterpriseName` 就整批返回 400（提示第几条），避免跑到一半才失败。

## 5. 字段缺失对结果的影响（重要）

本链路的核心前提是**任何企业字段都可能没有值**。误读这一节会导致分数被错误解释。

### 5.1 企业侧三态仍然成立

| 状态 | 含义 | 处理 |
|---|---|---|
| 有值 | 已核验的真实取值 | 参与条件判定 |
| `0` | **确认为零**（如确认没有知识产权） | 参与判定，按真实值比较 |
| `unknown` | **不知道**（字段为 null / 空） | 对应条件判为「缺失」，按缺失口径记 10 分，并计入待补齐 |

### 5.2 申报要求符合度怎么算（新口径，替代原 150 分制）

推荐排序不再用五维打分，改为**逐条核对政策申报条件**后取平均：

1. **硬性先行**：先逐条判定硬性条件（资格门槛）。任一硬性条件明确不满足 → 该政策**直接 `not_recommended`，不再判软性**。
2. **硬性通过后，硬性与软性条件一起计分**：

| 条件结果 | 单条得分 | 说明 |
|---|---|---|
| 满足 | 100 | 企业事实明确达到要求 |
| 软性不满足 | 30 起步 | "≥"类要求按企业实际值靠近门槛的程度加分，达不到记 30 |
| 缺失（unknown） | 10 | 判不了按最低分算，**不是 0**——0 是"确认达不到"，10 是"不知道" |
| 硬性不满足 | 0 且整条不推荐 | 已在第 1 步被否决，不参与排序 |

3. **申报要求符合度 = 各条可计分条件（含硬性与软性）得分的平均**，换算成 0–100，即 `conditionMatchScore`。

> 缺数据只把条件记 10 分并进「待补齐」，**不冤枉企业**；补齐字段后重新评估会自动更新分数与档位。

### 5.3 已知会大面积缺失的字段

实测样本（3251 家）里以下字段 100% 为空，依赖它们的规则必然 `skipped`：

`enterpriseCredit`、`techContractAmount`、`productServiceIntro`、`highTechField`、`enterpriseScale`、`hasRndAccount`、`hasRndInstitution`、`industryUniversityCoop`、`isInnovativeSme`、`isSpecializedSme`、`isSpecializedLittleGiant`、`isTechLeaderEnterprise`、`isInnovativeLeader`

`registerCapital` 仅 0.03% 有值。`industryLevel1/2` 约 31% 有值——**约七成企业的 C 行业领域为 `unknown`，领域匹配度 30 分不参与计分**。

### 5.4 规则三态

`channelResults` 里每条规则有三种状态，**`skipped` 既不是命中也不是未命中**：

| 状态 | 含义 |
|---|---|
| `matched` | 条件满足 |
| `unmatched` | 条件可判定但不满足 |
| `skipped` | 依赖字段为 `unknown`，判不了。附 `skipReason` |

`skipped` 里 `permanent=true` 的（目前只有 R17）是接口契约就没这个字段，补不了；其余补齐字段后自动生效，无需改代码。

### 5.5 G0 信用拦截

`enterpriseCredit` 实测 100% 为空。缺失时：

- **不拦截**（否则全部企业被拦）
- **不标记信用良好**（否则白送 10 分）
- `gateResult.creditChecked=false`，信用记录 10 分从分母剔除

`gateResult.passed=true` 且 `creditChecked=false` 的含义是「未发现信用问题，但也未校验」。

## 6. 档位与阈值

| 档位 | 判定 | 含义 |
|---|---|---|
| `direct_push` | 符合度 ≥60 且所有条件均已核实、无缺数据 | 申报条件基本满足，可直接推送 |
| `needs_supplement` | 还有条件「无法判断」（缺数据/无法核实） | 部分满足、部分待核实；补齐后会自动重新判定 |
| `not_recommended` | ① 任一**硬性条件不满足**（一票否决）；或 ② 全部已核实但符合度 <60 | 没资格或满足程度不足，不进推荐列表，单列 `eligibilityExclusions` |
| `not_evaluable` | 该政策无申报条件档案或评估出错 | **不展示**（`eligibilityResult` 与推荐列表均不含） |

**推荐列表只含 `direct_push` 与 `needs_supplement`**，按 `conditionMatchScore` 降序；`not_recommended` 在 `eligibilityExclusions` 中保留原因，`not_evaluable` 静默丢弃。

> 注：当前政策库 77 条中仅 41 条有可评估的申报条件档案，其余 36 条评估为 `not_evaluable` 不会出现在输出里；多数政策缺数据，故推荐多落 `needs_supplement`。启用逐条件模型抽取事实（`--eligibility-llm` 或接口 `useLlmEvidence=true`）可回填部分条件、提升符合度。

## 7. `GET /api/v2/policy-tags`

查看政策标签与分布，排查用。

| 参数 | 默认 | 说明 |
|---|---|---|
| `fusionPolicyId` | 无 | 查单条，不存在返回 404 |
| `includeNotApplicable` | `false` | 是否含不可申报政策 |
| `limit` | 200 | 返回条数 |

**不可申报政策默认排除**。政策库里有 13 条不是面向企业的可申报政策（评审专家征集、报告报送、统计调查、中介机构资格认定、面向高校院所科研人员的项目等），检索时自动排除，不会出现在推荐里。

## 8. 错误码

| 状态码 | 场景 | 示例 message |
|---|---|---|
| 400 | 参数非法 | `mode 非法：'magic'，合法值 ['agent', 'deterministic']` |
| 400 | 请求体格式错误 | `请求体不是合法 JSON：...` |
| 400 | 缺必填字段 | `企业数据缺少 enterpriseName` / `第 3 条企业数据缺少 enterpriseName` |
| 400 | 批量超上限 | `批量上限 50 条，实际 60 条。更大批量请用 run_tagmatch_batch.py` |
| 400 | 政策索引未就绪 | `政策标签不存在：...，请先运行 run_policy_tagging.py` |
| 404 | 路径或资源不存在 | `未知路径 /api/v2/xxx` / `政策不存在或未打标：NOPE` |
| 500 | 服务内部错误 | `服务内部错误：TypeError: ...` |

`agent` 模式下 LLM 不可用**不会**返回 5xx——会降级到确定性路径，返回 200 与完整分数，`meta.degraded=true`。

## 9. 耗时预期

实测（minimax2.7，单企业 30 条候选政策）：

| 场景 | 耗时 |
|---|---|
| `deterministic` 单企业 | P50 74ms，P95 195ms |
| `agent` 单企业 | 约 50 秒，6–10 轮 tool-calling |
| `deterministic` 批跑 100 家 | 约 2 秒 |
| `agent` 批跑（4 并发） | 约 15 秒/家 |

`agent` 模式耗时主要在 LLM 往返。已实现上下文压缩（旧工具结果压成摘要），避免多轮后 prompt 膨胀导致超时——未压缩时实测会涨到 19812 token 并触发 240 秒超时。

## 10. 审计日志

每次请求按 `requestId` 落盘到 `backend/PEMatching_v2/logs/<requestId>.log`，JSON Lines 格式，一行一事件。

记录内容：模式与入参、画像结果、规则三态、每次工具调用（名称/参数/耗时/是否成功）、每次 LLM 调用（token 数/耗时/tool_calls）、降级原因、上下文压缩事件。

排查 badcase 时先看这个文件，能定位到是规则判错、检索漏了还是模型选错。

## 11. 新申报条件匹配接口

`POST /api/v2/condition-match/enterprise` 与 `POST /api/v2/condition-match/batch` 是不依赖 A/B/C/D/E/F 标签的新链路。请求企业 JSON 与旧接口相同，支持 `today=YYYY-MM-DD` 固定回归日期；`topN` 仅在最终排序后截断，省略时返回全部推荐政策。

单企业响应的每条推荐包含 `fusionPolicyId`、`policyTitle`、`rank`、`finalScore`、`conditionScore`、`timelinessScore`、`reason` 和 `applicationWindow`。`audit` 额外保存逐条件证据、模型分、服务端复算分、原文冲突、缓存命中、重试次数和内容哈希。

模型调用失败只在该政策的 `meta.failures` 中记录，不中断同企业其他政策或同批其他企业。`GET /health` 的 `conditionMatch` 显示全局模型并发、缓存状态和评分配置版本。

当前默认 `PEMATCHING_V2_ENGINE=condition_llm`，现有 `/api/v2/tagmatch/*` 和本节 `/api/v2/condition-match/*` 均使用新条件链路。故障回滚时显式设置 `PEMATCHING_V2_ENGINE=legacy`；旧标签后台任务仍保持关闭。
