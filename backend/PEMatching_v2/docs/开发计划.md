# PEMatching_v2：工商数据标签匹配 Agent 开发计划

> 依据《基于工商数据的科技政策标签体系与匹配规则.docx》设计。本目录是**独立新链路**，与 `backend/PEMatching/` 零代码耦合：不 import 其任何模块、不修改其任何文件、不读写其 config 与 output、独立进程独立端口。docx 原件仍在 `backend/PEMatching/docs/` 下，本目录只引用不搬移。

## 0. 决策记录（已确认，不再讨论）

| # | 问题 | 决定 |
|---|------|------|
| 1 | docx 要求的 12 类工商字段，企业接口缺很多 | **有字段就处理，缺字段的规则和维度直接跳过**，不造假、不均值补造 |

## 1. 隔离原则

- **代码**：不 `import` 任何 `backend/PEMatching/` 下的模块。需要同类能力（如政策拉取、原子写文件）时在 v2 内重新实现，允许参照其写法但不共享代码。
- **配置**：v2 自己的 `.env`，变量统一 `V2_` 前缀。端口默认 `8020`（老链路 `8010`）。
- **数据**：v2 自己从结构化政策接口拉取并维护 `config/policy_snapshot.json`，不读老目录的 `config/主政策申报条件.json`。
- **产物**：v2 自己的 `logs/`、`output/`。
- **测试**：v2 自己的 `tests/`，用 `pytest backend/PEMatching_v2` 单独跑，不影响老链路回归。

技术栈与老链路保持一致，便于维护：标准库 `http.server` 起服务、`urllib.request` 调 LLM 与业务接口、`python-dotenv` 读配置、`openpyxl` 出 Excel、`pytest` + `unittest.mock` 测试。不引入新的第三方依赖。

## 2. 字段可用性声明（重要前提）

### 2.1 基本原则

**本链路不假定任何企业字段一定有值。** 每个字段在读取时都要走"取值 → 判空 → 标记可用性"三步，得到 `available` / `unknown` 两种状态：

- `available`：字段有值，参与规则判定与计分。
- `unknown`：字段为 `null` / 空串 / 子表缺失。**依赖它的规则记 `skipped`，依赖它的计分项从分母剔除**，不按"不满足"处理，不按 0 值处理，不用均值或默认值补造。

`unknown` 与"已核验的真实 0"必须区分。例：`ipClass1Count = 0` 是"确认没有 I 类知识产权"，创新活跃度记 0 分；`ipClass1Count = null` 是"不知道"，该计分项剔除分母。两者绝不可混同。

企业画像产出中必须携带 `fieldAvailability` 明细，接口响应也要回传，使调用方能判断结果是在多少信息量上算出来的。

### 2.3 由字段缺失导致的规则实际可用性

以现有样本为准，34 条规则的状态分三类：

| 状态 | 规则 | 说明 |
|---|---|---|
| **永久跳过**（字段在接口契约里就不存在） | R17 | 对外投资、跨省分支机构字段接口无定义 |
| **当前样本判不出**（字段有定义但 100% 空，新接口若补齐即可启用） | R00、R19、R20、R23、R26、R37 | 分别依赖 `enterpriseCredit`、`isInnovativeSme`、`isSpecializedSme`、`isTechLeaderEnterprise`/`isInnovativeLeader`、`techContractAmount`、`industryUniversityCoop`/`hasRndInstitution` |
| **可判定但覆盖率受限** | R08–R12（产业专项）、R18 | 依赖 C 子类，而子类关键词源（`productServiceIntro` 0% / `highTechField` 0% / `brief` 4.4% / 产品技术子表 ~7%）几乎全空，**实际最多覆盖 7% 的企业** |
| **可正常判定** | R05、R06、R07、R13–R16、R21、R22、R24、R25、R27–R35 | 其中部分依赖 30.8% 覆盖率字段，个例仍会 skip |

规则实现全部到位，不因当前数据空就不写——新接口补齐字段后无需改代码即可生效。响应里通过 `skippedRules` + `skipReason` 显式暴露，不静默截断。

### 2.4 G0 信用拦截的特殊处理

docx 把 R00（经营异常/严重失信）设为 P0 最高优先级、一票否决。但 `enterpriseCredit` 当前 100% 为空，无法判定。处理方式：

- **不因缺失而拦截**（否则全部企业都被拦），也**不因缺失而标记"信用良好"**。
- `gateResult` 返回 `{"passed": true, "creditChecked": false, "reason": "enterpriseCredit 字段无值，未执行信用校验"}`。
- 基础分里"信用记录 10 分"这一项同步从分母剔除，不白送 10 分。
- 字段一旦有值即自动启用完整拦截逻辑。

## 3. 标签体系

### 3.1 维度定义（落 `config/tag_taxonomy.json`，不硬编码）

- **A 支持方式**（政策侧单选为主，允许次标签）：A1 资质认定 / A2 财税优惠 / A3 资金奖补 / A4 人才 / A5 金融支持 / A6 载体平台 / A7 成果转化 / A8 科技合作
- **B 发展阶段**（多选）：B1 初创期 / B2 成长期 / B3 成熟期。企业侧运行时按"三信号或逻辑"算，政策侧打的是"适用哪些阶段"
- **C 行业领域**（多选，含子类）：见 3.1.1
- **D 申报门槛**（政策侧单选）：D1 低（登记/入库/自行判别即享）/ D2 中（需资质或规模达标）/ D3 高（竞争立项、评审择优）
- **E 支持力度**（可选）：E1–E5，按单项奖励上限从万元级到亿元级
- **F 兑现周期**（可选）：F1 一次性奖励 / F2 长期普惠 / F3 年度申报

#### 3.1.1 C 维度编号

docx 只写"C1-C8 高企八大领域"未逐项列出。按其给出的子类（C1.1 新型显示 / C1.2 集成电路 / C1.3 软件开发 均挂 C1）反推 C1 = 电子信息，即《高新技术企业认定管理办法》国家重点支持的八大领域：

| 编号 | 领域 | 子类 |
|---|---|---|
| C1 | 电子信息 | C1.1 新型显示、C1.2 集成电路、C1.3 软件开发 |
| C2 | 生物与新医药 | — |
| C3 | 航空航天 | — |
| C4 | 新材料 | — |
| C5 | 高技术服务 | — |
| C6 | 新能源与节能 | — |
| C7 | 资源与环境 | — |
| C8 | 先进制造与自动化 | — |
| C9 | 通用（全行业普惠兜底） | — |
| C10 | 未来产业 | C10.1 人工智能 |
| C11 | 数字经济 | — |

**子类只保留 docx 明文定义的这 4 个**（决策 11）。docx 虽写"叠加地方重点产业子类"，但地方产业清单若取自政策库 `industryFieldPath`，即等于把政策库分类引回匹配轴，与决策 10 冲突；且子类判定依赖的文本字段实测覆盖率仅 7%，扩充后也判不出来。需要扩充时由业务方直接给产业清单，加进 `tag_taxonomy.json` 即可，代码无需改动。

**副作用与补偿**：docx 计分是"子类命中 30 / 大类命中 20 / 仅 C9 通用 10"。只有 4 个子类且都在 C1、C10 下，意味着 C2–C8 类政策的领域匹配度天然封顶 20 分。为避免这一差距被误读为匹配度差异，计分改为四档（见 6.1）：**子类交集 30 / 大类精确交集 25 / 政策仅 C9 通用 10 / 无交集 0**，用"大类精确匹配"这一档承担区分度，不依赖子类。

### 3.2 政策侧打标（离线 LLM 批量，产出 `config/policy_tags.json`）

**输入上下文**（每条政策一次调用）：

| 内容 | 来源字段 | 作用 |
|---|---|---|
| 标题、摘要 | `policy_info.policyTitle` / `summary` | 通用 |
| 支持方式 | `support_methods[].supportType` / `supportTypePath` / `contentDesc` / `amount` / `maxAmount` | 推 A、E 主依据 |
| 行业领域 | `policy_info.industryField` / `industryFieldPath` | 推 C 的**证据**（不是取值来源，见决策 10） |
| 适用范围 | `policy_info.applicableScopePath` | 推属地标签 |
| 政策自带关键词 | `raw_detail.keywords[].text` / `pathText` | 88/111 条有值，一级分类含研发创新/资质认定/科技金融/税收优惠等，A、C 的强信号 |
| 申报条件 | `structured_conditions[]` | 推 D 门槛、抽申报期 |
| 关联政策 | `raw_detail.parentPolicy` / `directParentPolicies` / `ancestorPolicies` / `childPolicies` / `descendantPolicies` | 23 条有父政策、5 条有子政策；子政策条件常不完整，靠父政策补口径 |
| 申报材料 | `materials[].materials` / `method` | 辅助判 D |

**输出契约**（`response_format: json_object` 约束，打标不用 tool-calling）：

```json
{
  "fusionPolicyId": "6548",
  "tags": {
    "A": {"primary": "A1", "secondary": ["A3"], "confidence": "high", "basis": "supportTypePath=资质荣誉-…"},
    "B": {"values": ["B1", "B2"], "confidence": "medium", "basis": "申报条件未限定年限，按科小口径覆盖初创成长期"},
    "C": {"values": ["C9"], "subValues": [], "confidence": "high", "basis": "industryField=通用行业，无产业限定"},
    "D": {"value": "D1", "confidence": "high", "basis": "评价入库、自行判别即享"},
    "E": {"value": null, "confidence": "low", "basis": "支持方式未给金额"},
    "F": {"value": "F3", "confidence": "medium", "basis": "年度评价"}
  },
  "applicationWindow": {
    "startDate": "2026-03-01", "endDate": "2026-05-31", "yearScope": "2026",
    "isRolling": false, "confidence": "medium", "basis": "申报说明：2026年3月1日至5月31日"
  },
  "growthChain": {"prerequisite": null, "nextStage": "6534", "basis": "科小→市高→国高"},
  "keywordIndex": {"title": ["科技型中小企业", "评价"], "aKeywords": ["资质认定", "入库"], "cKeywords": []},
  "notes": ""
}
```

**约束**：

- **C 标签只能取 `tag_taxonomy.json` 里的 C1-C11 及 4 个子类编号**，禁止输出 `通用行业`、`半导体和集成电路` 这类政策库原始词表值。`basis` 里可引用 `industryField` 作为判断依据，但 `values`/`subValues` 必须是 C 编号。产出后走枚举校验，非法编号视为无效产出重跑。
- `basis` 必填，为空视为无效产出。
- 抽不出申报期填 `null`，**禁止编造日期**。
- `confidence=low` 的维度运行时不参与硬过滤，只影响排序。
- 增量打标：以 `fusionPolicyId` + 政策 `updateTime` 做指纹，政策未变则跳过。
- 并发上限 `V2_MAX_WORKERS`（默认 20）。111 条全量预计 3–6 分钟。
- 写入 `config/policy_tags.json`，`schemaVersion: pematching-v2-policy-tags-v1`，原子替换（写 `.tmp` 再 `os.replace`）。

**人工复核**：产出 `output/policy_tags_review.xlsx`，一行一政策，列出各维度取值、置信度、依据原文。复核修正后回写 JSON 的机制放四期。

### 3.3 企业侧标签计算（确定性，无 LLM）

- **B 发展阶段**：按 docx 三信号"或"逻辑，成立年限（`registerDate`）、营收（`operatingIncome` 最新年度，元→万元）、已有资质（`honorQualificationList`）任一命中即归入，**可同时属多个阶段**。三信号全 `unknown` 则 B 记 `unknown`。注意 `registerDate` 覆盖率 100%，故 B 实际总能算出至少一个阶段。
- **C 行业领域**：`industryLevel2` → 4.1 映射表 → C 大类；未命中降级 `industryLevel1`；再用 4.2 关键词库在 `brief` + `mainProductList` + `mainTechnologyList` + `industryLevel2` 文本上判子类。大类子类都不命中 → C9；行业字段全空 → `unknown`。
- **规模**：`employeeCount`（100%）+ `operatingIncome`（31.1%）。`registerCapital` 与 `enterpriseScale` 实测不可用，不作依据。
- **创新活跃度**：`ipClass1Count + ipClass2Count` → 回退 `ipCount` → 回退 `inventionPatentCount`；全 `null` 则 `unknown`（区别于确认的 0 件）。
- **信用**：`enterpriseCredit` 有值时关键词判定（含异常/失信/处罚/黑名单 → G0 拦截）；无值按 2.4 处理。
- **属地**：`registerDistrict` → `nationalHighTechZone` → `registerAddress` 文本匹配，三级回退。`registerAddress` 覆盖率 100%，故属地标签实际总能算出。

## 4. 两张映射表（`config/`，人工可维护）

### 4.1 `config/industry_to_c_tag.json`：国标行业 → C1-C11

企业侧是国标行业分类（统计口径），C 维度是高企领域口径，两套编码不通用必须过表。省掉这一步则领域匹配度 30 分无法计算、R08–R12 无法判定。

实测取值是**有限封闭集合**：`industryLevel1` 10 种、`industryLevel2` 44 种，不是开放词表，一次映射即固化。

- `industryLevel1`：`I 信息传输、软件和信息技术服务业`(505)、`C 制造业`(321)、`M 科学研究和技术服务业`(149)、`E 建筑业`(7)、`N 水利环境`(5)、`D 电力热力`(4)、`G 交通运输`(3)、`R 文化体育`(3)、`A 农林牧渔`(2)、`P 教育`(1)

### 4.2 `config/keyword_library.json`：C 子类关键词 + 属地园区关键词

**这张表的预期覆盖率很低，定位是加分项不是主判据。** 子类判定的文本源实测：`productServiceIntro` 0%、`highTechField` 0%、`brief` 4.4%、`mainProductList` 2.9%、`mainTechnologyList` 5.4%，任一有值的企业仅 **7.0%**。即 93% 的企业无论关键词库写得多全都判不出子类，只能停在大类。

关键词取值只用两类来源，**不用编者的行业常识**：

1. **docx 原文出现的词**（有据）：集成电路、半导体、流片、EDA、IP 核、人工智能、大模型、算力、显示、光电、数据服务、数据要素、软件
2. **在真实企业文本里实测有命中的词**（有据），下表括号内为命中企业数：

| 子类 | 关键词（附实测命中企业数） |
|---|---|
| C1.1 新型显示 | 面板(57)、光电(30)、新型显示(4)、背光(4)、OLED(2)、Micro LED(1) |
| C1.2 集成电路 | 芯片(44)、半导体(17)、集成电路(11)、晶圆(8)、流片(1)、EDA(1) |
| C1.3 软件开发 | 系统集成(15)、软件开发(8)、SaaS(4)、信息技术服务(2) |
| C10.1 人工智能 | 人工智能(22)、机器学习(11)、算力(2)、大模型(1) |

**属地园区关键词**（同文件另一段，驱动 R13/R35/R36/R14）：火炬高新区、厦门科学城、自贸片区（含"自由贸易试验区"）、思明区、湖里区、集美区、海沧区、同安区、翔安区。匹配源 `registerDistrict`(30.8%) → `nationalHighTechZone`(7.7%) → `registerAddress`(100%)，因末级源覆盖率 100%，**属地这组规则是本链路覆盖率最高、最可靠的一组**。

## 5. 四通道规则引擎

规则**数据化**落 `config/rules.json`，引擎只解释执行，增删调整规则不改代码。

```
G0 前置拦截 (P0)  R00                     → 命中即终止，返回信用修复引导
       ↓ 通过（含 enterpriseCredit 缺失时的"未校验通过"）
G2 第一轮直推 (P1-P3)  纯工商数据
   梯度培育  R05 R06 R07
   产业专项  R08 R09 R10 R11 R12          （受 C 子类 7% 覆盖率限制）
   属地专项  R13 R35 R36 R14              （覆盖率最高的一组）
   规模普惠  R30 R31 R32 R15 R33 R34
   成长提示  R16 R17(永久跳过) R18
G3 链路推荐 (P1)  资质名单触发
   R19(缺字段) R20(缺字段) R21 R22 R23(缺字段)
       ↓ enableStage2=true 时继续
G4 第二轮精推 (P1-P3)  用请求体已有的研发/人才/技术合同字段
   R24 R25 R26(缺字段) R27 R28 R29 R37(缺字段)
```

规则数目核对：R00(1) + R05–R18(14) + R19–R23(5) + R24–R29(6) + R30–R37(8) = **34 条**，与 docx 一致。docx 无 R01–R04。

**单条规则结构**：

```json
{
  "ruleId": "R09",
  "channel": "G2",
  "priority": "P1",
  "name": "软件和信息技术服务业专项",
  "conditions": [{"field": "cTags", "op": "contains", "value": "C1.3"}],
  "signals": {"aTags": ["A2"], "cTags": ["C1.3"], "keywords": ["软件", "即征即退", "CMMI"]},
  "policyPackDesc": "软件专项包（两免三减半、即征即退、CMMI/CSMM 认证补贴）",
  "requiredFields": ["industryLevel2"],
  "chainBonus": false
}
```

**三态判定**：`requiredFields` 任一字段为 `unknown` → `skipped`（附 `skipReason` 指明缺哪个字段），既不算命中也不算未命中。响应单列 `skippedRules`，**不静默截断**。R17 在配置里直接标 `permanentlySkipped: true` 并注明字段在接口契约中不存在。

**规则命中 ≠ 产出推荐**：规则产出的是 `signals`（标签 + 关键词），供第 6 节检索与加分使用。`policyPackDesc` 只进"可关注方向"文案，不构成推荐项。库内无对应政策时记入 `unmatchedSignals`，作为补政策库的输入清单。

## 6. 评分模型（确定性）

**总分 = 基础分（≤100） + 附加分（≤50）**，满分 150。

### 6.1 基础分

| 项 | 权重 | 计分规则 | `unknown` 处理 |
|---|---|---|---|
| 领域匹配度 | 30 | 企业与政策 **C 子类**有交集 30；**C 大类精确**交集 25；政策仅 C9 通用 10；无交集 0 | 企业 C 为 unknown（实测约 69%）→ 剔除分母 |
| 发展阶段匹配 | 20 | 企业阶段与政策 B 有交集 20；相邻阶段 10 | B 为 unknown → 剔除分母（实测 B 基本总能算出） |
| 创新活跃度 | 25 | ≥10 件 25；5–9 件 15；1–4 件 8；**确认 0 件** 0 | 知产字段全 null → 剔除分母 |
| 规模适配 | 15 | 落在政策门槛区间 15；边界 8 | `employeeCount` 与 `operatingIncome` 均无 → 剔除分母 |
| 信用记录 | 10 | 无失信 10 | `enterpriseCredit` 无值（实测 100%）→ 剔除分母，见 2.4 |

**归一化**：`基础分 = Σ实际得分 / Σ有效项权重 × 100`。字段缺失多的企业不被系统性压低，阈值口径保持可比。

领域匹配度的 25 分档（大类精确交集）是本方案对 docx 的调整，理由见 3.1.1 副作用说明——docx 原本靠子类拉开区分度，而本方案只有 4 个子类且覆盖率 7%，需要一个不依赖子类的区分档位。

响应必须回传 `effectiveWeight`、`excludedItems`、每项 `basis`，使分数可解释、可复算。

### 6.2 附加分（≤50，超出封顶）

| 项 | 分值 | 触发条件 |
|---|---|---|
| 关键词命中主标题 | +20 | 入参 `keyword` 命中政策标题 |
| 关键词命中 A 类标签 | +12 | 命中支持方式标签 |
| 关键词命中 C 类标签 | +10 | 命中行业标签 |
| 关键词命中政策正文 | +5 | 仅命中摘要/条件文本 |
| 时效性：当年未启动 | +15 | 当前日期 < `applicationWindow.startDate` 且同年 |
| 时效性：当年进行中 | +10 | `startDate ≤ 当前 ≤ endDate` |
| 时效性：往年政策 | +5（2025 年按 +8） | 窗口已过但政策仍有效 |
| 链路加成 | +10 | 企业正处于该政策 `growthChain.prerequisite` 位置 |

关键词四级**取最高一级不叠加**（docx 的"优先级"语义）。时效性三档互斥。不传 `keyword` 时四项全 0。`applicationWindow` 为 null 时时效性项 0，并在 `scoreExplanation` 注明原因。

### 6.3 阈值

- `≥80` → `direct_push`
- `60–79` → `needs_supplement`
- `<60` → `not_recommended`

阈值沿用 docx 取值，但 docx 是基于完整数据设想的。一期用真实企业跑分布后按实际情况校准（四期任务）。

## 7. Agent 设计

### 7.1 定位与职责边界

模型负责**编排、检索决策、结果解释**；算术与规则判定全部由工具（确定性 Python 函数）完成。模型不算分、不判规则命中、不编造政策。

用 tool-calling 而非一次性大 prompt 的三个理由：

1. **上下文可控**。111 条政策的 `raw_detail` 中位数约 9360 字符，全量拼入约 100 万字符，超上下文。按标签检索后只有十几条候选进入上下文。
2. **计分可复现**。`score_policy` 是确定性函数，同输入同输出，可单测可回归。
3. **过程可审计**。每轮调了什么工具、什么参数、返回什么，全部落 `logs/<requestId>.log`，badcase 能定位到是规则错、检索漏还是模型选错。

代价：单企业需 5–8 轮往返，预计 30–60 秒；tool 循环需自行实现（无 Agent 框架依赖）。

### 7.2 工具清单

| 工具 | 入参 | 出参 | 实现 |
|---|---|---|---|
| `build_enterprise_profile` | 无（用请求体企业对象） | 工商画像 + B/C/规模/知产/信用/属地标签 + `fieldAvailability` | 3.3 节 |
| `run_channel_rules` | `profile`, `enableStage2` | 各通道命中/未命中/跳过明细、聚合 signals、优先级 | 第 5 节 |
| `search_policies` | `aTags`,`cTags`,`bTags`,`dLevels`,`regionTags`,`keyword`,`limit` | 候选政策**摘要**列表（不返回全文） | 读 `policy_tags.json` + `policy_snapshot.json` |
| `score_policy` | `profile`, `fusionPolicyId`, `keyword` | 总分、基础分、附加分、逐项明细、档位 | 第 6 节 |
| `get_policy_detail` | `fusionPolicyId` | 单条政策申报条件、材料、支持方式 | 按需取，避免上下文膨胀 |

### 7.3 循环控制

用标准库 `urllib.request` 手写 tool 循环：

- 最大轮次 `V2_AGENT_MAX_TURNS`（默认 12），超限强制收尾并标 `truncated: true`。
- 超时、重试、退避走 `V2_LLM_TIMEOUT` / `V2_LLM_RETRY` / `V2_LLM_BACKOFF`。
- 每轮 `tool_calls`、参数、返回摘要写入 `logs/<requestId>.log`。
- **降级**：模型连续 2 轮不调工具或返回不可解析内容 → 切 `deterministic` 路径（固定顺序执行 profile → rules → search → score），只让模型写最终解释；响应标 `degraded: true` 及原因。接口不因模型异常而整体失败。

### 7.4 System Prompt 要点（`prompts/agent_system_prompt.md`）

- 禁止自行计算分数、自行判断规则命中、推荐 `search_policies` 未返回的政策。
- 给出建议调用顺序，但允许按需重复 `search_policies`（换标签组合再检索）与 `get_policy_detail`。
- 明确最终输出契约：推荐排序、每条分数与档位、推荐理由、命中规则、补数建议、跳过项说明。
- 明确告知模型：**字段缺失是常态**，遇到 `unknown` 不要推测填补，如实反映在解释里。

## 11. 政策库规模扩展性

当前政策库 111 条。本节记录规模增长到千级、万级时的应对，**现在不实现，但接口设计要留口子**——等真到万级再改是大手术，现在留接口成本很低。

### 11.1 实测基准（决定哪里是瓶颈）

| 项 | 实测值 | 结论 |
|---|---|---|
| 确定性算分吞吐 | 25000 条/秒 | 单企业算 10000 条政策仅需 0.4 秒，**算分永不是瓶颈** |
| 全部政策文本总量 | 111 条 = 29.8 万字符（约 18.6 万 token） | 已超 12.8 万上下文窗口，**全量塞给模型判断在 111 条时就已不可行** |
| 单条政策文本 | 中位数 2354 字符，P90 3953，最大 14247 | 单条精读没问题 |
| **C9 通用政策占比** | **69%（77/111）** | **这是真正的瓶颈**，见 11.2 |

### 11.2 真正的瓶颈：C9 通用政策过滤不掉

C9 通用政策对任何企业都是候选，标签筛选无效。按当前比例推演到 10000 条：

```
通用政策约 6936 条 → 全部进候选
产业政策约 3063 条 → 按 C 标签过滤后单企业约命中 278 条
单企业候选量约 7214 条 → 标签过滤只砍掉 28%，检索层基本失效
```

**这个问题与"是否预打标"无关**，改成匹配时让模型判断只会更糟（10000 条 × 企业数次调用）。解法是给检索层加筛选维度，见 11.4。

### 11.3 打标层：规模越大越该预打标

预打标是一次性、可增量的成本；匹配时判断是每企业重复付费。

| 政策库规模 | 预打标总调用 | 匹配时判断总调用（3251 家企业） | 倍数 |
|---|---|---|---|
| 111 条 | 111 次（一次性） | 9753 次 | 88× |
| 1000 条 | 1000 次 | 约 8.8 万次 | 88× |
| 10000 条 | 10000 次（20 并发约 8-10 小时，跑一夜） | 约 88 万次 | 88× |

万级规模的打标要点：
- **增量为主**：指纹（政策 `updateTime` + prompt mtime + taxonomy 版本）已在二期设计，首次全量后每天只打新增与变更。
- **分批落盘**：不要等全部跑完才写文件，每 500 条落一次盘，中断可续。
- **失败清单**：`output/tagging_failures.json` 记录失败条目，支持只重跑失败项。

### 11.4 检索层：叠加筛选维度 + 倒排索引

**第一步，加筛选维度**（千级规模够用）。除 C 标签外叠加：

| 维度 | 数据来源 | 筛选力 |
|---|---|---|
| 属地 | 政策 `applicableScopePath`（实测市级 79 / 省级 14 / 国家级 3 / 各区若干） | 强。企业只看得到本区+市级+省级+国家级 |
| D 申报门槛 | 打标产出 | 中。企业够不上 D3 的直接排除 |
| 申报期 | 打标抽取的 `applicationWindow` | 强。已截止的不进候选 |
| A 支持方式 | 打标产出 | 弱，仅配合用户查询意图使用 |

四维叠加后 7214 条可砍到几百条。

**第二步，倒排索引**（万级规模需要）。按标签建 `tag → policy_ids` 映射，用集合交集代替全表扫描：

```python
# 内存倒排，万级规模毫秒返回
index = {"C1": {id1, id2, ...}, "D1": {...}, "思明区": {...}}
candidates = index["C1"] & index["D1"] & (index["思明区"] | index["市级"])
```

`policy_index.py` 的 `search_policies` 签名不变，内部实现从"遍历过滤"换成"倒排交集"，对上层透明。

### 11.5 存储层：全量读内存不可持续

`policy_snapshot.json` 在 111 条时 6.8MB 可直接 `json.load`，10000 条会到 600MB+。

**二期就要做的抽象**（避免三期返工）：`policy_index.py` 对外只暴露四个函数，内部存储可换：

```python
def load_policy_tags() -> Dict[str, Dict]      # 只加载标签（轻量，万级也就几十 MB）
def search_policies(...) -> List[Dict]         # 返回摘要，不返回全文
def get_policy_detail(policy_id) -> Dict       # 按需读单条全文
def iter_policies() -> Iterator[Dict]          # 流式遍历，供打标脚本用
```

万级规模时的替换方案：标签仍用 JSON（轻量），政策全文改 SQLite（`policy_id` 主键索引）或按 ID 前缀分片为多个 JSON 文件。`get_policy_detail` 按需读单条，永不全量加载。

### 11.6 Agent 层：上下文压力与政策库大小脱钩

一期已埋好设计，万级规模无需改动：

- `search_policies` 有 `limit` 参数，默认返回 20 条
- 工具返回摘要（`summary` 前 200 字），不返回全文
- `get_policy_detail` 按需精读单条

即 Agent 永远只看十几条政策，上下文压力恒定。**这是"预打标做粗筛、模型做精判"分工的价值**：用 N 次一次性打标把 N 条政策收敛到十几条候选，再让模型精读那十几条。

### 11.7 分级触发条件

不提前优化。按实际规模触发对应改造：

| 政策库规模 | 需要做的 |
|---|---|
| < 500 条 | 现方案够用，无需改动 |
| 500–2000 条 | 加 11.4 第一步的筛选维度；打标改分批落盘 |
| 2000–10000 条 | 加倒排索引；政策全文改 SQLite 或分片存储 |
| > 10000 条 | 评估向量检索补充标签检索（应对 C9 通用政策的语义排序），打标改分布式队列 |
