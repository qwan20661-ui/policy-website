# 企业政策匹配重构开发计划

> 版本：V1.0  
> 日期：2026-08-06  
> 规则基准：[企业政策匹配新规则.md](企业政策匹配新规则.md)  
> 状态：T0-T9 的代码实现与离线自动验证已完成；真实模型压测、典型企业人工抽查和正式切换仍按灰度流程执行。
> 注意：开发阶段不用做过多无用的测试，主要进行改造成功就可以，后续开发完成后在真实跑几家企业进行测试最终结果是否政策就可以了
---

## 1. 重构目标

将当前“政策打标、标签召回、Agent 编排、资格门禁、逐政策证据抽取、业务二次过滤”多层链路，收敛为一条围绕申报条件的主链路：

```text
审核政策同步
→ 企业画像
→ 明确业务排除
→ 逐政策模型判断全部条件
→ 服务端复算条件分和总分
→ 排序输出
```

目标：

1. 只使用 `reviewStatus=1&structureReviewStatus=1` 的政策；
2. 服务启动时同步一次最新审核政策；
3. 取消 A/B/C/D/E/F 打标在核心匹配中的依赖；
4. 一条政策只调用一次模型，政策内全部条件一起判断；
5. 模型逐条件给分，服务端复算和聚合；
6. 同时支持单企业实时接口与批量接口；
7. 保留完整证据、模型输出和计算审计；
8. 通过功能开关实现灰度和快速回滚。

## 2. 当前基线与根因

### 2.1 数据基线

2026-08-06 本地接口核验：

| 指标 | 数量 |
|---|---:|
| `reviewStatus=1` 主政策 | 89 |
| 同时 `structureReviewStatus=1` | 78 |
| 规则表非空 | 41 |
| 规则表为空 | 37 |
| 条件项 | 220 |
| 已绑定标准字段 | 8 |
| `unresolved` | 212 |
| `llm_judge` | 69 |
| 硬性组 | 8 |
| 软性组 | 212 |
| OR 组 | 0 |

### 2.2 已确认的问题

1. 6534 高企政策原文条件完整，审核规则表仍为空；
2. 6509 研发补助规则表只覆盖部分条件；
3. 6451 原文 OR 条件在规则表中没有正确表达；
4. 现有 212/220 条件没有标准字段绑定；
5. 现有逐政策 LLM 平均约 12 秒，24 条政策、6 并发约 70 秒；
6. A/B/C/D/E/F 打标与申报条件评分存在重复语义；
7. Agent 多轮编排不负责最终分数，却增加模型调用和状态复杂度；
8. 推荐、资格、证据、业务过滤多处共同改变最终集合，排查困难；
9. 现有政策快照存在按“当天”命中缓存的行为，不能保证每次启动读取接口当前状态；
10. 当前没有人工标注的企业—政策正确答案，不能用单一自动分布证明效果改善。

### 2.3 根因判断

问题不在于缺少更多评分维度，而在于：

1. 政策原文、规则表和企业字段之间没有稳定的单一判断链路；
2. 标准字段映射覆盖率低，却试图用确定性门禁覆盖全部政策；
3. 同一匹配目标被标签分、资格分、模型理由和业务过滤重复表达；
4. 模型调用粒度、并发和缓存没有围绕实时与批量统一设计；
5. 没有业务标注集，历史验收更多证明实现一致性，而非推荐正确性。

## 3. 目标架构

### 3.1 模块职责

| 模块 | 职责 | 不负责 |
|---|---|---|
| 政策同步 | 拉取78条审核政策、详情、版本指纹 | 不打 A～F 标签 |
| 条件包组装 | 原样组合原文、规则表和政策元数据 | 不调用模型改写政策 |
| 企业画像 | 标准化企业事实、保留原始证据 | 不判断具体政策 |
| 预过滤 | 信用、年份、明确主体/属地/行业、资质、专利等确定性排除 | 不处理模糊语义 |
| 政策判断模型 | 单政策全部条件判断、逐条件给分、发现原文遗漏 | 不直接决定正式总分 |
| 评分验证器 | 证据校验、数值复算、AND/OR、时效和总分 | 不解释政策语义 |
| 编排器 | 候选调度、并发、缓存、失败隔离、排序 | 不修改模型证据 |
| API | 单企业、批量、健康状态和审计元数据 | 不重复实现匹配规则 |

### 3.2 目标目录建议

```text
service/
  policy_source.py              # 审核政策同步与快照
  policy_condition_package.py   # 条件包组装与质量检查
  enterprise_profile.py         # 复用或收敛现有 profile.py
  match_prefilter.py            # 明确业务排除
  policy_match_model.py         # 单政策模型调用与契约校验
  condition_scoring.py          # 条件复算、AND/OR、时效和总分
  match_orchestrator.py         # 实时/批量统一编排
  match_cache.py                # 内容哈希缓存
prompts/
  policy_condition_match_prompt.md
config/
  policy_condition_snapshot.json
  match_rules.json
```

文件名可根据现有风格调整，但职责边界不得重新混合。

## T1：统一政策启动同步

### 目标

服务每次启动只同步一次当前审核通过的78条政策，并生成可回滚快照。

### 工作项

1. 固定列表过滤：`reviewStatus=1`、`structureReviewStatus=1`、`requireSourcePolicyId=1`；
2. 按分页 `pagination.total` 校验完整性；
3. 并发拉取详情，设置超时、重试和全局并发上限；
4. 原样保存 `conditions`、`ruleTableJson` 和核心政策元数据；
5. 计算每条政策内容指纹和全库版本哈希；
6. 取消“当天已有快照就跳过同步”的行为；
7. 新快照完整生成后原子切换；
8. 同步失败且存在旧快照时继续提供服务并标记 `degraded`；
9. 首次启动无可用快照且同步失败时不进入就绪状态；
10. 服务启动后不定时刷新，政策变化通过重启服务重新同步。

### 建议修改

- 重构 `service/policy_sync.py`；
- 合并 `service/eligibility/sync.py` 的重复拉取能力；
- 调整 `api_server.py` 启动顺序；
- 健康接口增加政策总数、版本、同步时间和降级原因。

### 完成标准

1. 本地接口返回78条时快照必须为78条；
2. 任何单条详情失败都不能生成“看似成功”的不完整新快照；
3. 同一内容重复启动产生相同版本哈希；
4. 启动后运行期间不再次请求政策接口。

## T2：建立政策条件包

### 目标

由代码直接组装模型输入，不进行 A/B/C/D/E/F 模型打标。

### 条件包内容

```text
fusionPolicyId
policyInfo
conditions
ruleTableJson
supportMethods
keywords
documents
relatedPolicies
policyContentHash
qualityFlags
```

### 工作项

1. 统一接口字段名与内部字段名；
2. 保留完整 `applicationRequirement`，不得只保存摘要；
3. 原样保留硬性、软性、特殊通道和条件组；
4. 计算质量标记：规则表为空、规则项 unresolved、存在 llm_judge、原文疑似 OR 但规则表全 AND、目标值为空；
5. 不因质量标记直接丢弃政策；
6. 政策原文和规则表冲突时仅记录，不在组装阶段擅自改写；
7. 为模型构造精简但完整的条件输入，去掉附件和无关大字段。

### 完成标准

1. 6451 条件包同时包含原文 OR 表达和规则表结构；
2. 6534 即使规则表为空也保留完整高企申报原文；
3. 条件包生成过程不调用模型；
4. 条件包可序列化、可哈希、可审计。

## T3：取消旧政策打标依赖

### 目标

新匹配链路不依赖 A/B/C/D/E/F 标签和旧政策打标模型。

### 工作项

1. 新链路不调用 `service/tagging.py`；
2. 新链路不读取 `config/policy_tags.json` 作为评分依据；
3. 停止新链路启动时执行 `_startup_sync_policy_tags()`；
4. 行业、属地、申报对象直接使用接口字段和模型判断；
5. 支持方式、支持金额和时效直接使用政策详情；
6. 资质链迁移到独立业务配置；
7. 旧标签接口暂时保留，仅供旧链路灰度和回滚使用；
8. 所有删除动作推迟到新链路验收后。

### 完成标准

1. 删除或清空 `policy_tags.json` 不影响新链路；
2. 新链路不会触发政策打标模型；
3. 新链路启动日志不再出现后台 A～F 打标任务。

## T4：实现明确业务预过滤

### 目标

在调用模型前排除无需语义判断的确定性不适用政策，减少模型调用。

### 工作项

1. 企业信用负面时整家拦截；
2. 前年及更早政策排除；
3. 已有资质不推同级及以下，只保留直接后继；
4. 无资质或资质字段全空时只保留科小、创新型等链路起点；
5. Ⅰ类、Ⅱ类为空或总数为0时排除研发补助；
6. 处理知识产权业务代理口径；
7. 明确主体、属地、行业不符时排除；
8. 明确不可逆年龄、成立年限和上限条件排除；
9. 模糊或缺少证据的情况不得在预过滤阶段排除；
10. 每个排除结果必须记录原因码和证据。

### 完成标准

1. 所有预过滤规则有正例、反例和缺失值测试；
2. `null` 与 `0` 的行为分别测试；
3. 预过滤结果不依赖模型；
4. 同一输入结果稳定可复现。

## T5：设计单政策模型判断

### 目标

一次模型调用完成一条政策全部条件的语义判断、证据提取和逐条件评分。

### 输入

1. 单条政策的精简模型视图，完整保留申报条件原文和原始规则表；
2. 标准业务画像与未覆盖原始业务字段合并后的单一事实列表；
3. 缺失分、成长比例和精简条件键目录；
4. 不输入附件、材料、支持方式、审计哈希、旧标签和字段可用性状态；
5. 输出 JSON Schema 和证据约束。

### 输出

```text
sourceConflicts
conditionResults[]
discoveredConditions[]
```

### 模型行为

1. 优先读取 `ruleTableJson` 的硬性、软性、操作符和分组，并仅核验条件键目录；
2. 使用 `applicationRequirement` 理解规则语义和检查冲突；
3. 规则表非空时遗漏只记录冲突、不新增计分条件，规则表为空时才回退正文发现条件；
4. 为全部条件返回可由服务端回读的证据路径，不重复输出事实值；
5. 返回满足、部分满足、不满足或缺失；
6. 判断失败效果是范围不适用、不可逆、可成长或普通差距；
7. 逐条件给 0～100 分；
8. 规则表条件只回填条件键、判断、证据路径、理由和置信度；
9. 无证据时不得通过；
10. 不计算或输出条件总分和最终总分；
11. 输出必须是合法 JSON。

### 调用策略

1. 一个政策一次调用；
2. 不允许一个条件一次调用；
3. 不同政策受控并发；
4. 默认最多重试一次；
5. 单政策失败隔离；
6. 记录模型、提示词版本、token、耗时和重试。

### 完成标准

1. 模型输出 Schema 首次成功率和重试后成功率可统计；
2. 证据路径必须能由服务端回读；
3. 模型不得引用输入中不存在的企业字段；
4. 6451 能恢复原文 OR；
5. 6534 能从原文发现规则表遗漏条件；
6. 6509 能发现规则表未覆盖的申报主体和连续年度要求。

## T6：实现评分验证器

### 目标

模型负责语义，服务端负责可复现的证据、数学和业务边界。

### 工作项

1. 校验条件键、分数范围、状态和失败效果枚举；
2. 按证据路径回读事实值和说明，不信任模型生成的事实值；
3. 对数值条件执行单位转换和重新计算；
4. 最低门槛按实际值/目标值计算；
5. 最高上限超标和不可逆条件触发排除；
6. 缺失条件记10分但不计为命中；
7. AND 组取平均，OR 组取最高；
8. 正常组暂按等权平均；
9. 计算初始时效分和10%时效权重；
10. 复算 `verifiedConditionScore` 和 `finalScore`；
11. 从已核验的范围不适用或不可逆条件生成直接排除结论；
12. 所有条件缺失或所有已知条件为0时不推荐；
13. 政策本身没有任何条件数据时放到结果末尾，分数为空且标记数据待补齐。

### 完成标准

1. `1400/2000=70` 精确通过测试；
2. OR 分支 100/0 聚合为100；
3. AND 条件 100/0 聚合为50；
4. 模型不输出汇总分，正式总分只有服务端单一来源；
5. 所有公式和枚举均有单元测试；
6. 无人工权重隐藏在提示词中。

## T7：统一实时与批量编排

### 目标

单企业和批量企业复用同一匹配核心，只在外层调度方式上不同。

### 实时流程

```text
校验企业输入
→ 构建企业画像
→ 全局信用拦截
→ 政策预过滤
→ 候选政策并发模型判断
→ 单条失败隔离
→ 服务端评分验证
→ 排除与排序
→ 返回全部推荐政策
```

### 批量流程

1. 企业输入顺序固定；
2. 企业之间并发；
3. 企业内政策并发；
4. 两层并发统一受全局信号量控制；
5. 单企业失败不影响同批其他企业；
6. 支持命令行大批量和 HTTP 小批量；
7. 缓存相同企业与政策版本的判断结果。

### 缓存键

```text
enterpriseProfileHash
+ policyContentHash
+ modelName
+ promptVersion
+ scoringConfigVersion
```

### 完成标准

1. 每条候选政策每次未命中缓存时最多一次模型主调用；
2. 不存在逐条件模型调用；
3. 实时和批量对同一企业返回相同集合、分数和排序；
4. 模型调用数、缓存命中率和耗时可观测；
5. 全局并发上限在压力测试中有效。

## T9：测试、效果验证与性能验收

### 9.1 规则测试

至少覆盖：

1. 信用负面整家拦截；
2. 个人/高校主体排除；
3. 属地明确不符；
4. 行业明确不符；
5. 前年政策排除；
6. 今年已截止仍可推荐且时效分降低；
7. 已有资质不推同级；
8. 无资质只推链路起点；
9. 无专利不推研发补助；
10. 发明专利字段回退到Ⅰ/Ⅱ类总量；
11. 最低门槛成长分；
12. 最高上限不可逆排除；
13. 全部缺失不推荐；
14. AND 平均；
15. OR 最高；
16. 原文与规则表冲突；
17. 规则表为空但原文有条件；
18. 模型引用虚假证据被拒绝；
19. 模型总分与服务端复算不一致；
20. 单政策模型失败不影响其他政策。

### 9.2 集成测试

1. 使用固定本地接口夹具同步78条政策；
2. 使用模拟模型返回，禁止单测访问真实模型；
3. 验证服务启动只同步一次；
4. 验证旧快照降级；
5. 验证实时与批量一致；
6. 验证并发和缓存；
7. 验证响应与审计结构。

### 9.3 无人工标注时的效果验证

当前没有企业—政策人工正确答案，第一阶段采用：

1. 业务规则不变量测试；
2. 典型企业人工可解释性抽查；
3. 新旧链路差异清单；
4. 直接排除原因统计；
5. 每个政策被推荐企业数分布；
6. 全缺失、全0、规则冲突和模型失败比例；
7. 后续补建 5～10 家企业的人工标注集。

不得仅用“新旧集合重合度”证明新链路正确。

### 9.4 性能指标

第一轮先测量再定最终 SLA，但必须输出：

1. 单企业总候选数；
2. 预过滤后模型调用数；
3. 单政策模型 P50/P95；
4. 单企业总耗时 P50/P95；
5. 批量吞吐量；
6. 模型调用失败率和重试率；
7. 缓存命中率；
8. 并发排队时间。

阶段性硬约束：

1. 模型调用数不得等于条件数；
2. 模型调用并发必须受控；
3. 相同输入命中缓存后不得再次调用模型；
4. 批量任务不得因单条失败整体中止；
5. 若单企业 P95 不能满足业务实时使用，应在上线前评估多政策批次调用或异步任务，不得无限增加并发。

## 5. 迁移与灰度

### 5.1 功能开关

建议增加：

```text
PEMATCHING_V2_ENGINE=legacy|condition_llm
PEMATCHING_V2_POLICY_SYNC_ON_STARTUP=true
PEMATCHING_V2_POLICY_LLM_WORKERS=6
PEMATCHING_V2_POLICY_LLM_TIMEOUT=120
PEMATCHING_V2_MATCH_CACHE_ENABLED=true
PEMATCHING_V2_MODEL_ARCHIVE_ENABLED=false
```

### 5.2 灰度顺序

1. 新模块和新测试落地，不改变旧接口默认行为；
2. 增加影子模式，对同一企业同时运行新旧链路但只返回旧结果；
3. 输出差异报告，不用重合度直接判定对错；
4. 人工抽查典型企业；
5. 测试环境切换新引擎；
6. 观察模型错误、耗时和推荐分布；
7. 正式切换默认引擎；
8. 稳定后再删除旧打标和 Agent 代码。

### 5.3 兼容边界

1. 旧 A～F 标签文件在灰度期间保留；
2. 旧推荐接口可以通过功能开关回退；
3. 新旧响应字段需要明确版本，不静默改变同名字段含义；
4. 旧批量产物保留用于对照，不作为新规则验收真相。

## 6. 风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 模型逐政策调用慢 | 实时和批量耗时高 | 预过滤、受控并发、缓存、性能门槛 |
| 模型评分漂移 | 同一条件分数不稳定 | 温度0、固定版本、证据约束、服务端复算 |
| 原文与规则表冲突 | 条件口径不稳定 | 规则表优先参与评分、原文用于冲突记录 |
| 结构审核通过但规则为空 | 政策无法仅靠规则表执行 | 始终输入 `applicationRequirement`，规则表为空时回退正文发现条件 |
| 模型编造企业事实 | 错误推荐 | 证据路径回读、无证据不通过 |
| 无限并发 | 429、网关排队、服务失稳 | 全局信号量、退避、超时、熔断 |
| 政策接口不可用 | 服务启动失败或数据过期 | 上一份可用快照、健康状态降级 |
| 无人工标注 | 无法证明推荐正确 | 不变量测试、差异审计、后补小型标注集 |
| 企业敏感数据进入日志 | 隐私风险 | 最小字段、脱敏、归档开关、访问控制 |
| 双层分数不一致 | 排序可信度下降 | 容差校验、重试、异常隔离和审计 |

---

## 7. 回滚方案

1. 通过 `PEMATCHING_V2_ENGINE=legacy` 切回旧链路；
2. 政策快照始终保留上一版本，原子切换失败不覆盖；
3. 新提示词、评分配置和模型版本全部带版本号；
4. 新接口异常时不修改旧接口产物；
5. 数据迁移不删除旧标签和旧资格快照；
6. 回滚不依赖重新调用政策接口或模型。
