# PEMatching_v2 推荐链路数据说明

> 本文档解释：推荐结果（04_全量匹配批次 的 JSON、05_链路证据导出 的 xlsx）怎么读，以及"政策是怎么被推荐出来的"这条链路各环节的含义。
> 相关代码：`service/agent.py`、`service/rules.py`、`service/scoring.py`、`service/policy_index.py`、`service/tagging.py`、`service/profile.py`。
> 配置来源：`config/rules.json`、`config/tag_taxonomy.json`、`config/policy_tags.json`。

---

## 1. 推荐总流水线（6 步）

```
① 企业画像提取 → ② 前置门禁 → ③ 规则通道匹配 → ④ 信号聚合 → ⑤ 候选召回+打分 → ⑥ 排序输出
```

- **① 企业画像**：把企业标准化成标签与指标（`data.enterprise`）。
- **② 门禁**：信用负面清单前置拦截（`gateResult`），命中直接拦截全部推荐。
- **③ 规则通道**：规则引擎（`channelResults`，分 G0/G2/G3/G4 通道）逐条求值，输出 命中/未命中/跳过。
- **④ 信号聚合**：把所有命中规则的 `signals`（aTags/cTags/keywords）合并去重（`aggregatedSignals`）。
- **⑤ 候选召回+打分**：从政策库召回候选（`candidateCount`/`scoredCount`），逐条按企业画像打分。
- **⑥ 原始 TopN、证据过滤、输出**：资格可用候选先按既有确定性评分取原始 TopN；仅该窗口内的候选必须具有政策级规则证据（`matchedRules` / `policyEvidence` 非空）才保留为最终推荐。无证据候选写入 `evidenceExclusions`，窗口外政策不补位，因此最终推荐数可以小于 TopN。

## 2. JSON 输出结构

| 字段 | 含义 |
|---|---|
| `data.enterprise` | 企业画像：tags（B/C/区域）、metrics（指标）、qualifications（资质）、credit、fieldAvailability（字段可用性） |
| `data.gateResult` | 门禁结果：`passed`、`rules[]`（R00 信用拦截）、`blockedBy` |
| `data.channelResults` | 各通道规则求值结果：G2/G3/G4，每个含 `matched/unmatched/skipped` |
| `data.aggregatedSignals` | 命中规则信号的并集：`aTags/dLevels/keywords/…` |
| `data.recommendations[]` | **最终推荐**：总分、基础分、附加分、档位、非空的 matchedRules / policyEvidence、scoreExplanation、bonusDetail |
| `data.preEvidenceTopNCount` | 资格可用候选按原始分数截断后的证据过滤窗口大小 |
| `data.eligibilityExclusions[]` | 因 `source_conflict`、`ineligible`、`not_applicable` 被资格层排除的候选；这不是证据过滤 |
| `data.evidenceExclusions[]` | 资格未排除但无政策级规则证据的候选；不进入最终推荐，且不表示严格资格不符合 |
| `data.supplementSuggestions` | 建议企业补哪些字段可解锁被跳过的规则 |
| `data.unmatchedSignals` | 命中了规则但政策库无对应政策的"空信号"（政策库缺口） |
| `meta` | 模式（deterministic/agent）、耗时、数据完整度 |

## 3. 关键概念①：标签体系 A/B/C/D/E/F

两个正交的命名空间，**不要被字母混淆**：

| 维度 | 名称 | 取值 | 归属 |
|---|---|---|---|
| **R**（规则） | 规则引擎 | R00~R36 | **企业侧**执行，输出命中/未命中/跳过 + signals |
| **A** | 支持方式 | A1 资质认定 / A2 财税优惠 / A3 资金奖补 / A4 人才 / A5 金融支持 / A6 载体平台 / A7 成果转化 / A8 科技合作 | **政策侧**标签 |
| **B** | 发展阶段 | B1 初创 / B2 成长期 / B3 成熟期 | 企业侧画像算 + 政策侧标注"适用阶段" |
| **C** | 行业领域 | C1~C11，**C9=通用** | 企业侧画像 + 政策侧标注 |
| **D** | 门槛/程序 | D1 简易登记 / D2 资质审核 / D3 竞争立项 | 政策侧 |
| **E** | 支持力度 | E1~E4（万级→千万级） | 政策侧 |
| **F** | 申报周期 | F1 一次性 / F2 长期受理 / F3 年度申报 | 政策侧 |

要点：

- **企业不打 A 标签**（画像 tags 只有 B/C/cSub/regions）。企业的"支持方式倾向"通过**规则命中后发出的 aTags 信号**间接表达（如 R06→A1）。
- **政策不打 R**（推荐里的 `tags` 只有 A/B/C/D/E/F 六维）。
- R 与 A 字母无从属关系，是两个独立命名空间。

## 4. 关键概念②：R 规则（企业侧执行）

规则定义在 `config/rules.json`，每条含：

```json
{
  "ruleId": "R06",
  "channel": "G2",          // G0门禁 / G2通用 / G3梯度培育 / G4第二轮精推
  "priority": "P1",
  "conditions": [{"field": "tags.B", "op": "contains", "value": "B2"}],
  "requiredFields": ["bTags"],     // 字段缺失→规则跳过(skipped)
  "signals": {"aTags": ["A1"], "keywords": ["高企","认定"]},
  "policyPackDesc": "市高企培育库 → 国家级高企认定链路",
  "chainBonus": true,              // 是否属于"梯度培育链路"规则
  "chainStage": "国高→专精特新"    // 链路阶段名
}
```

- **条件独立、单条触发**：每条规则只查 1~2 个字段，互不排斥，命中就发信号。所以企业画像字段越齐，命中的规则越多（广撒网）。
- **matched/skipped/unmatched 三态**：
  - `matched`：条件成立，发信号
  - `skipped`：`requiredFields` 无值，规则被跳过（`skipReason` 注明缺哪个字段）——**不是"不命中"，是"判不了"**
  - `unmatched`：条件不成立（`details` 注明判断详情）
- **跳过规则可通过补数据解锁**：`supplementSuggestions` 就是按 skipped 规则的缺失字段汇总的（如补 `isInnovativeSme` 解锁 R19）。
- **"链路"（chain）**：只有带 `chainBonus+chainStage` 的规则（R19~R23）是真链路。链路 = 梯度培育逐级解锁，如 科小入库(R05入口)→专精特新(R19)→小巨人(R20)→瞪羚(R23)；高企线 科小→市高→国高(R21)→专精特新(R22)。链路加分见第 6 节。

### 为什么命中规则数 = 数据覆盖度

企业画像里 规模/资质/区域/招工 各线索有值，对应规则就被点亮。例（企业 2252）：

```
员工108   → 点亮 R30/R31/R15/R34（规模类）
营收2399万 → 配合员工点亮 R30；配合资质点亮 R06(B2)
科小资质   → R32；高企资质 → R22
思明区    → R14；新招15人 → R33
```

同一批数据点"广撒网"点亮多条规则，不是 9 个独立事实。

## 5. 关键概念③：规则→政策关联（matchedRules）

政策与规则的关联采用**规则关键词与具体政策关键词的直接交集**，由 `_rules_by_policy` 调用 `rule_evidence_for_policy` 计算。A/C 粗标签相同只用于候选召回，不能作为具体政策的规则背书：

```python
对每条命中规则：
  若规则 signals.keywords 与政策 title / keywordIndex 存在直接包含关系：
      记录 ruleId、matchedKeywords、basis 作为政策级证据
```

- A/C 标签不参与政策级规则背书；它们仍可用于召回，不等于可以推荐。
- 证据不进入通用评分公式，但它是**最终推荐的必要条件**：评分和资格排除完成后，系统先固定原始 TopN，再仅保留其中 `policyEvidence` 非空的候选；不从原始 TopN 外补位。
- `matchedRules` 是 `policyEvidence[].ruleId` 的扁平展示；需要查看关键词依据时使用 `policyEvidence`。

### `matchedRules=[]` 的含义

**"这条政策可以被召回并完成通用评分，但没有任何具体规则信号能够直接支持该政策。"** 它不会进入 `recommendations`，而会转入 `evidenceExclusions`。这不是严格资格失败，不能与 `eligibilityExclusions` 混用。

## 6. 打分计算

每候选政策 `totalScore = baseScore + bonusScore`。

### 基础分 baseScore（五项加权，`scoreExplanation`）

| 计分项 | 权重 | 说明 |
|---|---|---|
| 领域匹配度 | 30 | C 子类强交集 30 / 弱交集 25 / 大类精确 25 / 政策 C9 通用 10 / 无交集 0 |
| 发展阶段匹配 | 20 | 按企业在命中阶段的**信号数**计：3 信号 20 / 2 信号 15 / 1 信号 10 |
| 创新活跃度 | 25 | **IP 分档**：≥10 件 25 / ≥5 件 15 / ≥1 件 8 / 确认 0 件 0 |
| 规模适配 | 15 | 落在政策门槛区间 15 / 边界 8 / 越界 0；政策无门槛视为适配 15 |
| 信用记录 | 10 | 无失信 10 / 有负面 0；`enterpriseCredit` 无值→剔除分母 |

权重、分档、阈值全部在 `config/tag_taxonomy.json` 的 `scoring` 段，调参不改代码。

**"落 ≥10 件档"是什么意思**：创新活跃度分档是配置写死的（docx 方案原样），`innovationTiers` = `[{minCount:10,score:25},{minCount:5,score:15},{minCount:1,score:8},{minCount:0,score:0}]`。从高到低找第一档命中，11 件 → 落"≥10 件档"得 25 分。四期校准认为该分档合理（四档均有分布、方差 36.41、相关性 0.575），保留未改。

**归一化**（`scoreExplanation`）：

```
有效权重 = 100 − 被剔除计分项的权重合计
基础分   = Σ实际得分 / 有效权重 × 100
```

例（企业 2252 / 政策 6548）：10+15+25+15=65，信用剔除 10 → 有效权重 90 → `65/90×100=72.22`。字段缺失多的企业不被系统性压低。

### 附加分 bonusScore（`bonusDetail`）

目前只有**时效性**一项（互斥三档）：

| 时效档位 | 分数 | 含义 |
|---|---|---|
| `not_started` | 15 | 当年申报未启动（窗口在未来） |
| `in_progress` | 10 | 申报期进行中 / 常年受理 |
| `past_year` | 8 | 上一年度政策，仅参考 |

另有 `chainBonus`（链路加成 10）机制：政策标签含 `growthChain.prerequisite` 且企业 `chainStages` 命中时加分（scoring.py `_score_chain`）。本批次 Top20 未触发。

### 档位 band（`thresholds` 配置）

```
totalScore ≥ 85         → direct_push      直接推送
60 ≤ totalScore < 85    → needs_supplement 需补资料/条件存疑
< 60                    →（更低档，默认不进 Top20）
```

**⚠️ 已知现象**：当企业画像通用（C9 + 资质 unknown）时，所有 C9 政策的基础分几乎相同，**排名实际由时效加分决定**（`not_started` 15 > `in_progress` 10 > `past_year` 8），导致"还没开报的"排在"正在申报的"前面，业务上可能反而应倒过来。

## 7. 召回机制与 C9"放水口"（为什么无交集仍可能进入候选）

候选池 = **4 组标签检索的并集**（`_search_candidates`，agent.py:352）：

| 组 | 检索口径 | 作用 |
|---|---|---|
| 全标签组 | aTags(信号) + C + C子类 + B + 区域 | 最贴合企业 |
| 领域组 | 只按 C + C子类 | 捞跨阶段政策 |
| 阶段属地组 | 只按 B + 区域 | 捞跨领域普惠政策 |
| 规则信号组 | aTags(信号) + 区域 | 捞规则命中方向 |

**4 组任意一组命中即进池**（去重合并）。`search_policies` 逐政策做维度匹配，`_match_dimension`（policy_index.py:191）的取舍规则：

- 调用方未指定该维度 → 保留，不算命中
- 政策该维度标签为空 → 保留，不算命中（不因缺标签而排除）
- confidence=low → 保留，不算命中（低置信度不参与过滤）
- **政策含通用标签 C9 → 无条件保留且算命中**（`if generic in policy_values: return True, True`）

**C9 放水口**：只要政策标了 C9，无论企业行业如何都保留并命中。企业行业是 C9 时，领域组检索 = 所有 C9 政策全进池（94 条候选的主要来源）。

**结论链**：C9 或其他宽泛标签仍可能使政策进入候选池并完成通用评分；资格排除后先按分数固定原始 TopN，再在该窗口内进行政策级规则证据过滤。没有关键词证据的候选进入 `evidenceExclusions`，不再占用推荐名额，也不会由第 N+1 名之后的政策补位。

## 8. 证据文件怎么读

### 04_全量匹配批次（JSON）

即本说明第 2 节的 `data` 结构。企业级事实看 `enterprise`，规则求值看 `channelResults`，最终结论看 `recommendations`。

### 05_链路证据导出（xlsx）

| Sheet | 内容 |
|---|---|
| 汇报总览 | 汇总数字 |
| 推荐证据 | Top20 每行：总分/基础分/附加分/**命中规则**/申报窗口/时效/政策标签 A-F |
| 基础评分证据 | 五项计分逐项：权重/得分/依据/有效权重/原始得分 |
| 排除项证据 | 被剔除的计分项（如信用记录） |
| 附加分证据 | 时效/链路等附加分明细 |
| 企业画像证据 | 企业标签/指标/资质/字段状态 |
| **企业规则证据** | **每条规则的求值结果：状态/判断详情/跳过原因/缺失字段/聚合信号/政策包描述/链路加成** |
| 政策标签证据 | 每条政策的 A-F 打标：标签值/置信度/打标依据 |
| 证据边界 | 各证据覆盖范围说明 |

**看"某政策的命中规则证据"的步骤**：

1. 「推荐证据」的「命中规则」列 → 拿到该政策的规则清单（如 6534 = R06/R15/R22/R30/R31/R32）。
2. 「企业规则证据」按规则ID逐条看 → 判断详情（为什么命中）、聚合信号、链路加成。
3. 规则判定条件定义在 `config/rules.json`，政策打标依据在「政策标签证据」。
4. 最原始输出回 JSON `channelResults` 核对。

注意：企业规则证据**按企业组织**，一条规则不会因喂给多个政策而重复；政策↔规则的对应只在「推荐证据」体现。
