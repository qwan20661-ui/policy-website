## 问题 1：无命中规则（matchedRules=[]）的候选曾仍被推荐，且可进入 Top10

**状态**：已修复，待重新生成单企业与全量批次验证
**发现时间**：2026-08-04
**来源**：全量匹配批次 `20260804_125016` 企业 `2252_测试企业名称1_json.json`

### 历史现象

企业「测试企业名称1」的 Top20 推荐中：

- 政策 `6590 中日青少年科技交流计划申报`：`matchedRules=[]`（无任何规则背书），总分 **82.22**，排名 **第 7**，档位 `needs_supplement`。
- 同类 `matchedRules=[]` 的政策还有 6458（省级新型研发机构绩效测评）、6466（科技成果登记）等，均被正常推荐。
- 而该政策的申报条件实际要求**国家级专精特新"小巨人"企业**，企业 `isSpecializedSme` / `isSpecializedLittleGiant` 均为 `unknown`，不存在任何可支撑的画像证据。

即：**一条门槛很高的定向政策，在无规则命中、资质全未知的情况下，仅凭通用四项打分被排进 Top7**。

### 原根因

1. **召回不依赖规则信号**：候选池 = 4 组标签检索的并集（`_search_candidates`，agent.py:352）。6590 经「领域组（C9 ∩ C9）」与「阶段属地组（B2/B3 ∩ B2/B3）」进池，与 `matchedRules` 无交集无关。4 组中任意一组命中即入选。
2. **C9 是"放水口"**：`_match_dimension`（policy_index.py:211）对标签含 C9 的政策无条件 `return True, True`（保留且算命中）。企业行业为 C9（通用），等于**所有 C9 普惠政策对任何企业全开放**，这是 94 条候选的主要来源。
3. **打分与规则完全解耦**：旧版 `matchedRules` 是评分完成后才计算的展示标注，不进评分公式。6590 通用四项 10+15+25+15=65 → 归一 72.22 + 时效 10 = 82.22。
4. **无背书不降权**：旧版 `matchedRules=[]` 在召回、评分、排序、档位判定四个环节均无任何惩罚或过滤。

### 影响

- 高门槛定向政策被当成普惠政策推荐，对用户产生误导（误以为企业符合申报条件）。
- 通用四项基础分对 C9 政策几乎完全相同（均 72.22），Top 排名实际由时效加分决定，区分度弱。
- 推荐结果高度同质化、可信度下降；用户按此申报将大概率被驳回。

### 已实施修复

1. `_rules_by_policy` 改为只接受规则关键词与政策标题/关键词索引的直接交集，A/C 粗标签巧合不能形成 `matchedRules`。
2. 最终推荐组装改为：完成通用评分 → 排除 `source_conflict` / `ineligible` / `not_applicable` → 确定性排序并固定原始 TopN → 仅在该窗口内排除 `policyEvidence=[]`。窗口外候选不补位，因此最终推荐数允许小于 TopN。
3. 无证据候选不再静默丢弃，输出到 `data.evidenceExclusions`，状态固定为 `no_matched_rule_evidence`；资格排除仍只输出到 `data.eligibilityExclusions`，避免把“没有推荐证据”误表述为“严格资格不符合”。
4. `preEvidenceTopNCount` 记录过滤前的原始 TopN 窗口，`recommendableCount` 记录过滤后的最终推荐数；`scoredCount` 仍保留全部完成通用评分的候选数，用于审计过滤影响。

### 残余风险与验证边界

- 此修复收紧的是**推荐入口**，不改变召回、通用评分和严格资格判断；无证据不是资格失败。
- 政策关键词索引或规则关键词缺失会导致真实相关政策进入 `evidenceExclusions`，应以该清单和 `unmatchedSignals` 作为规则/政策库补齐输入。
- 历史批次的 JSON 与 Excel 均不具备新规则；必须在新批次目录重跑，旧批次仅保留为对照基线。

### 关联

- 修复代码：`service/agent.py`（`_assemble`、`_rules_by_policy`）、`service/policy_evidence.py`（关键词证据校验）、`service/policy_eligibility.py`（资格排除）。
- 回归边界：推荐中的每条政策必须有非空 `matchedRules` / `policyEvidence`；无证据和资格排除分别审计。
- 详细机制说明见《数据说明.md》第 5、7 节。

## 问题 2：政策「厦门市科技型中小企业评价」B 阶段打标偏差（标 B1/B2，应按 docx 标 B1）

**状态**：已修复
**发现时间**：2026-08-04
**来源**：全量匹配批次 `20260804_125016` 企业 `2252_测试企业名称1_json.json`

### 现象

- 政策 `6548 厦门市科技型中小企业评价` 的 B 阶段标签为 **`B1、B2`**（[policy_tags.json](backend/PEMatching_v2/config/policy_tags.json) 6548，confidence=medium），依据"职工≤500人、营收≤2亿元的规模门槛覆盖初创期与成长期企业，政策未限定成立年限"。
- 但原始设计 docx《基于工商数据的科技政策标签体系与匹配规则》[段落22] 明确：**"B1 初创期：成立≤3 年 或 营收 < 2000 万 或 无任何科技资质，对应创业补贴、科小入库等入门政策"**；[段落23] B2 成长期对应"高企、研发补助、专精特新等**成长政策**"，不含科小。
- 即：按 docx 设计，科小评价/入库应**只标 B1**，当前 B1/B2 属打标偏差。

### 根因

1. **打标口径错误**：打标时用"政策自身的规模门槛（职工≤500、营收≤2亿）反推适用阶段"，得出"覆盖初创+成长"；而 docx 定义的是"科小入库 = B1 入门政策"。两套口径不一致。
2. **规模门槛 ≠ 阶段归属**：规模门槛（职工≤500、营收≤2亿，来自《科技型中小企业评价办法》国科发政〔2017〕115号，存于 policy_snapshot.json 6548 的 `structuredConditions.applicationRequirement`）回答"**谁符合申报条件**"；B 阶段标签回答"**该政策属于哪个生命周期阶段**"。打标环节把前者误当后者的依据。
3. **规则与政策标签自相矛盾**：推送科小入库的规则 **R05 条件是 `tags.B 含 B1`**（rules.json），而政策标签却是 B1/B2——规则说"科小入库是 B1 的事"，标签却说"科小评价覆盖 B1/B2"。

### 影响

- 这是企业「测试企业名称1」（B 阶段 {B2,B3}）被推荐科小评价的直接原因：`{B2,B3} ∩ {B1,B2} = {B2}` → 阶段 15 分（scoring.py:144-153）。
- 若按 docx 标 B1-only，则 `{B2,B3} ∩ {B1} = ∅`，只能走相邻（B2↔B1）得 **10 分**，基础分与排名明显下降。
- **"已获科小"的企业被打 B2 的循环**：按 docx [23]，企业因"已获科小/高企"命中 B2 信号；已入库科小的企业（B2）又被 B1/B2 标签推回"科小评价"，造成低价值的重复推荐。

### 解决方案建议（待定）

| 方案 | 思路 | 影响 |
|---|---|---|
| A. 修正打标 | 6548 的 B 标签由 `B1、B2` 改为 **`B1`**（policy_tags.json 一处），依据 docx [22] | 所有企业科小评价推荐下降：B2 企业改走相邻 10 分；含 B1 的企业仍命中但分数变化 |
| B. 规范打标口径 | 政策 B 阶段打标统一依据 docx 的阶段归属定义，不再用规模门槛反推 | 需复核全部政策打标 |
| C. 规则与标签统一 | 使 R05 与 6548 的阶段口径一致（收紧标签或放宽规则） | 需产品确认 |

**建议先跑全量对比**：将 6548 改为 B1 后重跑，统计科小评价的推荐量与排名变化，确认符合预期再定方案。

### 关联

- 相关配置：`config/policy_tags.json`（6548 B 标签）、`config/policy_snapshot.json`（6548 原文：`structuredConditions.applicationRequirement`、`policyCode=国科发政〔2017〕115号`）。
- 设计依据：`PEMatching/docs/基于工商数据的科技政策标签体系与匹配规则.docx` [段落22/23/59]。
- 规则：`config/rules.json` R05（B1 触发）、R32（已入库科小 → 信用贷）。
- 阶段匹配打分逻辑见 `service/scoring.py:120-166`；标签体系说明见《数据说明.md》第 3 节。

## 问题 3：matchedRules 挂钩失真——粗标签巧合造成的"假背书"

**状态**：已修复
**发现时间**：2026-08-04
**来源**：全量匹配批次 `20260804_125016` 企业 `2252_测试企业名称1_json.json`

### 现象

政策 `6605 厦门市联合资助项目申报`（rank 2）的 `matchedRules = [R15, R22, R31]`，其中：

- **R15 是"小规模增信基金与创新券"**（关键词：增信基金、创新券），与 6605"联合资助项目申报"（产业项目资助资金）**内容零交集**。
- R15 挂上 6605 仅因 R15 信号 `aTags=[A5,A3]` ∩ 政策 6605 A 主标签 `{A3}` = `{A3}`（agent.py:244 的标签交集逻辑）。
- R22、R31 同理，三条规则全是靠 **A3（资金奖补类）这个大筐**碰巧同框。

**即：matchedRules 看起来是规则背书，实际是粗粒度 A 标签巧合，规则语义与政策内容无关。** 比 `matchedRules=[]`（问题 1）更误导——它给了一个"看似合理实则无关"的推荐理由。

### 根因

1. **挂钩只看 A/C 粗标签交集**：`_rules_by_policy`（agent.py:221-248）只用规则 `aTags/cTags` 与政策 A/C 标签做集合交集，**不看关键词、不看政策包描述语义**。A3（资金奖补类）把"增信基金、创新券、联合资助项目、研发补助"等全部塞进同一筐，任何发 A3 信号的规则都会挂到任何 A3 政策上。
2. **matchedRules 不参与打分却展示为背书**：它在评分完成后才计算（agent.py:148），纯展示用；但客户端把它读作"命中规则=推荐理由"，形成误导。

### 影响

- 推荐理由失真：客户看到"命中规则 R15（增信基金）"会误以为该政策与增信基金相关，实际无关。
- matchedRules 无法作为"为什么推荐"的可信依据，削弱整份推荐的可解释性。
- 真正内容相关的规则如果发的是其他标签（如 A8 科技合作），反而挂不上；A3 大筐政策反而被无关规则"撑场面"。

### 解决方案建议（待定）

| 方案 | 思路 | 影响 |
|---|---|---|
| A. 挂钩加关键词校验 | 规则信号关键词必须与政策内容/关键词有交集，才允许进 matchedRules | 直接消除"增信基金↔联合资助项目"这类假背书，但需政策关键词索引完善（当前 keywordIndex 已有） |
| B. 区分"触发规则"与"标签匹配" | matchedRules 只展示真正触发该类政策的规则；A/C 标签匹配不作背书展示 | 语义清晰，需重新定义展示口径 |
| C. 标注匹配依据 | matchedRules 旁注明"仅 A 标签 A3 匹配、关键词无交集"，保留现状但防误导 | 最小改动，客户仍能看出挂钩依据 |
| D. 挂钩参考政策包语义 | 用 policyPackDesc 与政策内容做语义相似度（如关键词重合率）作为必要条件 | 最贴近真实语义，需引入语义匹配 |

**建议**：与问题 1 一并处理——问题 1 是"无背书不降权"，本问题是"假背书误导"，根源同是标签/匹配粒度粗。方案 A 或 B 能同时缓解两者。

### 关联

- 代码：`service/agent.py`（`_rules_by_policy`、agent.py:148 写入 matchedRules）。
- 示例数据：政策 6605 `matchedRules=[R15,R22,R31]`，均为 A3 标签交集（见简化版 03 页「命中交集」列）。
- 与《问题.md》问题 1（无背书仍推荐）、问题 2（B 标签打标偏差）同源，均指向标签体系与匹配粒度。
