# 二期开发流程：政策打标

> 目标：给全量政策打上 A/B/C/D/E/F 六维标签与申报期，产出 `config/policy_tags.json` 与人工复核表，并实现按标签检索政策的能力。本期结束时，一期的 `score_policy` 有了真实政策标签可算，链路能对真实政策库出分。
>
> 依据 [开发计划.md](开发计划.md) 第 3.2、4、8.3 节。前置：[一期](一期_确定性底座开发流程.md) 已验收。

## 0. 前置条件

- 一期 DoD 全部达成，特别是 `taxonomy.py` 的 `is_valid_tag` / `validate_tag_payload`（本期的枚举校验依赖它）
- LLM 网关可用：`V2_API_URL` + `V2_MODEL_NAME=minimax2.7`
- 结构化政策接口可达（老链路用的 `STRUCTURE_API_BASE_URL`，v2 用自己的 `V2_STRUCTURE_API_BASE_URL`，值可相同）

## 1. 任务顺序

```
T1 policy_sync.py + run_sync_policies.py     → config/policy_snapshot.json
 └─ T2 policy_tagging_prompt.md              打标 prompt 与输出契约
     └─ T3 tagging.py                        单条打标 + 校验 + 重试
         └─ T4 run_policy_tagging.py         批量 + 增量 + 复核表
             └─ T5 policy_index.py           检索 + 时效性判定
                 └─ T6 验收
```

T5 只依赖 `policy_tags.json` 的结构，可与 T4 并行开发，但验收需等 T4 产出真实数据。

## 2. T1：政策快照

### 2.1 为什么 v2 自己拉

开发计划第 1 节：v2 不读老目录的 `config/主政策申报条件.json`。老目录那份是老链路的当天缓存，格式与生命周期由老链路控制，跨目录读会形成隐式耦合。v2 自己拉一份，格式自己定。

### 2.2 `service/policy_sync.py`

```python
def fetch_policies(force: bool = False) -> Dict[str, Any]
    """拉取结构化政策，写 config/policy_snapshot.json。当天已有快照且 force=False 则直接读缓存。"""
def load_snapshot() -> Dict[str, Any]
    """读本地快照；不存在时抛 FileNotFoundError 并提示先跑 run_sync_policies.py。"""
```

快照结构：

```json
{
  "schemaVersion": "pematching-v2-policy-snapshot-v1",
  "fetchedAt": "2026-08-03T14:22:10",
  "source": "http://127.0.0.1:8080",
  "count": 111,
  "data": [ { /* 单条政策，见 2.3 */ } ]
}
```

### 2.3 单条政策需保留的字段

只保留打标与检索需要的，不整份 `raw_detail` 落盘（老目录那份 6.8MB，其中大量字段打标用不上）：

| 字段 | 来源 | 用途 |
|---|---|---|
| `fusionPolicyId` | `id` | 主键 |
| `title` | `title` | 打标 + 关键词命中主标题 |
| `updateTime` | `raw_detail.reviewedAt` 或 `documents[].publishDate` | **增量指纹**，见 T4 |
| `policyInfo` | `policy_info` 全量 | 打标主依据 |
| `supportMethods` | `support_methods` | 推 A、E |
| `structuredConditions` | `structured_conditions` | 推 D、抽申报期 |
| `keywords` | `raw_detail.keywords` | 88/111 条有值，A/C 强信号 |
| `materials` | `materials` | 辅助判 D |
| `relatedPolicies` | `raw_detail` 的 parent/child/ancestor/descendant 四组，**只保留 id + title + policyInfo 摘要** | 补口径，见 2.4 |
| `documents` | `documents[]` 的 `publishDate` / `policyLevel` / `issuingDepartment` | 时效性辅助 |

### 2.4 关联政策的深度控制

`raw_detail` 里 parent/child/ancestor/descendant 四组关联，若递归展开会爆炸。规则：

- **只展开一层**，且每条关联政策只保留 `id`、`title`、`policyInfo.summary`、`structuredConditions` 前 5 条
- 实测 23/111 有父政策、5/111 有子政策，展开后单条政策上下文增量可控
- 关联政策自身的关联**不展开**

### 2.5 `run_sync_policies.py`

```powershell
python backend/PEMatching_v2/run_sync_policies.py            # 当天已有快照则跳过
python backend/PEMatching_v2/run_sync_policies.py --force    # 强制重拉
python backend/PEMatching_v2/run_sync_policies.py --stats     # 只打印快照统计不重拉
```

`--stats` 输出：政策总数、各字段非空率、有 keywords 的条数、有关联政策的条数、`policyAttribute` 分布。这份统计用于确认快照质量，也是 T2 写 prompt 的依据。

### 2.6 测试 `tests/test_policy_sync.py`

- mock HTTP 响应，断言快照结构与 `schemaVersion`
- 当天缓存命中时不发请求（`patch` 掉 urlopen 并断言未被调用）
- 关联政策只展开一层（造一个三层嵌套的 mock，断言第三层被截断）
- 原子写：写入过程中异常时原文件不被破坏

## 3. T2：打标 prompt

`prompts/policy_tagging_prompt.md`。**输出契约见开发计划 3.2 节，此处不重复，只列 prompt 设计要点。**

### 3.1 必须写进 prompt 的硬约束

| 约束 | 为什么 |
|---|---|
| C 标签只能输出 `tag_taxonomy.json` 里的编号 | 模型看到 `industryField=通用行业` 极易照抄，那会污染匹配轴（开发计划决策 10）。prompt 里要把 11 个大类 + 4 个子类编号完整列出，并明确"`industryField` 是证据不是答案" |
| **申报期不交给模型** | 见 3.5。实测 96.4% 的政策可确定性提取，模型只兜底剩余 4 条 |
| `basis` 必填且必须引用原文片段 | 便于人工复核；空 basis 视为无效产出 |
| 六个维度都要给 `confidence` | 下游按置信度决定是否参与硬过滤 |
| 不确定时给 `low` 而非猜一个高置信度值 | 宁可标不确定也不要假确定 |

### 3.2 上下文拼装顺序

按信息价值从高到低排，模型注意力有限：

1. 政策标题 + 摘要
2. 支持方式（`supportType` / `supportTypePath` / `amount` / `maxAmount`）
3. 政策自带 `keywords`（88/111 有值，是 A/C 最强信号）
4. `policyInfo` 的 `industryField` / `applicableScopePath` / `sceneUsage`
5. 申报条件全文（推 D、抽申报期）
6. 关联政策摘要（若有）
7. 申报材料

### 3.3 few-shot 示例

prompt 里放 2 个示例，覆盖两种典型：

- **通用普惠类**（如科技型中小企业评价）：C9、D1、B1+B2、F3、E 为 null
- **产业专项类**（如集成电路专项）：C1 + C1.2 子类、D3、B2+B3、E4、有明确申报期

示例必须是真实政策，从快照里挑，不虚构。

### 3.4 测试 `tests/test_prompt_contract.py`

- prompt 文件存在且非空
- prompt 里包含全部 11 个 C 大类编号与 4 个子类编号（防漏写导致模型输出非法值）
- prompt 里**不含**未定义的子类编号（决策 11：不自行扩充子类）
- prompt 里包含"industryField 是判断依据不是答案"字样（防匹配轴污染，契约不能被误删）
- prompt 里的 JSON 示例本身可 `json.loads`，且示例标签全部过 `validate_tag_payload`
- 示例覆盖通用普惠（C9/D1）与产业专项（含子类/D3）两种典型

### 3.5 申报期改为确定性提取（对原计划的修正）

原计划让 LLM 从申报条件文本抽申报期。实测快照后发现不必要：

| 来源 | 政策数 | 占比 |
|---|---|---|
| `applicationStartTime` / `applicationEndTime` 结构化字段 | 93 | 84.5% |
| `applicationInstruction` 含"长期受理"等字样 | 13 | 11.8% |
| **确定性可提取合计** | **106** | **96.4%** |
| 无任何申报期线索（LLM 也只能返回 null） | 4 | 3.6% |

因此实现为 `service/application_window.py`，三级策略：结构化字段 → 申报说明文本正则 → LLM 兜底。`merge_llm_window` 保证确定性结果永远优先。

**收益**：编造日期的风险从设计上消除（结构化字段不可能编造）；prompt 不再负责申报期，减少一处出错面；验收指标从"申报期抽取准确率 ≥80%"提高到 ≥95%。

## 4. T3：tagging.py

### 4.1 函数签名

```python
def tag_policy(policy: Dict[str, Any], max_retries: int = 2) -> Dict[str, Any]
    """单条政策打标。返回符合开发计划 3.2 契约的 dict，失败抛 RuntimeError。"""
def build_tagging_context(policy: Dict[str, Any]) -> str
    """按 T2 的顺序拼装上下文文本。"""
def validate_tagging_result(result: Dict, policy_id: str) -> List[str]
    """返回错误列表，空表示合法。"""
```

### 4.2 校验规则（`validate_tagging_result`）

按严重程度分两类：

**致命（触发重试）**
- JSON 不可解析
- `fusionPolicyId` 与输入不一致
- 任一维度的值不过 `is_valid_tag`（特别是 C 输出了 `通用行业` 这类政策库词表值）
- 任一维度 `basis` 为空
- `applicationWindow.startDate` 格式非 `YYYY-MM-DD`

**警告（记录不重试）**
- 六维全为 `low` 置信度（可能是政策信息本身太少）
- `applicationWindow` 全 null 但申报条件文本里出现了日期模样的字符串（疑似漏抽）

重试时把校验错误回传给模型（追加一轮 user message 说明哪里错了），比原样重试有效。重试 `max_retries` 次仍失败则抛 `RuntimeError`，由 T4 记入失败清单。

### 4.3 LLM 调用

- `response_format: {"type": "json_object"}`，**不用 tool-calling**（打标是单轮纯产出，用不上工具）
- 超时 `V2_LLM_TIMEOUT`（默认 180 秒，政策文本长）
- 标准库 `urllib.request`，与老链路写法一致

### 4.4 测试 `tests/test_tagging.py`

- mock 一个合法响应，断言解析结果结构完整
- mock 一个 C 输出 `"通用行业"` 的响应，断言被 `validate_tagging_result` 拒绝（**这条是防匹配轴污染的关键测试**）
- mock 一个 `basis` 为空的响应，断言被拒绝
- mock 前两次非法第三次合法，断言重试生效且最终返回合法结果
- mock 连续失败，断言抛 `RuntimeError` 且异常信息含 `fusionPolicyId`
- `build_tagging_context` 在关联政策为空时不报错

## 5. T4：run_policy_tagging.py

### 5.1 增量指纹

```
指纹 = sha256(fusionPolicyId + updateTime + prompt文件的mtime + taxonomy版本)
```

四要素的理由：政策本身变了要重打；prompt 改了要重打（打标口径变了）；taxonomy 加了新标签也要重打。指纹存 `config/policy_tags.json` 每条记录的 `_fingerprint` 字段。

```powershell
python backend/PEMatching_v2/run_policy_tagging.py                    # 增量，只打指纹变化的
python backend/PEMatching_v2/run_policy_tagging.py --force            # 全量重打
python backend/PEMatching_v2/run_policy_tagging.py --ids 6548,6534    # 只打指定几条，调试用
python backend/PEMatching_v2/run_policy_tagging.py --limit 5          # 只打前 5 条，验证流程
```

### 5.2 并发与容错

- 线程池，上限 `V2_MAX_WORKERS`（默认 20）。111 条预计 3-6 分钟
- 单条失败**不中断整批**，记入 `output/tagging_failures.json`（含 `fusionPolicyId`、错误类型、最后一次模型原始响应）
- 失败条目在 `policy_tags.json` 里**不写入**，保留上一次的结果（如果有），并在汇总里报告
- 全批结束打印：成功数 / 失败数 / 跳过数（指纹未变）/ 各维度置信度分布

### 5.3 原子写

先写 `config/policy_tags.json.tmp` 再 `os.replace`。**中途 Ctrl+C 不能留下半份文件**——这条要在测试里验证。

### 5.4 复核表 `output/policy_tags_review.xlsx`

一行一政策，列：

`fusionPolicyId` / `title` / `A主` / `A次` / `A置信度` / `A依据` / `B值` / `B置信度` / `B依据` / `C大类` / `C子类` / `C置信度` / `C依据` / `D` / `D置信度` / `D依据` / `E` / `F` / `申报开始` / `申报结束` / `申报期置信度` / `申报期依据` / `链路前置` / `链路后继` / `备注`

要求：
- 置信度 `low` 的单元格标黄，便于优先复核
- `applicationWindow` 全 null 的行标灰
- 冻结首行，各列宽度适配（`openpyxl` 支持）

### 5.5 测试 `tests/test_run_policy_tagging.py`

- 指纹机制：同一政策连跑两次，第二次断言 skip
- prompt 文件 mtime 变化后断言重打
- 单条失败不影响其余（mock 第 2 条抛异常，断言其余 4 条正常写入）

## 6. T5：policy_index.py

### 6.1 函数签名

**这四个函数是存储层的唯一出口**（开发计划 11.5）。政策库现在 111 条可以全量读内存，万级规模时要换 SQLite 或分片存储——届时只改这四个函数的内部实现，上层不动。所以**其他模块一律不许直接读 `policy_snapshot.json`**，全部走这里。

```python
def load_policy_tags() -> Dict[str, Dict]           # {fusionPolicyId: 标签}，lru_cache
def search_policies(a_tags=None, c_tags=None, b_tags=None, d_levels=None,
                    region_tags=None, keyword="", limit=20) -> List[Dict]
    """按标签检索，返回政策摘要列表（不含全文）。"""
def get_policy_detail(fusion_policy_id: str) -> Dict
    """按需读单条全文。不做批量——批量读全文是万级规模下爆内存的主因。"""
def iter_policies() -> Iterator[Dict]
    """流式遍历，供打标脚本用。不返回 list，避免全量驻留内存。"""
def resolve_timeliness(window: Dict, today: date) -> Dict
    """返回 {"band": "not_started"|"in_progress"|"past_year"|"unknown", "bonus": 15|10|5|8|0, "basis": str}"""
```

### 6.2 检索逻辑

- 各维度**取交集但不苛刻**：政策 C9（通用）应对所有 `c_tags` 查询都命中；政策无 B 标签时不因 `b_tags` 过滤而被排除
- `confidence=low` 的维度**不参与过滤**，只影响排序（开发计划 3.2 约束）
- 排序：先按命中维度数降序，再按 `confidence` 高低，最后按 `fusionPolicyId` 稳定排序（保证结果可复现，便于测试）
- 返回摘要只含：`fusionPolicyId`、`title`、`tags`、`applicationWindow`、`policyInfo.summary` 前 200 字。**不返回全文**（开发计划 7.2 节，防上下文膨胀）

### 6.3 时效性判定（开发计划 6.2）

```
today < startDate 且同年        → not_started,  +15
startDate ≤ today ≤ endDate    → in_progress,  +10
today > endDate 且 endDate 年份 == 2025 → past_year, +8
today > endDate 其他年份        → past_year,    +5
window 为 null 或日期缺失        → unknown,      +0
```

`isRolling=true`（常年受理）按 `in_progress` 处理。2025 年 +8 的特例值写在 `tag_taxonomy.json` 的 `scoring` 段，不硬编码。

### 6.4 测试 `tests/test_policy_index.py`

- 检索：C9 政策对任意 `c_tags` 查询都命中
- 检索：政策无 B 标签时不被 `b_tags` 过滤掉
- 检索：`confidence=low` 的维度不参与过滤
- 排序稳定性：同一查询跑两次结果完全一致
- 时效性五档各一个用例 + `isRolling` 用例
- 跨年边界：`today=2026-01-01`，`startDate=2026-03-01` → `not_started`；`startDate=2025-03-01` → `past_year` +8
- 摘要不含全文（断言返回 dict 里没有 `structuredConditions`）

## 7. T6：验收

### 7.1 自动化

```powershell
python -m pytest backend/PEMatching_v2/tests -q
```

### 7.2 打标质量抽检

从 111 条里抽 30 条（**分层抽样**：10 条通用普惠、10 条产业专项、10 条随机），人工核对：

| 维度 | 准确率要求 | 判定标准 |
|---|---|---|
| A 支持方式 | ≥85% | 主标签正确即算对，次标签不计 |
| C 行业领域 | ≥85% | 大类正确即算对；子类漏标不算错（覆盖率天然低），子类**错标**算错 |
| D 申报门槛 | ≥85% | 三档判对 |
| 申报期 | ≥95% | 已改为确定性提取（见 3.5），96.4% 走结构化字段与正则，不依赖模型；抽不出算正确处理 |
| C 枚举合法性 | **100%** | 出现任何政策库词表值（如"通用行业"）即为不通过，需查 prompt 与校验逻辑 |

抽检结果记入 `output/phase2_manual_review.md`，逐条列出政策 ID、各维度模型判定、人工判定、是否一致。

## 9. 风险

| 风险 | 应对 |
|---|---|
| 模型把 `industryField` 原值当 C 标签输出 | 双保险：prompt 明确禁止 + `validate_tagging_result` 枚举校验拒绝并重试。测试 4.4-2 专门验证 |
| 申报期编造 | 已消除：改为确定性提取（3.5），结构化字段不可能编造；仅 4 条走 LLM 兜底且抽不出即为 null |
