# 企业政策双链路匹配优化实施计划

## 一、方案摘要

| 项目 | 最终方案 |
|---|---|
| 计划文档 | `backend/PEMatching/docs/企业政策关联匹配优化实施计划.md`；切换到执行模式后先将本计划原文写入该文件 |
| 企业输入 | 不修改现有企业请求体，不要求上游新增字段，不修改现有标准化字段及取值 |
| 原匹配链路 | 完整保留现有申报要求匹配，继续独立生成 `matchScore`、`isRecommended`、`matchedConditions` 等结果 |
| 新关联链路 | 对同一企业和每一条政策额外执行一次独立的政策关联判断，生成 `associationScore` 及关联证据 |
| 两个分数 | 一个政策并列拥有“申报要求匹配分”和“政策关联分”，两者不加权、不相加、不互相修正 |
| 默认排序 | 保留现有按 `matchScore` 和证据覆盖率排序的行为；`associationScore` 仅作为新增结果返回 |
| 执行范围 | 默认对本次加载的全部政策执行两条链路；`policyId`、`policyKeyword`、`policyLimit` 仍可用于定向测试 |
| 核心边界 | 关联度只表达政策与企业发展特征是否相关，不表示企业符合申报资格，不得改变原 `isRecommended` |

## 二、双链路架构

```text
现有企业请求体
       |
       +--> 现有标准化与申报要求匹配链路
       |        |
       |        +--> matchScore / isRecommended / matchedConditions
       |
       +--> 新增政策关联匹配链路
                |
                +--> associationScore / associationLevel / associationReasons

最终按 fusionPolicyId 合并到同一政策结果
默认排序仍只使用现有 matchScore 规则
```

### 2.1 原链路保护要求

新增关联功能不得修改以下任何行为：

| 保护项 | 要求 |
|---|---|
| 企业输入契约 | `POST /api/pematching/match/enterprise` 继续接收现有完整企业对象 |
| 企业标准化 | 不新增必填字段，不改变金额、比例、人数、资质、行业和地区的现有标准化语义 |
| 申报条件判断 | 不修改模型事实提取、本地比较、硬性失败、缺失分、直通车及条件分 |
| 原匹配分 | `matchScore`、`final_score` 的计算公式和取值保持不变 |
| 原推荐结论 | `isRecommended` 继续只由原申报匹配链路决定 |
| 原排序 | 继续按原匹配分和原证据覆盖率排序 |
| 原接口字段 | 原有字段名称、类型、含义和层级保持兼容 |
| 原归档 | 现有申报条件输入、模型事实和计分详情原样保留 |

关联服务只读使用现有企业对象、现有标准快照和现有政策对象。为避免共享字典被意外修改，传入关联链路的企业画像和政策摘要使用独立只读副本；关联结果只能挂载到新增的 `associationMatch` 节点。

### 2.2 执行顺序与隔离

1. 每条政策继续按当前逻辑完成申报条件匹配。
2. 对同一企业、同一 `fusionPolicyId` 独立调用政策关联模型。
3. 两条链路分别捕获异常、分别记录状态，不共享分数或推荐结论。
4. 通过 `fusionPolicyId` 合并结果，禁止按数组下标或政策标题关联。
5. 关联链路失败时，原匹配结果照常返回；不得把关联失败转换成原政策匹配失败。
6. 最终政策列表继续使用原排序逻辑，不使用关联分参与默认排序。

## 三、新关联链路判断规则

### 3.1 七个关联维度

| 维度 | 权重 | 使用现有企业数据 | 政策关联方向 |
|---|---:|---|---|
| 所属行业 | 20 | 行业领域、高新技术领域、产品、服务、企业简介 | 软件、数字经济、先进制造、科技服务等行业专项 |
| 企业规模 | 15 | 企业规模、员工人数、营业收入、资产总额 | 小微、中小微、成长型、规上培育、采购支持、融资增信 |
| 成立阶段与资质进阶 | 15 | 注册日期、注册类型、现有资质荣誉 | 初创、台外资、首次认定、复核以及资质进阶政策 |
| 研发状态 | 15 | 研发费用、研发人员、研发机构、研发科目、知识产权 | 技术合同、技术交易、研发补助、国高、专精特新、研发机构 |
| 用工与就业 | 10 | 员工人数、新增人数、高校毕业生人数 | 就业、培训、社保、稳岗、招工招才 |
| 注册区域与园区 | 15 | 注册地址、行政区、园区字段 | 厦门六区、火炬高新区、自贸区及其他区域政策 |
| 学历与高层次人才 | 10 | 博士、硕士、本科、职称、人才资质 | 博士后工作站、生活补助、安家补贴、“双百计划”等 |

这些字段均从企业已经提交的原始对象和现有标准化快照中读取。字段缺失时返回 `unknown`，不修改企业对象，也不要求本次改造补录数据。

### 3.2 模型职责

模型不直接决定申报资格，也不直接输出任意总分。模型针对每个维度返回：

```json
{
  "dimension": "industry",
  "status": "strong",
  "enterpriseEvidence": [
    {
      "field": "行业领域",
      "value": "软件和信息技术服务业"
    }
  ],
  "policyEvidence": [
    {
      "field": "industryField",
      "text": "软件和信息技术服务业"
    }
  ],
  "reason": "企业所属行业与政策明确支持行业一致"
}
```

允许的 `status` 只有：

| 状态 | 本地系数 | 含义 |
|---|---:|---|
| `strong` | 1.00 | 企业特征与政策支持对象直接一致 |
| `medium` | 0.70 | 主要方向一致，但阶段或细分条件只部分对应 |
| `weak` | 0.40 | 存在合理潜在关联，但关键事实不足 |
| `conflict` | 0.00 | 企业已知事实与政策范围明确冲突 |
| `unknown` | 0.00 | 输入证据不足，不能判断 |
| `not_applicable` | 不进入分母 | 本维度与该政策无关 |

本地计算公式：

```text
associationScore =
    Σ(有效维度权重 × 状态系数)
    ÷ Σ(非 not_applicable 维度权重)
    × 100
```

关联等级固定为：

| 分数范围 | `associationLevel` |
|---|---|
| `80-100` | `strong` |
| `60-79.99` | `medium` |
| `30-59.99` | `weak` |
| `0-29.99` | `none` |
| 无有效结果 | `unknown` |

`isAssociated` 仅表示 `associationScore >= 60`，与原 `isRecommended` 完全独立。

### 3.3 业务边界

| 场景 | 判断要求 |
|---|---|
| 从业人数不超过300人 | 只能形成“小微候选关联”；不得仅凭人数认定法定小微企业资格 |
| 中小微企业 | 可关联采购、融资和就业支持，但理由必须标明仍需结合行业、营收或资产核验 |
| 规上企业 | 优先使用现有企业规模字段；缺少明确规模结论时只能作为成长型关联 |
| 资质进阶 | 可关联现有资质的复核政策和具有明确先后关系的下一阶段政策 |
| 无研发数据 | 不能直接认定“无研发”；只能标记研发状态未知，并结合行业、技术合同等其他事实判断 |
| 明确无研发 | 可关联技术合同登记、技术交易奖励及不依赖研发投入的政策 |
| 有研发 | 可关联研发补助、国高、专精特新、新型研发机构等政策 |
| 注册区域 | 必须同时引用企业地址/园区证据和政策适用区域证据 |
| 学历人才 | 博士人数不能证明博士后工作站；人才数量不能证明已经入选人才计划 |
| 相邻字段 | 研发人员占比不得证明学历人员占比，企业资质不得证明个人资质 |
| 高关联低申报分 | 可以返回较高 `associationScore`，但原 `matchScore` 和 `isRecommended` 不变 |

## 四、模型输入设计

### 4.1 企业输入

直接从当前企业对象中选择关联判断所需字段，不修改原始请求和现有标准化逻辑：

- 行业领域、高新技术领域、主要产品、产品描述、企业简介。
- 企业规模、员工人数、营业收入、资产总额。
- 注册日期、注册类型、注册地址、行政区和园区信息。
- 研发费用、研发人数、研发机构、研发科目和知识产权。
- 新增人数、高校毕业生人数、学历人数、职称人数。
- 科技型中小企业、创新型中小企业、高新技术企业、专精特新等现有资质。

不向关联模型发送统一社会信用代码、电话、邮箱、联系人、API密钥等无关或敏感字段。

### 4.2 政策输入

| 优先级 | 内容 |
|---|---|
| 必传 | 政策ID、标题、摘要、发文部门 |
| 必传 | 行业领域及路径、适用范围、适用对象 |
| 必传 | 申报要求原文、规则表中的政策要求、支持方式 |
| 必传 | 政策类型和关联文档标题 |
| 条件补充 | 当摘要、行业、适用对象和申报要求内容不足时，补充清洗后的政策正文摘录 |
| 禁止默认传入 | 申报材料清单、联系方式、附件二进制、重复正文、模型历史响应 |

正文补充按单政策限制长度，例如最多约3000个中文字符。不得直接把所有附件全文无上限送入模型。

### 4.3 输出校验

服务端必须校验：

1. 模型返回的 `policyId` 与本次 `fusionPolicyId` 一致。
2. 七个维度不重复，维度名和状态均属于固定枚举。
3. 企业证据字段必须存在于本次企业输入。
4. 政策证据必须能够在本次政策摘要或正文摘录中定位。
5. 模型不得使用未提交的企业事实进行推断。
6. 非法维度降级为 `unknown`，并记录 `association_evidence_rejected`。
7. 模型不得返回或覆盖 `matchScore`、`isRecommended`、`hard_pass` 等原链路字段。

## 五、接口与归档

原有政策结果字段全部保持不变，只新增一个独立对象：

```json
{
  "fusionPolicyId": "6617",
  "matchScore": 68.5,
  "isRecommended": true,
  "matchedConditions": [],
  "associationMatch": {
    "score": 86.0,
    "level": "strong",
    "isAssociated": true,
    "status": "matched",
    "reasons": [
      "企业所属软件和信息技术服务业与政策支持行业一致",
      "企业存在研发活动，与政策研发支持方向相关"
    ]
  }
}
```

`associationMatch` 对外字段定义：

| 字段 | 类型 | 含义 |
|---|---|---|
| `score` | `number/null` | 独立的百分制政策关联分 |
| `level` | `string` | `strong/medium/weak/none/unknown` |
| `isAssociated` | `boolean/null` | 关联分是否达到60 |
| `status` | `string` | `matched/待重试/disabled` |
| `reasons` | `string[]` | 最多三条权重最高且有证据的关联理由 |

七个维度的完整输入、模型输出、证据、拒绝原因、分项贡献、耗时和token写入现有 `runId` 完整归档，不扩大公共响应。关联归档作为新增节点保存，不改写原申报匹配明细。

## 六、失败处理与性能

| 场景 | 处理方式 |
|---|---|
| 关联模型未配置 | `associationMatch.status=disabled`，原匹配正常返回 |
| 单政策关联超时 | 按独立重试策略重试；耗尽后标记 `待重试` |
| 关联响应非法 | 本政策关联结果标记 `待重试`，保留协议错误类型 |
| 原链路成功、关联失败 | 返回完整原匹配结果，关联分为 `null` |
| 原链路失败、关联成功 | 保留原“匹配失败待重试”状态，同时允许保存独立关联结果，两个状态互不覆盖 |
| 部分政策失败 | 不影响其他政策，也不使整批请求失败 |
| 排序 | 始终保留原排序；关联失败或分数高低不得改变顺序 |

每个企业与每条政策最多新增一次正常关联模型调用，复用现有模型并发容量，不为关联链路盲目提高 `MAX_WORKERS`。日志记录政策ID、关联状态、耗时、输入字符数、token和错误类型，不记录完整企业数据。

新增环境开关用于独立启停关联链路。关闭后响应可不返回 `associationMatch`，或按兼容约定返回 `status=disabled`；默认采用始终返回该节点，以保证前端类型稳定。

## 七、测试与验收

| 测试层级 | 验收内容 |
|---|---|
| 原链路金丝雀回归 | 同一企业和政策快照在关联层关闭、开启时，除新增 `associationMatch` 外，原匹配字段逐项完全一致 |
| 输入不变测试 | 现有企业请求样例无需新增字段即可完成双链路匹配 |
| 不可变性测试 | 关联服务运行前后，企业对象、标准化快照、政策对象和原评分结果不被修改 |
| 关联计分测试 | 七维权重、六种状态、`not_applicable` 分母、等级和60分阈值正确 |
| 证据校验测试 | 伪造企业字段、伪造政策文本、错误政策ID、重复维度和非法状态均被拒绝 |
| 业务正例 | 软件企业对应软件政策、数字企业对应数字经济政策、有研发企业对应研发补助、区域企业对应辖区政策 |
| 业务反例 | 博士人数不证明博士后工作站、员工少不直接认定小微、厦门地址不证明火炬园区、研发人员不证明学历人员 |
| API契约测试 | 原字段结构和排序不变；每条政策按ID挂载正确的 `associationMatch` |
| 全政策测试 | 默认对全部已加载政策执行关联判断，不因同名政策、无规则表政策或单政策失败而漏项 |
| 归档测试 | `runId` 同时包含原申报匹配详情和新增关联判断详情，两个计算结果可独立回放 |
| 性能测试 | 对固定企业和政策集合比较开启前后的总耗时、请求数、超时率和token，不以提高并发代替容量评估 |

验收通过必须同时满足：

1. 原 `matchScore`、`isRecommended`、条件详情和默认排序无回归。
2. 企业请求体及现有标准化契约无变化。
3. 每条政策拥有独立、可解释的关联计算结果。
4. 关联模型故障不影响原匹配链路。
5. 高关联结果不会被展示或解释为“已符合申报资格”。
6. 全部政策均经过关联判断或具有明确的独立失败状态。

## 八、实施顺序

1. 将本计划落盘到指定 Markdown 文档。
2. 建立原链路输出基线和不可变性回归样本。
3. 新增独立关联提示词、模型服务、响应协议及本地计分器。
4. 从现有企业对象和政策对象构造只读关联输入，不调整原输入和标准化逻辑。
5. 在政策结果上挂载 `associationMatch`，通过 `fusionPolicyId` 合并并保留原排序。
6. 扩展完整归档、日志、环境开关和单政策失败降级。
7. 运行定向单元测试、API契约测试、全政策测试和固定样本性能测试。
