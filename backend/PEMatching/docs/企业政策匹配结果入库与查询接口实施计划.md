# 企业政策匹配结果入库与查询接口实施计划

## 1. 实施目标

本次改造以根目录 Node 服务 `3000` 端口作为统一公开入口，新增企业政策匹配结果持久化、企业最新匹配结果查询和已有匹配结果企业列表查询。

| 能力 | 公开接口 | 内部链路 |
|---|---|---|
| 执行企业政策匹配并入库 | `POST /api/pematching/match/enterprise` | `3000 → 8010 → 8080 → 达梦` |
| 查询企业最新匹配结果 | `GET /api/pematching/match/enterprise?enterpriseId=...` | `3000 → 8080 → 达梦` |
| 查询已有结果的企业列表 | `GET /api/pematching/match/enterprises` | `3000 → 8080 → 达梦` |
| 保存完整跑数 | 不公开 | `backend/PEMatching/output/enterprise_match_details` 文件归档 |

`8010` 仅负责 PEMatching 计算，`8080` 仅负责根目录 Java JDBC 与达梦数据库访问，不直接作为外部业务接口。

## 2. 数据库设计

使用单表 `SYSDBA.PEM_ENTERPRISE_MATCH_RUN`，一次匹配运行保存一行。同一企业允许保存多条不同 `RUN_ID` 的历史记录，不覆盖旧结果。

| 字段 | 类型 | 约束 | 用途 |
|---|---|---|---|
| `RUN_ID` | `VARCHAR2(32)` | 主键 | 每次运行唯一标识 |
| `ENTERPRISE_ID` | `VARCHAR2(100)` | 非空 | 上游企业接口返回的 `id` |
| `ENTERPRISE_NAME` | `VARCHAR2(500)` | 非空 | 企业名称快照 |
| `CREDIT_CODE` | `VARCHAR2(64)` | 可空 | 统一社会信用代码 |
| `POLICY_COUNT` | `INTEGER` | 非空，默认 `0` | 本次匹配政策数量 |
| `RESPONSE_JSON` | `CLOB` | 非空 | 完整 `{"policies":[...]}` 轻量响应 |
| `DETAIL_FILE_NAME` | `VARCHAR2(1000)` | 非空 | `output` 归档目录中的完整明细文件名 |
| `DETAIL_FILE_SIZE` | `BIGINT` | 非空，默认 `0` | 完整明细归档文件字节数 |
| `SCHEMA_VERSION` | `VARCHAR2(64)` | 非空 | 首版为 `enterprise-match-detail-v1` |
| `CREATED_AT` | `TIMESTAMP(6)` | 非空，默认当前时间 | 入库及最新结果排序时间 |

企业和运行元数据使用普通字段，便于列表、分页和索引查询；数量不固定且存在嵌套结构的政策列表使用 `RESPONSE_JSON` 原样保存。完整政策输入、企业快照和逐条件结果只写入 `output` 文件，不再复制到达梦，避免单次约数 MB 的大 CLOB 写入造成事务耗时和接口假超时。首版不拆分逐政策子表，后续只有在需要跨企业按政策、分数或推荐状态统计时再扩展关系表。

全新建表脚本位于 `docs/sql/pematching_enterprise_match_result.sql`。如果已经执行过包含 `DETAIL_JSON NOT NULL` 的旧脚本，则不要重复建表，改为执行 `docs/sql/pematching_enterprise_match_result_migrate_lightweight.sql`：该迁移只新增归档文件字段并将历史 `DETAIL_JSON` 改为可空，不删除旧列和历史数据。两个脚本都由用户手工执行，服务启动时不会自动修改数据库结构。

## 3. 公开接口

### 3.1 执行匹配并入库

```http
POST http://<根服务地址>:3000/api/pematching/match/enterprise
Content-Type: application/json
```

请求必须包含非空 `id`（兼容 `enterpriseId`）和 `enterpriseName`，`creditCode` 可选。缺少企业 ID 或名称时在加载政策、调用模型和持久化之前返回 `400`。

成功处理顺序：

1. `3000` 将请求转发到 `8010`。
2. `8010` 执行企业标准化和政策匹配。
3. 生成唯一 `runId`，构造轻量 `data.policies` 和完整跑数明细。
4. 使用同一个 `runId` 原子写入 `output/enterprise_match_details` 文件归档，并取得文件名和字节数。
5. 调用 `8080` 内部接口，将轻量响应、企业标识、运行元数据和归档文件关联信息事务写入达梦。
6. 文件与数据库均成功后返回现有轻量响应。

文件归档失败时不写数据库；数据库失败时保留文件用于排障，但公开接口返回 `500`，不返回未入库的伪成功结果。

### 3.2 查询企业最新匹配结果

```http
GET http://<根服务地址>:3000/api/pematching/match/enterprise?enterpriseId=900
```

按 `ENTERPRISE_ID` 查询，并以 `CREATED_AT DESC, RUN_ID DESC` 取得最新一行。接口只解析 `RESPONSE_JSON`，不读取或返回完整明细文件。

有结果时返回：

```json
{
  "success": true,
  "data": { "policies": [] },
  "meta": {
    "found": true,
    "runId": "运行标识",
    "policyCount": 0,
    "createdAt": "2026-07-31 12:00:00.000000"
  }
}
```

没有结果时返回 HTTP `200`、空政策数组和 `meta.found=false`；缺少 `enterpriseId` 返回 `400`，数据库或 JSON 解析失败返回 `500`。

### 3.3 查询已有匹配结果的企业列表

```http
GET http://<根服务地址>:3000/api/pematching/match/enterprises?page=1&size=20&enterpriseName=厦门
```

支持 `page`、`size`、`enterpriseName`，并兼容 `pageNum`、`pageNumber`、`pageSize`。`page` 最小为 `1`，`size` 范围为 `1..100`。

列表按 `ENTERPRISE_ID` 去重，每个企业只返回最新运行记录，并按最新匹配时间倒序。列表只读取普通字段，不加载 `RESPONSE_JSON` CLOB，也不读取完整明细文件。

```json
{
  "success": true,
  "data": [
    {
      "enterpriseId": "900",
      "enterpriseName": "厦门示例科技有限公司",
      "creditCode": "913502000000000900",
      "latestRunId": "运行标识",
      "policyCount": 115,
      "latestMatchedAt": "2026-07-31 12:00:00.000000"
    }
  ],
  "pagination": {
    "page": 1,
    "size": 20,
    "total": 1,
    "pages": 1
  }
}
```

`pagination.total` 表示去重后的企业数量，不是运行记录总数。

## 4. 内部 JDBC 接口

根目录 `JDBCService.java` 增加：

```http
POST /api/pematching/enterprise-match-results
GET  /api/pematching/enterprise-match-results?enterpriseId=...
GET  /api/pematching/enterprise-match-results/enterprises?page=...&size=...
```

保存请求中的 `responseJson` 作为字符串传输，Java 使用字符流写入 CLOB；同时保存 `detailFileName` 和 `detailFileSize`，不传输完整明细 JSON。保存使用独立数据库连接和事务；相同 `runId`、相同企业 ID 的重试按幂等成功处理，相同 `runId`、不同企业 ID 返回 `409`。

## 5. 测试与部署

专项验证命令：

```powershell
python -m pytest backend\PEMatching\test_single_enterprise_match_api.py -q
python -m pytest backend\PEMatching\test_enterprise_api_loader.py -q
python -m compileall -q backend\PEMatching\api_server.py
node --check server.js
mvn -DskipTests package
git diff --check
```

重点覆盖企业 ID 校验、文件与数据库共用 `runId`、存储失败、重复运行、最新结果、无结果、企业去重分页、名称搜索、CLOB 中文和大 JSON，以及 Node POST/GET 方法分流。

部署顺序：

1. 用户按数据库现状执行全新建表 SQL 或旧表轻量化迁移 SQL（二选一）。
2. 重启 Java JDBC `8080`。
3. 重启 PEMatching `8010`。
4. 重启 Node `3000`。
5. 通过 `3000` 执行一条 `policyLimit=1` 的匹配。
6. 验证文件与数据库 `RUN_ID` 一致。
7. 验证企业列表和企业最新结果接口。
